# IPC and App Wiring

- **Purpose** — The Tauri command surface that the Svelte frontend calls into (`src-tauri/src/ipc/`), the `AppState` it's injected with, the interactive tool-approval round-trip (`ipc/approval.rs`), and the `lib.rs::run` bootstrap that builds every long-lived service (storage, model manager, privacy gate, tool dispatcher) and hands them to Tauri via `.manage()`.

- **Files**
  - `src-tauri/src/ipc/mod.rs` — `AppState`, all `#[tauri::command]` handlers, request/response DTOs, arg-parsing helpers. This is the only place command names are defined.
  - `src-tauri/src/ipc/approval.rs` — `ApprovalRegistry` (parks pending approvals keyed by request id) + `TauriApprovalPrompter` (implements `hooks::ApprovalPrompter`: emits `tool:approval_request`, awaits a oneshot with a deny-by-default timeout).
  - `src-tauri/src/ipc/contract_tests.rs` (`#[cfg(test)]`, wired from `mod.rs:32`) — regression lock for the Tauri v2 "args nested under `args`" wrapping bug; drives real IPC dispatch (`tauri::test::get_ipc_response`) against the actual `invoke_handler` table.
  - `src-tauri/src/lib.rs` — `run()`: builds `Storage`, `ModelManager`, the classifier, `PrivacyGate`, `ApprovalLedger`/`ApprovalRegistry`/`TauriApprovalPrompter`, `build_tool_dispatcher`, `AgentLoop`, then `app.manage(AppState{...})` and `.invoke_handler(tauri::generate_handler![...])`.
  - `src-tauri/src/main.rs` — 9-line shim, just calls `lost_harness_product_lib::run()`.
  - `src-tauri/tauri.conf.json` — window config; `app.windows[0].url = "app.html"` is the fix for a blank-GUI bug (see Gotchas).
  - `src/lib/api/tauri.ts` — the **frontend-side mirror** of this contract. Its header comment is the canonical list of commands/events; every command/event added or renamed in Rust must be updated here too (this is a manual sync, not generated).

- **Key types / traits / functions**
  - `AppState` — `ipc/mod.rs:55-62`. Four `Arc` fields, no outer `Mutex`: `agent_loop: Arc<AgentLoop>`, `model_manager: Arc<ModelManager>`, `storage: Arc<Storage>`, `approvals: Arc<ApprovalRegistry>`. Injected into commands via `state: State<'_, AppState>`.
  - `SendMessageArgs` / `SendMessageResponse` — `ipc/mod.rs:172-183` / `68-80`. `profile` is required (not `Option`) deliberately, to avoid silently writing to the wrong profile db.
  - `ResolveApprovalArgs` — `ipc/mod.rs:421-435`. `decision: String` ("approve"/anything-else=deny), `scope: Option<String>` ("once"|"session"|"always", default once), `target: Option<String>` ("action"|"tool", default action).
  - `send_message(app: AppHandle, state: State<'_, AppState>, args: SendMessageArgs) -> Result<SendMessageResponse, String>` — `ipc/mod.rs:365-417`. Calls `state.agent_loop.process_message(...)`, then re-queries the profile db for the most-recently-persisted assistant message id (there's no direct return of the id from `process_message`).
  - `resolve_tool_approval(state, args: ResolveApprovalArgs) -> Result<bool, String>` — `ipc/mod.rs:442-471`. Builds an `ApprovalDecision` from the frontend's approve/deny + scope/target and calls `state.approvals.answer(id, closure)`. **Enforces `Once ⇒ action`-only** even if the frontend sends `target: "tool"` with `scope: "once"` (`want_tool` requires `!matches!(scope, GrantScope::Once)`, `ipc/mod.rs:456-457`) — defense in depth against a "just this once" answer silently becoming a whole-tool grant.
  - `ApprovalRegistry` — `ipc/approval.rs:58-113`. `pending: Mutex<HashMap<String, Pending>>`. `park(id, oneshot::Sender<ApprovalDecision>, fingerprint, tool_name)` stores a pending approval; `answer(id, mk: FnOnce(&str,&str)->ApprovalDecision) -> bool` takes it out and sends the decision (the frontend never has to echo the fingerprint back — it's stored server-side at park time and threaded through `mk`).
  - `TauriApprovalPrompter` — `ipc/approval.rs:117-183`. Implements `hooks::ApprovalPrompter::request()`: parks a channel, emits `tool:approval_request`, then `tokio::time::timeout(self.timeout, rx).await` (constructed with a 300s / 5-min timeout in `lib.rs:89`); on timeout or a dropped sender, returns `ApprovalDecision::Timeout` (fail closed).
  - `build_tool_dispatcher(base_path, classifier, ledger, approver) -> ToolDispatcher` — `lib.rs:198-255`. Registers the 6 fs tools, derives the policy **from each tool's `RiskClass`** (`Safe` ⇒ `PermissionMode::Allow` + pre-trusted; `Write|External|Dangerous` ⇒ `PermissionMode::Ask`), builds the pretooluse chain, and calls `.with_approval(ledger, approver)`.
  - `run()` — `lib.rs:41-137`. Sequential setup: storage → model manager (+ hydrate providers) → classifier (`RulesClassifier`) → `PrivacyGate` → approval spine (ledger + registry + prompter) → tool dispatcher → `AgentLoop` → `AppState` → `app.manage()` → `invoke_handler![...]`.

- **Data flow / how it fits**
  1. **Boot**: `main.rs` → `lib.rs::run()`. Builds every long-lived Arc'd service in a fixed order (storage must exist before providers can be hydrated; classifier must exist before the gate and the tool dispatcher, since both share the *same* `Arc<dyn Classifier>` so message-gate and tool-gate classify identically — comment at `lib.rs:66-72`). Ends with `app.manage(state)` and command registration.
  2. **Normal command call**: frontend `tauriInvoke("cmd", { args: {...} })` → Tauri deserializes into the command's typed `args` param → handler runs against `State<AppState>` → returns `Result<T, String>` (Err becomes a JS-thrown string).
  3. **send_message**: frontend calls `send_message` → `AgentLoop::process_message` (in `agent/loop_mod.rs`) does gate → route → stream, emitting `stream:token` (payload `{token, conversation_id, message_id}`) and `stream:error` (`{error, conversation_id, source}`) events as it goes → the command's own return value only carries the final assembled text, arriving after streaming is done.
  4. **Tool approval round-trip** (only for `Write|External|Dangerous` tools): `ToolDispatcher::dispatch` (`tools/dispatch.rs`) hits an `Ask` from the gating chain → calls `approver.request(ApprovalRequest{...})` → `TauriApprovalPrompter` parks a oneshot in `ApprovalRegistry` and emits `tool:approval_request` → frontend shows a dialog and calls `resolve_tool_approval` → that command looks the id up in `state.approvals` (same registry) and sends the decision down the oneshot → the parked `dispatch` call wakes, grants into `ApprovalLedger` if approved, and **re-runs the full gating chain** (bounded to `MAX_APPROVAL_ROUNDS = 4`, `tools/dispatch.rs:145`) before actually executing the tool.
  5. **Frontend mirror**: `src/lib/api/tauri.ts` is the sole frontend entry point into all of this — stores call it, components call stores. It also has a full in-browser mock fallback (`isTauri()` check) for developing the UI without the Tauri shell.

- **Invariants (do NOT break)**
  - **Args-nesting contract**: every command whose signature is `fn cmd(state: State, args: SomeArgs)` requires the frontend to call `invoke("cmd", { args: {...snake_case} })` — Tauri v2 nests a struct param under its own parameter name, and does NOT camelCase→snake_case struct fields (only top-level scalar param names). Commands with a bare scalar param (`remove_provider(id: String)`) are the exception and take `{ id }` unwrapped (`ipc/mod.rs:333`, `tauri.ts:228`). This is enforced by `ipc/contract_tests.rs`, which round-trips both the correct shape and the old broken flat/camelCase shape and asserts the latter is rejected at the IPC boundary (`is_ipc_arg_rejection`, `contract_tests.rs:161-163`).
  - **API keys never round-trip to the frontend.** `ProviderInfo` (`ipc/mod.rs:84-91`) and its `From<Provider>` impl omit `api_key`; both `ipc/mod.rs::tests::provider_info_omits_api_key` and `contract_tests.rs::add_provider_correct_shape_dispatches_and_succeeds` assert the raw JSON text doesn't contain the test secret.
  - **A `Once`-scope approval is action-scoped only, never tool-scoped.** Enforced twice: `resolve_tool_approval`'s `want_tool` gate (`ipc/mod.rs:456-457`) and `ApprovalLedger::grant`'s defensive no-op arm for `(Once, Tool(_))` (`hooks/approval.rs:160`).
  - **Approval resolution never touches the agent loop's stream lock.** `resolve_tool_approval` only touches `state.approvals` (the `ApprovalRegistry`), so it can always answer a parked dispatch even while `send_message`/`process_message` holds `AgentLoop`'s internal `tokio::sync::Mutex` — this is the deadlock-free property called out in the module docs at `ipc/mod.rs:437-441` and `ipc/approval.rs:9-13`.
  - **Fail-closed on prompt failure or timeout.** If `app.emit(...)` fails (no window yet) or nothing answers within 300s, `TauriApprovalPrompter::request` still resolves to `ApprovalDecision::Timeout`, which the dispatcher treats as a denial (`ipc/approval.rs:143-144, 163-167`).
  - **Tool risk gating is derived, not hand-maintained.** `build_tool_dispatcher` sets policy purely from `tool.risk()` (`lib.rs:236-245`) — adding a new tool to the registry can't accidentally skip gating; a new `Write`/`External`/`Dangerous` tool is `Ask` by construction.
  - **`Storage`'s `unsafe impl Send + Sync`** (documented in `ipc/mod.rs:18-24`, defined in `storage::Storage`) is sound only because every access goes through the single-threaded-per-command Tauri boundary plus the agent loop's own stream-serializing lock. Don't add a code path that touches `Storage` from a raw spawned task outside that discipline without re-auditing this.
  - **`app.windows[0].url` must stay `"app.html"`**, matching `vite.config.ts`'s `rollupOptions.input = resolve(__dirname, "src/app.html")`. It was previously unset/defaulted to `/`, which 404'd (blank GUI) — see Gotchas.

- **Gotchas / watch-items**
  - **`send_message` and `resolve_tool_approval` are absent from `contract_tests.rs`'s mock harness** (`contract_tests.rs:83-104` explicitly excludes `send_message` — a bare `AppHandle` param hard-codes the `Wry` runtime and won't compile against `MockRuntime`). Coverage for those two lives elsewhere: `send_message`'s business logic is covered by `agent::loop_tests` (never through real IPC arg deserialization), and `resolve_tool_approval` only has the registry-level unit tests in `ipc/approval.rs:185-218` (no test drives it through the actual `tauri::generate_handler!` dispatch path). If you touch `ResolveApprovalArgs`'s shape, there is no contract test that would catch a wrapping regression the way there is for `create_conversation` et al.
  - **`get_active_profile` and `list_profiles` are stubs.** `get_active_profile` (`ipc/mod.rs:231-234`) always returns `"personal"`; there's no per-profile routing wired yet ("per-profile routing lands when the UI ships the cycle chip"). Don't assume the returned value reflects any real UI state.
  - **`get_app_version` returns a hardcoded literal** `"0.1.0-m1"` (`ipc/mod.rs:225-227`), not `tauri.conf.json`'s `version` field (`"0.1.0"`) or `CARGO_PKG_VERSION`. These will drift; if you bump the app version, this string won't follow automatically.
  - **`send_message`'s `message_id` is recovered by a heuristic re-query**, not returned directly by `process_message`: it opens the profile db again and picks the most recent row with `role == "assistant"` (`ipc/mod.rs:394-407`), falling back to a fresh random UUID if that lookup fails for any reason. A future agent adding concurrent sends to the same conversation should double check this doesn't pick up the wrong message.
  - **The known, deferred single-in-flight limitation**: `dispatch.rs:211-217` notes that `process_message` holds the agent loop's stream lock across the `approver.request(...).await`, so while a tool-approval prompt is outstanding, the whole app is single-in-flight — a second `send_message` call blocks until the prompt is answered or times out. Documented as intentional-for-now, not a bug; a real fix needs a concurrency-model refactor (release the lock while parked + a cancel command).
  - **`ApprovalRegistry.answer`/`TauriApprovalPrompter.request` race** is explicitly documented and accepted (`ipc/approval.rs:169-178`): in a vanishingly small window, both a timeout and a concurrent `answer` can both "complete," so `resolve_tool_approval`'s return value can lie about delivery even though the *security* outcome (deny-by-default) stays correct. Don't chase this as a bug.
  - **`tauri.conf.json`'s `app.security.csp` is `null`** (`tauri.conf.json:26`) — i.e. **no CSP is enforced**. If this subsystem ever needs to tighten security posture, this is the first thing to look at; currently it's wide open.
  - **The frontend bridge is a hand-maintained mirror, not generated.** `src/lib/api/tauri.ts`'s header comment is the documented contract, and its own doc-comment says "If you add or rename a command or event on the Rust side, update the matching type, constant, or function below." There's no build step enforcing this beyond the `contract_tests.rs` arg-shape regression test — a renamed Rust command/event with no corresponding TS update won't be caught automatically except by that one test's specific coverage (create_conversation, list_conversations, get_messages, add_provider, list_models) or by hand-testing in the app.
  - **`ProviderKind` serializes lowercase** (`#[serde(rename_all = "lowercase")]`, referenced at `contract_tests.rs:326-329`) and the frontend compares against lowercase strings in multiple `.svelte` files — a regression to PascalCase would silently break provider-kind checks in the UI without any type error, since the frontend's `ProviderInfo.kind` type is just `string`.
  - `mod.rs`'s own module doc (`ipc/mod.rs:1-29`) is a good first read before touching this file — it states the conventions (command naming, Result<T,String>, event naming `<domain>:<action>`) that any new command/event should follow.

- **How to extend**
  - **New command**: add a `#[tauri::command]` fn in `ipc/mod.rs` (define an `Args` struct if it needs more than trivial scalar params — remember non-scalar params get the `args`-wrapper contract), add it to the `tauri::generate_handler![...]` list in `lib.rs` (and to `contract_tests.rs`'s mirrored list if it's a model-free command that can run under `MockRuntime`), then mirror the function + any new type in `src/lib/api/tauri.ts` (both the header-comment contract listing and the actual `tauriInvoke` call + browser-mode fallback). Add a contract test pair (correct-shape / old-broken-shape) in `contract_tests.rs` following the existing pattern if the command takes a struct arg.
  - **New event**: choose a `<domain>:<action>` name, emit it via `app.emit(name, payload)` from wherever it's raised (see `stream:token`/`stream:error` in `agent/loop_mod.rs`, `tool:approval_request` in `ipc/approval.rs`), define the payload struct with `#[derive(Serialize)]`, then add a matching TS interface + `on<Event>` subscribe helper in `tauri.ts`, updating its header-comment "Events" list.
  - **New gated (state-changing) tool**: implement it under `tools/`, give it the right `RiskClass` (`Write`/`External`/`Dangerous` routes it through the approval spine automatically via `build_tool_dispatcher`'s derivation — no IPC-layer change needed), register it in `build_tool_dispatcher` (`lib.rs:220-225`). The approval UI path (`tool:approval_request` → `resolve_tool_approval`) is already generic over tool name/fingerprint, so it needs no changes for a new tool.
  - **Changing the approval timeout**: it's the `Duration::from_secs(300)` literal passed to `TauriApprovalPrompter::new` in `lib.rs:89` — change it there.
  - **If the GUI goes blank again**: check `tauri.conf.json`'s `app.windows[0].url` still points at `"app.html"` and that it still matches `vite.config.ts`'s `rollupOptions.input`.
