## Summary of the second pass (2026-07-29)

The first pass (`70b5711`) fixed H-11 and *documented* M-20 in this file. But
documentation in a progress note does not change what CI does. CI was still
running `cargo audit` with `continue-on-error: true`, so 19 known warnings

identical to them. That is the "noisy, not deliberate" state the packet called
out.

This pass converts the prose into an enforced, dated exception list:

- **New file** `src-tauri/.cargo/audit.toml` — the 19 advisories, grouped by

  that reads that file, instead of an advisory step that ignores it.

Net effect: the 19 known-unfixable advisories are silent, and **anything else
fails the build**. Verified below by removing an entry and watching CI's
command go red.

### Step 2 — which tool does this repo actually run?

Checked `.github/workflows/build.yml` before choosing. It used
`rustsec/audit-check@v2.0.0`, i.e. **cargo-audit**, not cargo-deny.
`cargo-deny` is not installed and is not referenced anywhere in the repo
(`which cargo-deny` → not found). So the correct config file is
**`audit.toml`**, not `deny.toml`. Local tool: `cargo-audit 0.22.2`.

cargo-audit reads `.cargo/audit.toml` relative to its working directory, and CI
runs the audit with `working-directory: src-tauri` — hence the file lives at
**`src-tauri/.cargo/audit.toml`**.

### Step 3 — the exception file

`src-tauri/.cargo/audit.toml` lists all 19 IDs in three groups, each carrying
*why* and an exit condition:

| Group | Crates | Why it can't be fixed | Exit condition |
|---|---|---|---|
| 1. GTK3 / gtk-rs 0.18.x | glib (unsound) + atk, atk-sys, gdk, gdk-sys, gdkwayland-sys, gdkx11, gdkx11-sys, gtk, gtk-sys, gtk3-macros, proc-macro-error | webkit2gtk is GTK3; no GTK4 port; glib 0.20 is breaking and gtk 0.18.2 won't take it | Tauri ships a non-GTK3 Linux webview, or we drop Linux |
| 2. unic-* | unic-char-property, unic-char-range, unic-common, unic-ucd-ident, unic-ucd-version | tauri-utils 2.9.3 pins urlpattern 0.3.x, which depends on unic-* | Tauri release whose tauri-utils moves off urlpattern 0.3 |
| 3. tokenizers transitives | number_prefix, paste | both are at their **final published version** — "unmaintained" means the author stopped, not that a fix exists; there is no upgrade target | indicatif / tokenizers drop them upstream |

**Global revisit date: `2027-01-31`**, written into the file, with an explicit
rule that a past revisit date is a bug and that the correct procedure is to
empty the list, re-run `cargo audit`, and re-justify whatever still fires.

**Residual-risk note on the one non-trivial entry.** RUSTSEC-2024-0429 is the
only `unsound` (rather than merely `unmaintained`) exception. The unsoundness is
in the `Iterator`/`DoubleEndedIterator` impls for `glib::VariantStrIter`. This
app does not construct or iterate GVariant string arrays; the type is reachable
only from glib-internal paths inside the GTK3 windowing stack. Assessed as
acceptable and recorded as such in the file, with a trigger to re-assess if we
ever call glib's Variant API directly. **This is the one judgement call in the
packet** — see "Needs human decision" below.

### Step 4 — the 18 unmaintained warnings

Per the packet's option A: **codified, not left as warnings.** All 18 are in the
`ignore` list with per-group rationale, exactly like the unsound one. Deliberately
*not* done: switching `informational_warnings` off for the `unmaintained` /
`unsound` categories. That would have silenced these 18 with one line, but it
would also silence every *future* unmaintained or unsound crate — which is the
"quietly permanent" failure this packet exists to prevent. Enumerating the 18 by
ID keeps the categories armed.

### Step 5 — CI now consumes the file

`.github/workflows/build.yml`, audit step, before:

```yaml
      - name: cargo audit (advisory)
        uses: rustsec/audit-check@v2.0.0
        with:
          token: ${{ secrets.GITHUB_TOKEN }}
          working-directory: src-tauri
        continue-on-error: true
```

after:

```yaml
      - name: cargo audit (gate — exceptions in src-tauri/.cargo/audit.toml)
        if: matrix.os == 'ubuntu-latest'
        working-directory: src-tauri
        run: |
          cargo install cargo-audit --locked --version ^0.22
          cargo audit
```

Three deliberate changes:

1. **`continue-on-error` removed.** The step can now fail the build. This is
   only safe *because* the exceptions are codified — previously it would have
   failed on all 19.
2. **Direct `cargo audit` instead of the action.** `rustsec/audit-check` carries
   its own `ignore` inputs and does not read `.cargo/audit.toml`; using it would
   have split the exception list across two files with the rationale in only one
   of them. Running the binary directly makes `audit.toml` the single source of
   truth. The gate itself (`deny = ["warnings"]`) also lives in that file, so the
   CI command is just `cargo audit` with no flags to drift out of sync.
3. **Pinned to ubuntu-latest.** The check is lockfile-only and OS-independent;
   running it on all three matrix legs was triplicated work.

## 2. `"unnotice"` removed from `informational_warnings`

```diff
-informational_warnings = ["unmaintained", "unsound", "notice", "unnotice"]
+informational_warnings = ["unmaintained", "unsound", "notice"]
```

`unnotice` is not a rustsec informational category (the real ones are
`notice`, `unmaintained`, `unsound`). cargo-audit does not reject it — it
deserializes into the catch-all `Informational::Other("unnotice")` and matches
nothing — which is why the previous pass's clean run did not catch it. It was
inert before and its removal is behaviour-neutral: `cargo audit` still exits 0
after the edit (verified), and the gate test in the table above was run with the
corrected file.

I did **not** independently read cargo-audit's source to confirm the
`Informational::Other` deserialization path; the claim I can back with observed
output is narrower and sufficient — the value never produced an error and its
removal changed nothing.

## 3. The `revisit: 2027-01-31` date is a COMMENT ONLY — nothing enforces it

Stating this plainly, because the previous pass's wording ("Nothing gets added
without a … REVISIT date", "an exception with a past REVISIT date is a bug")
reads like a mechanism. It is not one.

- **cargo-audit's `ignore` is a flat `Vec<advisory::Id>`.** There is no per-entry
  struct, no `expires` field, no date parsing. The dates in that file live in
  `#` comments that the parser discards.
- Consequence: on 2027-02-01 nothing changes. CI stays green. The 19 exceptions
  persist silently and forever until a human opens the file on purpose. If the
  GTK3 constraint disappears tomorrow, the ignore entries would keep suppressing
  the (then-gone) advisories with no signal either way.
- **cargo-deny is the tool that does support expiry**, via
  `[[advisories.ignore]] { id = "…", reason = "…", expires = "2027-01-31" }`,
  where a passed date fails the check. cargo-deny is **not** adopted in this repo
  (not installed, not in CI) and adopting it is out of this packet's scope.

I added this warning as a comment block at the top of `audit.toml` itself so the
next reader sees it where the dates are, rather than only in this note. The only
real enforcement options are (a) adopt cargo-deny, or (b) add a scheduled CI job
that greps the dates — neither is done here. **Recommend spinning (a) out as its
own packet.**

## 4. Merge collision with P21 — build.yml audit step

`fix/p21-ci-gates` also rewrites the same CI step, in a **different and mutually
exclusive** direction. Verified by reading `git show fix/p21-ci-gates:.github/workflows/build.yml`:

| | P20 (`fix/p20-deps`, this branch) | P21 (`fix/p21-ci-gates`) |
|---|---|---|
| Step | `run: cargo install cargo-audit … && cargo audit` | keeps `uses: rustsec/audit-check@v2.0.0` |
| `continue-on-error` | removed | removed |
| Reads `src-tauri/.cargo/audit.toml` | **yes** — it is the whole point | **no** — the action has its own `ignore:` inputs and never reads the file |
| Matrix | pinned `ubuntu-latest` | unpinned |
| Also adds | — | a separate release-blocking `npm audit` step (+~208 lines elsewhere in the file) |

**This is a real conflict, not a textual one.** If P21's version of the step
wins the merge, `src-tauri/.cargo/audit.toml` becomes dead configuration: the
audit-check action will not read it, so the 19 justified advisories are no
longer covered by anything the gate consults, and P20's fix for M-20 is silently
undone.

**Recommended resolution when integrating:** take **P20's** audit step body
(direct `cargo audit`, so `audit.toml` is the single source of truth) and
**P21's** everything else in that file, including its `npm audit` step. The two
are compatible that way — they only fight over which binary runs the Rust audit.
P21's inline comment "exceptions can be configured via a deny.toml" also becomes
wrong once P20 lands (the file is `audit.toml`, not `deny.toml`, because the repo
runs cargo-audit); fix that comment or drop it during the merge.
