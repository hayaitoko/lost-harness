# Classifier (privacy egress-guard)

## Purpose

Decides, per outgoing message (and per tool-action, per drafted memory fact, per drafted skill), whether text is `Private` / `Public` / `Uncertain` so callers can route it to a cloud model or force it local. This module is the classifier only — it does not itself block or route anything; `agent::gate::PrivacyGate` (message egress) and `hooks::privacy_filter::PrivacyFilterHook` (tool-action egress) consume its output.

**As of this read, the trained model is live, not a stub.** `lib.rs:100-119` tries `EnsembleClassifier::load(&classifier_models)` first — the real INT8 ONNX ensemble (bge-small + distilbert) — and only falls back to `RulesClassifier` when the model files aren't present. A prior revision of this doc (and some in-code doc comments predating that wiring) said the ensemble was an unwired stub with no caller; that is no longer true.

## Files

- `src-tauri/src/classifier/mod.rs` — the `Classifier` trait, `Label`, `Classification`, `ClassifierConfig` (per-profile tunable thresholds). The shared interface everything else implements/consumes.
- `src-tauri/src/classifier/rules.rs` — `RulesClassifier` and the underlying `detect()` pass. Deterministic, regex-based, span-producing "layer 0" — a line-for-line Rust port of a delivered Python file (`rules.py` v3, `pf-bundle`). Runs first inside the ensemble (short-circuit) and stands alone as the rules-only fallback.
- `src-tauri/src/classifier/heuristic.rs` — `HeuristicClassifier`, the original coarse regex/keyword classifier ported from the old Electron app. Not constructed in production wiring; still the default `Classifier` used throughout the test suite (gate/hook/dispatch tests), and two of its detector functions (`detect_health_info`, `detect_home_address`) are borrowed directly by `rules.rs` as a stopgap for two categories a pure regex can't own.
- `src-tauri/src/classifier/engine.rs` — `EnsembleClassifier`. The trained model: two ONNX encoders (bge-small + distilbert) fused with the rules layer, loaded via `ort` (ONNX Runtime). Feature-gated: with `onnx-classifier` on (the default), `EnsembleClassifier` is the real implementation (`engine.rs`'s `mod onnx`); with it off, `EnsembleClassifier` is a placeholder stub (`engine.rs`'s `mod stub`) whose `load()` always errors and `classify()` always returns `Uncertain`/0.0, so the crate still compiles with zero ONNX Runtime dependency.
- `src-tauri/src/classifier/redact.rs` — `redact`/`rehydrate`/`Redaction`/`Replacement`/`is_redactable_value`. Span redaction for the agent loop's partial-delegation ("redact-and-send") path — see `agent-loop-and-privacy-filter.md`.
- `src-tauri/src/lib.rs:100-119` — where the ensemble-or-fallback choice is actually made at boot; `src-tauri/Cargo.toml:73-80` — the `onnx-classifier` feature definition (default-on) and its three optional deps (`ort`, `tokenizers`, `ndarray`).
- `src-tauri/src/hooks/privacy_filter.rs` — `PrivacyFilterHook`, the tool-action consumer. See the KNOWN GAP below.
- `src-tauri/src/ipc/mod.rs:1336` — `explain_classification`, the IPC command backing the "why" sidebar.
- `src-tauri/src/agent/gate.rs` — the message-egress consumer (`PrivacyGate::check_detailed`, see `agent-loop-and-privacy-filter.md`).

## Key types / traits / functions

- `trait Classifier: Send + Sync` — `mod.rs:224`. `classify(&self, text: &str) -> Classification` is the primary method; `classify_with(&self, text, cfg: &ClassifierConfig) -> Classification` (`mod.rs:233`) defaults to ignoring `cfg` and calling `classify` — only `EnsembleClassifier` overrides it to actually grade against the profile's thresholds. All three implementors (`HeuristicClassifier`, `RulesClassifier`, `EnsembleClassifier`) hold behind `Arc<dyn Classifier>`.
- `enum Label { Private, Public, Uncertain }` — `mod.rs:29`. `Uncertain` is spec'd (Risk 4) to be treated identically to `Private` by every consumer — "when uncertain, route to private."
- `struct Classification { label, confidence: f32, raw_output: Vec<f32>, spans: Vec<rules::Span> }` — `mod.rs:39-54`. `spans` is populated by `RulesClassifier` (and, when the rules layer fires inside the ensemble, by `EnsembleClassifier` too — see Data flow); empty when only the transformer layer fired, and always empty for `HeuristicClassifier`.
- `struct ClassifierConfig { tau_block: f32, tau_band: f32 }` — `mod.rs:70-75`. Per-profile, runtime-tunable fusion thresholds for the trained ensemble (PLAN §11): `max_prob ≥ tau_block ⇒ Private`; `tau_band ≤ max_prob < tau_block ⇒ Uncertain`; `max_prob < tau_band ⇒ Public`. `Default` is `tau_block = 0.5, tau_band = 0.05` (`mod.rs:100-101`), matching the reference server's env defaults. **The deterministic rules layer ignores these entirely** — a structured-PII hit is always `Private` regardless of any threshold; the thresholds only grade the transformer layer's output.
  - `ClassifierConfig::from_ui(strictness: u8, band: &str) -> Self` (`mod.rs:129-145`) — the settings-page mapping. **`strictness` drives `tau_band` — this is the real egress dial**, because at the gate `Private` and `Uncertain` route identically (both stay local); the only threshold that changes what actually reaches the cloud is where the `Public`/not-`Public` line sits. Higher strictness ⇒ lower `tau_band` ⇒ more content kept on-device (log-scaled so the historical default lands at the slider midpoint). **`band` (`"narrow"|"medium"|"wide"`) drives `tau_block`, not `tau_band`** — it only widens or narrows the `Uncertain` zone above `tau_band`, a labeling/severity distinction the "why" sidebar shows; both `Private` and `Uncertain` already stay local, so this never changes egress.
  - `ClassifierConfig::to_ui(self) -> (u8, &'static str)` (`mod.rs:151-185`) — the inverse, for rendering the settings page from stored values; round-trips exactly for any value `from_ui` itself produced (`mod.rs`'s `config_tests::ui_round_trips_for_values_this_code_writes`).
  - `ClassifierConfig::sanitized(self) -> Self` (`mod.rs:199-217`) — the single validation choke point (called by `from_ui`, and by `classify_with` defensively before using a caller-supplied `cfg`). Any value outside the range the UI could actually produce — including NaN/∞, or a hand-edited DB row — resets to `Default`, then floors `tau_block` at `tau_band` so the ordering invariant always holds. **A corrupt row can never end up looser than the most permissive setting a user could deliberately choose** (strictness 0); it fails toward stricter, never toward leakier. `mod.rs`'s `sanitize_rejects_out_of_range_and_never_looser_than_strictness_zero` test is the regression lock for a specific prior leak repro (a hand-edited row with both thresholds ~1.0 used to slip through).
- `enum RuleCategory { PiiContact, PiiId, Financial, Credential, Proprietary }` — `rules.rs:74-80`. `.as_str()` gives the wire string (`"PII_CONTACT"`, etc.) matching the delivered bundle's `prompt.py::CATEGORIES`.
- `struct Span { text, start_byte, end_byte, start_char, end_char, category, rule: &'static str }` — `rules.rs:103-111`. Both byte and char offsets are carried — Rust slicing needs bytes, the original Python used codepoints, and neither is UTF-16 (what a JS/TS frontend's `String.slice()` uses) — a redaction/annotation UI consuming `Span` over IPC needs its own UTF-16 conversion.
- `pub fn detect(text: &str) -> Vec<Span>` — `rules.rs:342-438`. Structured-PII layer 0: emails, SSNs, phones (with an isolation check so a phone match doesn't fire inside a longer digit run), IPv4, service-credential tokens (Stripe `sk-`/`sk_live_`, GitHub `gh*_`, AWS `AKIA`, Slack `xox*`, Google `AIza`), labeled secrets (`password is …`), Luhn-valid card-shaped digit runs, confidentiality cue phrases, spelled-out digit runs, spaced/obfuscated digit runs (with Unicode-digit folding across ~18 `Nd` blocks, not the full Unicode set — a deliberate scope cut), leetspeak-obfuscated ID-like tokens, and obfuscated emails (`x [at] y [dot] com`). Zero lookaround (the `regex` crate is RE2-derived — also why these patterns can't ReDoS).
- `impl Classifier for RulesClassifier` — `rules.rs:464-496`. Any span found → `Label::Private @ 1.0`, spans populated, `raw_output = vec![spans.len() as f32]`. No spans, but the borrowed `heuristic::detect_health_info`/`detect_home_address` stopgap fires → `Label::Uncertain @ 0.8`, empty spans. Otherwise `Label::Public @ 1.0`. Does **not** override `classify_with` — thresholds never apply to the rules layer.
- `EnsembleClassifier::load(model_dir: &Path) -> anyhow::Result<Self>` — `engine.rs:129-168` (feature on) / `engine.rs:61-66` (feature off, always errors). Loads two `ort::Session`s + `tokenizer.json`s from `<model_dir>/tf_bge_scaled/` and `<model_dir>/tf_distilbert_scaled/` (each needs `model.int8.onnx` + `tokenizer.json`); errors — so the caller falls back to `RulesClassifier` — if either file is missing. **Critically disables tokenizer padding/truncation on load** (`engine.rs:148-151`, see Gotchas).
- `EnsembleClassifier::classify_with` — `engine.rs:277-336`. Layer 0: `rules::detect(text)` runs first; any span → immediate `Private @ 1.0` with those spans, no transformer inference at all (`engine.rs:286-294`). Layer 1: both encoders run `windowed_max_prob` (`engine.rs:172-269`) — the text is tokenized whole (no truncation), scanned in sliding 128-token windows (stride 96, each wrapped in `[CLS]`/`[SEP]`), and the **max** probability of class 1 ("private") over every window is that encoder's score, so sensitive content past token 128 can't slip through by being "later in a long message." The two encoders' scores are `f32::max`-fused into one `max_prob`. Layer 2 (fusion): `cfg.sanitized()` is applied defensively first (`engine.rs:280`, defense-in-depth against a corrupt threshold widening the filter even though `sanitized` is also applied at the storage boundary), then `max_prob ≥ tau_block ⇒ Private`, `tau_band ≤ max_prob < tau_block ⇒ Uncertain`, else `Public`. Any ONNX inference error **fails closed to `Private @ 1.0`** (`engine.rs:296-315`) rather than risking a leak.
- `pub fn redact(text, spans, nonce) -> Redaction` — `redact.rs:80-128`. Blacks out every `is_redactable_value` span (`redact.rs:28-36`: `PiiContact | PiiId | Financial | Credential` — **never** `Proprietary`, since that category is a cue phrase, not a value; redacting the cue would strip the very signal that made the message private while leaving the actual sensitive content untouched). Overlapping spans are **merged into one contiguous interval and the whole union is blacked out** (`redact.rs:93-106`) — an earlier "skip the later overlapping span" approach leaked the tail of a staggered overlap, which `redact.rs`'s `staggered_overlap_redacts_the_union_no_tail_leak` test locks in as a regression. Each placeholder embeds a per-turn random `nonce` (`redact.rs:76-79,113-114`) so untrusted content elsewhere in the conversation can't forge a `[REDACTED:…]` string that `rehydrate` would blindly expand.
- `pub fn rehydrate(reply, replacements) -> String` — `redact.rs:133-140`. Swaps each placeholder the model echoed back for its real original value; a placeholder the model didn't echo is simply left alone.
- `explain_classification(state, args: ExplainClassificationArgs) -> Result<ClassificationExplanation, String>` — `ipc/mod.rs:1336-1344`. Classifies `args.text` with `args.profile`'s actual `ClassifierConfig` (via `profile_classifier_config`, `ipc/mod.rs:1349-1361` — defaults on any read error or a `None` profile) using the **same shared classifier** the gate uses, so the "why" sidebar's explanation always matches the real routing decision. `build_explanation` (`ipc/mod.rs:1365-`) maps `Classification` to the wire shape, annotating each span with a display category/label and whether it's a "hard" category.

## Data flow / how it fits

```
lib.rs setup()
  └─ classifier_models = <storage>/models/classifier/                (lib.rs:100)
       ├─ EnsembleClassifier::load(&classifier_models) succeeds
       │    └─ classifier: Arc<dyn Classifier> = Arc::new(ensemble)   (lib.rs:109, "loaded trained ONNX ensemble classifier")
       └─ else (models missing / onnx-classifier feature off)
            └─ classifier = Arc::new(RulesClassifier::new())          (lib.rs:117, "using rules-only classifier")
  └─ shared into PrivacyGate::new(Arc::clone(&classifier))            (lib.rs:146)
  └─ shared into the tool gating chain's PrivacyFilterHook            (lib.rs, built alongside the dispatcher)
  └─ shared into AgentLoop::with_flush_classifier(Arc::clone(&classifier))  (lib.rs:200 — the pre-compaction memory flush re-classifies extracted facts with the same classifier)
       └─ PrivacyGate::check_detailed(binding, text, is_cloud_endpoint, cfg)   (gate.rs:97-140)
            - Binding::Auto → classifier.classify_with(text, cfg), then:
                Label::Public              → GateDecision::Allow
                Label::Private|Uncertain   → RouteLocal if is_cloud_endpoint else Allow
            - Binding::Public/Private bypass or hard-block without calling the classifier
```

`explain_classification` (IPC) and `PrivacyFilterHook` (tool actions) each call the same `Arc<dyn Classifier>` independently, with their own `ClassifierConfig` (the profile's, and the hardcoded default, respectively — see KNOWN GAP). `Classification::spans` feeds two consumers: `agent::loop_mod::AgentLoop::plan_redaction` (redact-and-send, via `redact()`) and `explain_classification`'s "why" sidebar; `confidence` is surfaced to the sidebar and to logging, not otherwise consumed downstream.

Audit logging: `AgentLoop::log_trm_decision` writes a `trm_logs` row (`storage/schema.rs`, `storage/profile.rs::insert_trm_log`) — hash of the text only, never the text itself, per spec §3. The table name and surrounding identifiers (`TrmLog`, `log_trm_decision`, `insert_trm_log`/`list_trm_logs`/`purge_trm_logs_older_than`) are a deliberate naming holdover from before the `trm/` → `classifier/` module rename (renaming a persisted table needs a migration) — grep both `classifier` and `trm` if you're trying to find "everything related to the classifier."

## Invariants (do NOT break)

- **`Uncertain` must never be treated as `Public`.** Enforced at `gate.rs:129` (`Label::Private | Label::Uncertain => …RouteLocal`) and equivalently inside `EnsembleClassifier::classify_with`'s own fusion (`engine.rs:322-328`, the `tau_band` branch). Any new call site that pattern-matches on `Label` must mirror this.
- **The rules layer (layer 0) is un-tunable and always wins.** `EnsembleClassifier::classify_with` checks `rules::detect` first and short-circuits to `Private @ 1.0` on any hit, **before** `ClassifierConfig` is even consulted (`engine.rs:286-294`) — no threshold, however permissive, can suppress a structured-PII hit.
- **`sanitized()` never lets a corrupt/out-of-range config become looser than the loosest value the UI itself could produce** (`mod.rs:199-217`, locked in by `config_tests::sanitize_rejects_out_of_range_and_never_looser_than_strictness_zero`). A hand-edited or corrupted `classifier_settings` row fails toward stricter, never toward leakier.
- **ONNX inference failure fails closed to `Private`, never to `Public`** (`engine.rs:296-315`) — a runtime error on either encoder is treated as "assume the worst," not "assume it's fine."
- **`RulesClassifier::classify` never returns `Uncertain` from `detect()` hits** — any span found is unconditionally `Private @ 1.0` (`rules.rs:5-9` doc comment). Only the borrowed HEALTH/LOCATION stopgap returns `Uncertain` in the rules-only path.
- **Layer 0 is tuned for recall, not precision** — the opposite bias from `heuristic.rs`'s original design goal (`rules.rs:6-12`). A false positive routes a message local (safe); a false negative is a leak. Don't "fix" a rules.rs false positive by loosening a pattern without re-reading that tradeoff.
- **The regex crate has no backtracking/lookaround**, which is also why these patterns can't ReDoS — don't introduce `fancy-regex` or similar to port a lookaround more faithfully without weighing that away.
- **Only concrete VALUE spans are redacted, never PROPRIETARY cues** (`redact.rs:9-18,28-36`) — redacting a cue phrase would strip the signal that made the message private while leaving the actual sensitive content in the sent text. The agent loop's `plan_redaction` re-classifies the redacted remainder specifically because redaction can only *propose* a safe remainder; that re-classify pass is what proves it (see `agent-loop-and-privacy-filter.md`).
- **Overlapping redaction spans are unioned, never dropped or truncated** (`redact.rs:93-106`) — a staggered overlap must black out its full combined range, not just the first span found.
- **Redaction placeholders are nonce-keyed** (`redact.rs:76-79`) — untrusted content must never be able to forge a placeholder that `rehydrate` would expand into a real value.
- **`trm_logs` logs a hash of the text, never the text itself** (spec §3) — lives in `agent/loop_mod.rs`/`storage/profile.rs`, not in `classifier/`, but any change that threads raw text further downstream from `Classification` must preserve this.
- **Byte offsets vs char offsets vs UTF-16.** `Span` carries byte + char offsets; a frontend consumer needs its own UTF-16 conversion — don't assume `start_char`/`end_char` are safe to feed straight into a JS `String.slice()`.

## Gotchas / watch-items

- **The exported `tokenizer.json` bakes in `Fixed(128)` padding and truncation — this MUST be disabled at load, or the model scores garbage.** `EnsembleClassifier::load` calls `tokenizer.with_padding(None)` and `tokenizer.with_truncation(None)` immediately after loading each tokenizer (`engine.rs:148-151`) specifically because the classifier does its own windowing + batch padding over the full un-truncated token sequence; leaving the baked-in fixed padding on would silently pad every input to 128 tokens before the sliding-window logic ever sees it, producing wrong (but not obviously wrong — no panic, no error) probabilities. If you ever re-export the tokenizer bundle or bump the `tokenizers` crate, re-verify this still takes effect.
- **The `onnx-classifier` feature is default-on but genuinely optional.** `Cargo.toml:74` sets `default = ["onnx-classifier"]`; building with `--no-default-features` (or on a target where `ort`'s native ONNX Runtime binary isn't available) compiles the stub `EnsembleClassifier` instead (`engine.rs`'s `mod stub`, feature-gated at `engine.rs:45-46`) — `load()` always errors, so the app transparently runs rules-only. Don't assume the ensemble is always compiled in; check for the feature (or just call `load()` and handle the `Err`, which is what `lib.rs` already does).
- **The model files are not in the git repository.** They live at `~/Documents/Lost-Harness/models/classifier/{tf_bge_scaled,tf_distilbert_scaled}/{model.int8.onnx,tokenizer.json}` — outside the project tree entirely, delivered separately (the `pf-bundle`/"Classifier Model + Install Guide" package) and referenced only by path at runtime. A fresh checkout or a different machine without that directory populated will silently run rules-only (by design — `lib.rs`'s `Err` branch — not a bug to "fix" by vendoring ~96 MB of model weights into git).
- **The ONNX parity test is env-gated and skips by default.** `engine.rs`'s `parity_tests::matches_python_reference_probs` (feature-gated `#[cfg(all(test, feature = "onnx-classifier"))]`, `engine.rs:340-381`) only runs when `LHP_CLASSIFIER_MODELS_DIR` is set to a directory containing the two model subdirs; otherwise it prints a skip message and returns `Ok`. `cargo test` on a machine without the models set up will report this test as passed without it having actually asserted anything — don't read a green `cargo test` alone as proof the ensemble matches the Python reference; set the env var and re-run when you actually need that guarantee.
- **`strictness` and `band` drive different thresholds, and only one of them is the egress-relevant one.** It's easy to assume the settings-page "detection strictness" slider and the "uncertainty band" control both affect what reaches the cloud. Only `tau_band` (driven by strictness) does; `tau_block` (driven by band) only relabels the borderline zone `Private` vs `Uncertain` for the sidebar — both already stay local either way. See `ClassifierConfig::from_ui`'s doc comment (`mod.rs:87-98`) before changing either mapping.
- **`RulesClassifier` doesn't override `classify_with`**, so passing it a non-default `ClassifierConfig` (e.g. accidentally, in a rules-only build) has zero effect — the rules layer simply never consults thresholds. This is intentional (see Invariants) but easy to mistake for a bug when a "stricter" setting doesn't change rules-only behavior.
- **The tool-action `PrivacyFilterHook` still gates at the DEFAULT thresholds, not the profile's** (`hooks/privacy_filter.rs:41-57`, `let cfg = ClassifierConfig::default();`). The per-profile strictness knob is threaded into message-egress (`AgentLoop::process_message`) but not into the tool-dispatch gating chain yet — carrying the profile's `ClassifierConfig` through `EventContext` from the dispatcher is a tracked follow-up (see HANDOFF). Concretely: a profile configured **stricter** than default has its tool-action content (arguments passed to tools) gated *less* strictly than its own chat messages, in the narrow borderline band between the profile's `tau_band` and the default `tau_band`. This is bounded — the rules-layer floor (SSN/keys/email/etc.) is un-tunable and still fires regardless of thresholds, so structured PII in tool args is always caught either way — but it is a real, live inconsistency, not "always safe." Don't assume tightening a profile's strictness setting protects its tool calls too.
- **`heuristic.rs`'s two `pub(crate)` functions are load-bearing, not dead code.** `detect_health_info`/`detect_home_address` (`heuristic.rs:235,269`) look orphaned until you see `rules.rs:478-486` calling them directly as the HEALTH/LOCATION stopgap for `RulesClassifier`. Don't delete or privatize them, and don't change their regexes without checking `rules.rs`'s doc comment for which categories they're standing in for.
- **`RulesClassifier`'s `raw_output` shape differs from `HeuristicClassifier`'s and `EnsembleClassifier`'s** — `HeuristicClassifier` always emits 8 floats (one per detector); `RulesClassifier` emits `vec![spans.len() as f32]` or empty; `EnsembleClassifier` emits up to 2 floats (one per encoder, fewer on early inference failure). Don't write code that assumes a fixed-length `raw_output`.
- **Unicode digit folding covers ~18 of ~66 Unicode `Nd` blocks** (`rules.rs:147-170`, `DIGIT_BLOCKS`) — a deliberate scope cut for "realistic obfuscation surface for a personal single-user tool," not exhaustive.
- **`is_isolated_run`'s digit check is ASCII-only** even though the ported Python's lookbehind was Unicode-aware (`rules.rs:317-333`) — a narrow, documented fidelity gap.
- **No entropy-based secret detector exists**, despite the module doc calling this out (`rules.rs:54-59`) — a bare high-entropy token with no `password=`/`token=`-style label is not caught by anything in `rules.rs`.
- **`trm` → `classifier` naming split.** The module was renamed from `trm/` to `classifier/`, but the persisted `trm_logs` table, `TrmLog` struct, and `log_trm_decision`/`insert_trm_log`/`list_trm_logs` function names were deliberately left as `trm` (a table rename needs a migration). Grep both `classifier` and `trm` when auditing this subsystem end to end.

## How to extend

- **New deterministic detector (structured PII / secrets)**: add a pattern in `rules.rs`'s `patterns()` (or extend `CONFIDENTIALITY_CUES`), wire it into `detect()`, choose/extend `RuleCategory`, and add both a `rules::tests` unit test and — if it changes end-to-end classification — a `RulesClassifier` trait-level test near the bottom of `rules.rs`. Keep to the deterministic, zero-lookaround, RE2-compatible constraints in the module doc comment. Remember: anything added here is un-tunable — it will fire regardless of the profile's `ClassifierConfig`, so only add a genuinely hard/structural signal, not something that wants judgment.
- **New semantic category** (PII_NAME/PII_ORG/PERSONAL_CONTEXT, or improving HEALTH/LOCATION beyond the borrowed heuristic stopgap): this is explicitly the ensemble's job (`engine.rs`'s layer 1), not `rules.rs`'s — don't grow regexes to chase these. If HEALTH/LOCATION coverage needs improving independent of the ensemble, the two borrowed `heuristic.rs` functions are the seam, but changing their regexes affects both `RulesClassifier`'s stopgap and any direct `HeuristicClassifier` caller (mostly tests) — check both.
- **Retraining or re-exporting the ONNX models**: the two subdirs (`tf_bge_scaled/`, `tf_distilbert_scaled/`) each need `model.int8.onnx` + `tokenizer.json` under whatever directory you point `EnsembleClassifier::load` at (production always uses `<storage>/models/classifier/`, i.e. `~/Documents/Lost-Harness/models/classifier/`). Re-verify the padding-disable step still works against any new tokenizer export (see Gotchas), and set `LHP_CLASSIFIER_MODELS_DIR` to run the parity test against the new weights before trusting them.
- **Changing the fusion thresholds' UI mapping**: `ClassifierConfig::from_ui`/`to_ui` (`mod.rs:129-185`) are the single source of truth the settings page renders through — don't compute thresholds in the frontend. Any change here should preserve `sanitized()`'s "never looser than strictness 0" property (re-run `config_tests::sanitize_rejects_out_of_range_and_never_looser_than_strictness_zero`-style checks against the new mapping).
- **Closing the tool-action strictness gap** (the KNOWN GAP above): thread the profile's `ClassifierConfig` through `EventContext` from `ToolDispatcher` into `PrivacyFilterHook::on_event` (`hooks/privacy_filter.rs:57`), replacing the hardcoded `ClassifierConfig::default()`. This is a tracked, not-yet-done follow-up, not a hypothetical.
- **Building the PLAN §11 "annotated review view" / interactive redaction UI**: `Classification::spans` and `explain_classification`'s IPC output already carry everything needed (`ipc/mod.rs:1336-`); the remaining work is entirely on the frontend side (a Svelte sidebar component consuming `ClassificationSpan`, converting byte/char offsets to UTF-16 for display) — no further Rust plumbing is required for a read-only "why" view.
