## The defect the reviewer reproduced, and the fix

`install_pack` committed the global transaction (skills + agent types) at the top of the function,
**before the cron transaction was even opened**. So aborting a cron insert left
`skills=1, agent_types=1, cron=0` committed on disk while `install_pack` returned `Err`. A failed
import half-populated the DB — exactly what M-13 forbids. The previous pass's own comment ("cannot
join the global transaction above") was true about SQLite but did not justify that ordering.

Fixed by reordering. The two connections are independent `parking_lot` mutexes, so both transactions
can be open at the same time:

1. open the global transaction on `global.db`, insert skills, insert agent types;
2. open the cron transaction on the profile DB, insert cron jobs;
3. `commit()` cron;
4. `commit()` global.

Mechanically: `global_conn` / `global_tx` are now `Option`s that live to the end of the function.
Every `?` at steps 1–3 returns with `global_tx` still open, and the `Transaction`'s `Drop` rolls it
back. So a cron failure now rolls back the global rows too, and a failed import lands **nothing** in
either file.

`drop(global_conn)` cannot be written explicitly (E0505 — `global_tx` borrows it and is dropped
later); scope-end drop order already handles it, which is why it is absent.

**Lock ordering:** `install_pack` is the only place in the tree that holds a `global.raw()` guard and
a profile `raw()` guard simultaneously — verified by grepping `raw()`: the only other non-storage
caller is `agent/crash_recovery.rs:95`, which takes the profile guard alone. And `open_profile` runs
*before* the global guard is taken, so it cannot need the global lock while we hold it. No cycle, no
deadlock. If someone later adds a profile-then-global path, this becomes a real hazard; the fn doc
now says so.

## The residual — stated plainly, not papered over

**Error paths are now atomic. Crashes are not.** If the process is killed (or loses power) in the
window between step 3's commit and step 4's commit, the cron jobs are durable and the skills + agent
types are not. That window is one `commit()` call wide. It is **irreducible** across two separate
SQLite files without a distributed commit protocol (two-phase commit / an intent log), and this
packet does not add one. So: **this is not perfect atomicity.** It is atomicity against every failure
`install_pack` can itself observe, plus a bounded crash window.

Mitigating, not excusing: everything a pack installs is inert — skills and agent types `Pending`,
cron jobs `enabled=0`. The worst crash outcome is a set of orphaned **disabled** cron jobs visible
and deletable in Settings. Nothing gets armed either way.

Also unchanged from before: a failing `install_pack` returns `Err` and **no** `InstallReport`. There
is no partial-report path; the previous doc claim of one was false and is gone.

## The UNIQUE-constraint question — decided NO, deliberately

The reviewer noted there is no `UNIQUE` on `skills.name` / `agent_types.name`. I looked and chose not
to add one, so **the declared scope was not expanded**. Reasons, all checked against the code:

- **Duplicate names are already normal in real DBs.** `tools/skills.rs:246` (`save_skill`) and
  `agent/skill_reflect.rs:367` (autonomous drafting) both insert skills with a fresh uuid and no name
  check. Any existing install can already hold same-named skills, so a `UNIQUE(name)` migration would
  fail outright on those DBs — a migration that bricks startup is a far worse bug than M-13.
- **It would break an autonomous path.** With the constraint, `skill_reflect` re-drafting a
  same-named skill would start erroring instead of saving.
- **Nothing depends on name uniqueness.** Grep found no `WHERE name = ?` / `*_by_name` lookup on
  either table in `storage/global.rs`; built-in agent types are keyed by fixed ids.
- **It would not make import idempotent anyway.** Install mints fresh uuids and lands items
  `Pending`; re-importing a pack is a *new set of items to review*, not an upsert. A UNIQUE constraint
  would convert "re-import, see duplicates, delete the ones you don't want" into a hard mid-transaction
  failure with (now, correctly) nothing landing — worse UX for no safety gain, since duplicates are
  inert.

Genuine idempotent import would need a pack-identity column (`source` + item name) and an explicit
upsert-or-skip policy. That is a design decision, not a constraint tweak. Flagged for the human below.

## Honest remaining limits

- The crash window between the two commits, described above. Not closed.
- The three rollback tests all inject failure with SQLite `RAISE(ABORT)` triggers. That drives the
  real rollback path, but it is a synthetic trigger, not a naturally-occurring collision — and with
  no UNIQUE constraint (see above) there is no natural collision available to use instead.
- `open_profile` is still skipped entirely for a cron-less pack, so the "profile validated before any
  mutation" guarantee only applies to packs that carry cron jobs. Harmless (nothing touches the
  profile DB in that case), unchanged from `416026b`.
- The limit values (50 skills / 25 agent types / 25 cron jobs / 256 KB fields / 1 MB payload) are
  still chosen, not derived from a measured workload.
- Holding the `global.db` connection lock across the cron insert loop widens the time that lock is
  held on an import. Imports are user-initiated and rare, and the loop is capped at 25 inserts, so
  this is a deliberate trade of a little contention for atomicity — but it is a real behaviour change
  worth knowing about.

## Needs Human Decision

- Whether the cross-DB **crash** window is worth closing at all, given every installed item is inert.
  Closing it means real machinery: an intent/journal row committed first and reconciled at startup, or
  moving cron templates into `global.db`. Moving them is arguably the cleanest answer and would delete
  the whole problem — but it is a schema/ownership change well beyond this packet.
- Whether pack **re-import** should be idempotent. If yes, the design is a pack-identity key +
  upsert-or-skip, not a `UNIQUE(name)` constraint (which would break `skill_reflect` and fail to
  migrate on DBs that already hold duplicate names).
- Confirm the chosen ceilings for real packs — notably `PACK_MAX_SKILLS = 50` against
  `PACK_MAX_CONTENT_LEN = 256 KB` and the 1 MB payload cap (50 skills cannot each be 256 KB).
