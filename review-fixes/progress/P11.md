**Status:** Complete (revise pass applied)

## Findings addressed

| ID | Finding | Fix |
|----|---------|-----|
| M-14 | setsid escape: `kill(-pgid)` misses descendants in a new session/group | Process-tree kill, **snapshot before signal**, re-scan until stable |
| M-15 | Unescaped path interpolation into the Seatbelt profile | `seatbelt_escape_path()` — escape `\` / `"`, fail-closed on control chars + non-UTF-8 (unchanged from the first pass) |

## Codex verdict being answered

> REVISE: "Escaping is fixed, but killing the leader before discovery leaves a race for `setsid` descendants."

Correct, and worse than it reads. The first pass did `kill(-pgid)` and *then* walked
the tree. `kill(-pgid)` is precisely what destroys the links the walk needs: every
intermediate in the group dies, and the kernel reparents its children to `launchd`
as it exits, so a grandchild that had called `setsid(2)` becomes unreachable the
moment its parent goes. The old walk also ran **one `proc_pidinfo` call per pid per
BFS level**, so a wide tree made it slow enough to lose that race reliably.

## What changed this pass (all in `src-tauri/src/tools/exec.rs`)

### 1. `kill_group` — enumerate first, then signal, then re-scan

* `snapshot_processes()` reads the whole table once per round into
  `Vec<ProcRow{pid, ppid, pgid}>`. Expansion is now a pure in-memory function, so a
  round costs one table read instead of one read per BFS level.
* `kill_tree_with(pgid, protect_pid, protect_pgid, snapshot, signal)` holds the loop
  with both syscalls injected; `kill_group` is a thin wrapper over it. That is what
  makes the *ordering* testable without racing processes.
* Order per round: snapshot → expand → `signal(-pgid)` → signal each discovered pid.
  Rounds repeat while a round discovers something new (cap 8), so a child forked in
  the snapshot→delivery window is caught. Seeds accumulate across rounds (a child of
  an intermediate that has since died is still reachable); seeds are **not** signalled
  merely for being seeds — only what the current table still shows is, because a dead
  pid may have been recycled onto an unrelated process.
* Expansion follows two links: `ppid`, and `pgid` **whose group leader is itself
  in-tree**. The second catches a setsid escapee's own children after the escapee is
  gone (its new group is led by itself). Requiring the *leader* to be in-tree is what
  stops a hostile descendant that `setpgid`s into another group in our session from
  widening the blast radius.
* Self-protection: our own pid and our own process group are never returned or
  signalled, and pid ≤ 1 is never signalled.
* Dropped the hardcoded 4096-pid buffer (it silently truncated the table, and a
  truncated table means missed descendants) for probe-then-over-allocate.

### 2. `drain_reader` bounded

`drain_reader(reader, sink, budget)` now pushes into a shared sink and stops at a
deadline; `Drain::finish(grace)` waits at most `DRAIN_GRACE` (2 s) after the child is
gone, then aborts the task and renders what was collected. Previously an unbounded
read meant any process that inherited the write end and outlived the child held
`run_guarded` open for as long as it liked. The per-task budget (`timeout + grace`)
is a second backstop in case the `run_guarded` future is dropped before `finish`.

### 3. Resource ceilings (rlimits)

`ResourceCeilings::for_timeout()` + `apply_ceilings()` install limits via `pre_exec`,
inherited through `sandbox-exec` into the command:

| Limit | Value | Reasoning |
|-------|-------|-----------|
| `RLIMIT_CPU` | `timeout_secs × cores + 30` | A ceiling a well-behaved command can hit is a bug: `timeout` wall-seconds can legitimately buy `timeout × cores` CPU-seconds (a `-j8` build). What it forbids is spending CPU *after* the wall budget is gone — the escapee case. In production (120 s cap) this is 120 × cores + 30. |
| `RLIMIT_FSIZE` | 4 GiB | No legitimate in-workspace artifact reaches it; a `yes > file` runaway stops there instead of at "disk full". |
| `RLIMIT_NOFILE` | 1024 | The conventional POSIX default; this machine's inherited soft limit is 1048576. |

Soft **and** hard are lowered together — soft alone is theatre, the child can raise it
straight back to hard. Only ever tightens (an existing stricter limit is left alone,
neither half is ever raised). A `setrlimit` that does not take fails the spawn
(`ExecError::Io`), so a command never runs with the ceilings silently absent.

### DEFERRED, not skipped: address space (`RLIMIT_AS`)

**macOS will not accept a useful value.** `RLIMIT_AS` is `RLIMIT_RSS` (both 5) there,
and `setrlimit` returns EINVAL for anything small enough to matter. Measured on this
box (direct `libc::setrlimit`, errno read):

| requested | result |
|-----------|--------|
| 2 GiB | `-1`, errno 22 (EINVAL) |
| 8 GiB | `-1`, errno 22 |
| 64 GiB | `-1`, errno 22 |
| 1 TiB | `0` — accepted, and useless as a ceiling |

`RLIMIT_DATA` at 512 MiB is rejected the same way. So there is no memory ceiling to
install here; a real one needs the VM/container backend the module header already
names as the durable target. `RLIMIT_NPROC` is also deliberately **not** set: it is
per-UID on macOS, so it would throttle the whole login session including the harness.

### The adversarial setsid test (replaces the engineered-cooperative one)

`setsid_descendant_that_orphans_itself_is_still_reaped`. The old test arranged a
layout the implementation happened to survive. The new layout tries to escape:

* 40 sibling sleepers in the group — they make a kill-first walk expensive, which is
  exactly the window in which the group dies and its links evaporate;
* a 5-deep chain of intermediates, all in the group, so a post-hoc walk needs five
  sequential levels of links that the kill it just sent is destroying;
* then `setsid()` **and another fork**, so the process that would touch the marker is
  a child of the escapee, not the escapee itself.

It opens with a **positive control**: the same layout is spawned and *not* killed, and
the test asserts the marker DOES appear — otherwise a green result would prove nothing
(e.g. if perl failed to start).

## Behaviour changes beyond the assigned findings — disclosed

1. **Every `shell_exec` now runs under rlimits.** `ulimit -n` drops from this
   machine's 1048576 to 1024; a single file cannot exceed 4 GiB; CPU is capped at
   `120 × cores + 30` s. Smoke-checked that ordinary tools are unaffected at these
   values (`python3`, `node`, `git`, `tar`, `curl`, `cargo` all fine under
   `ulimit -n 1024 -f 4194304 -t 1470`). A command that genuinely needs >1024 fds or
   writes a >4 GiB single file will now fail where it previously would not.
2. **`pre_exec` disables the `posix_spawn` fast path**, so each shell spawn is now a
   real `fork` + `exec` (a fraction of a ms slower). The hook only calls
   `get/setrlimit` and `Error::last_os_error()`, all async-signal-safe and
   allocation-free, which is required when forking from the multi-threaded runtime.
3. **Output can now be truncated where it previously blocked.** If a process holds the
   pipe open past `DRAIN_GRACE`, we return the bytes collected so far instead of
   waiting. Nothing is lost that the old code would have returned *promptly* — only
   bytes that would have arrived after an unbounded wait.
4. **The tree kill is now reliable rather than racy**, so a descendant that
   deliberately daemonised (`setsid`) and would previously have survived a timeout is
   now reaped. That is the intent of the finding, but it *is* a behaviour change for
   any command relying on leaving a background process behind after a **timeout**. The
   normal-exit path is untouched: a command that exits cleanly still leaves its
   background children running, exactly as before.

## Untested / residual risk

* **Non-macOS unix is still a stub.** `snapshot_processes()` returns an empty table
  there, so `kill_tree_with` degrades to the plain group kill it always was on those
  platforms — no regression, no improvement. I did not write a `/proc` implementation
  because I cannot compile or run it here, and shipping an untested tree-walk into the
  one code path that decides what gets SIGKILLed is worse than a documented stub. The
  only real spawner on non-macOS is `UnsupportedSandbox`, which hard-errors anyway.
* **The ppid/pgid walk has a floor.** A process that orphans itself *before* the
  snapshot leaves no link to follow. macOS offers no PID namespace or cgroup, so this
  cannot be closed here; it needs the `Virtualization.framework` /
  `Containerization` backend the module header already names. Documented in
  `kill_group`'s doc comment rather than left as a surprise.
* **PID reuse** between a round's snapshot and its signal is theoretically possible
  (mitigated by only signalling pids the current table still shows). Inherent to any
  pid-based killer.
* Timing assertions (`< 5 s`, `< DRAIN_GRACE + 5 s`) have wide margins, but they are
  timing assertions on a shared machine.
