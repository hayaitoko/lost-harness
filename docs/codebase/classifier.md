# Classifier (privacy egress-guard)

## Purpose

Decides, per outgoing message, whether text is `Private` / `Public` / `Uncertain` so the §7 Privacy Gate (`src-tauri/src/agent/gate.rs`) can route it to a cloud model or force it local. This module is the classifier only — it does not itself block or route anything; `agent::gate::PrivacyGate` consumes its output.

## Files

- `src-tauri/src/classifier/mod.rs` — the `Classifier` trait, `Label`, `Classification`. The shared interface everything else implements/consumes.
- `src-tauri/src/classifier/rules.rs` — **the active production classifier** (`RulesClassifier`). Deterministic, regex-based, span-producing "layer 0". A line-for-line Rust port of a delivered Python file `rules.py` (v3) from the `pf-bundle` (see `/Users/hayai/Desktop/Classifier Model + Install Guide for Claude/`).
- `src-tauri/src/classifier/heuristic.rs` — `HeuristicClassifier`, the original coarse regex/keyword classifier ported from the old Electron app (`src/privacy/classifier.js`). No longer wired into production (`lib.rs`), but still used throughout the test suite as the default `Classifier` impl for gate/hook/dispatch tests, and two of its detector functions are reused directly by `rules.rs` as a stopgap (see Gotchas).
- `src-tauri/src/classifier/engine.rs` — `EnsembleClassifier`, an **unwired stub** for the real trained model (bge-small + distilbert ONNX ensemble). `load()` always returns `Err`; `classify()` always returns `Uncertain` at confidence 0.0. This is "layer 1" and is not called from anywhere in production code today.

## Key types / traits / functions

- `trait Classifier: Send + Sync` — `src-tauri/src/classifier/mod.rs:56-58`. One method: `fn classify(&self, text: &str) -> Classification`. All three implementors (`HeuristicClassifier`, `RulesClassifier`, `EnsembleClassifier`) satisfy this; callers hold `Arc<dyn Classifier>`.
- `enum Label { Private, Public, Uncertain }` — `mod.rs:25-32`. `Uncertain` is spec'd (Risk 4) to be treated identically to `Private` by the gate — "when uncertain, route to private."
- `struct Classification { label: Label, confidence: f32, raw_output: Vec<f32>, spans: Vec<rules::Span> }` — `mod.rs:36-50`. `spans` is populated only by `RulesClassifier`; empty for `HeuristicClassifier` and the `EnsembleClassifier` stub.
- `struct Span { text: String, start_byte, end_byte, start_char, end_char, category: RuleCategory, rule: &'static str }` — `rules.rs:103-111`. Both byte and char offsets are carried (see Gotchas — three different offset spaces exist across Rust/Python/JS).
- `enum RuleCategory { PiiContact, PiiId, Financial, Credential, Proprietary }` — `rules.rs:74-92`. `.as_str()` gives the wire string (`"PII_CONTACT"`, etc.), chosen to match `prompt.py::CATEGORIES` in the delivered bundle.
- `pub fn detect(text: &str) -> Vec<Span>` — `rules.rs:342-438`. The actual regex-detection pass: emails, SSNs, phones (with isolation check), IPv4, API/service tokens (Stripe/GitHub/AWS/Slack/Google), labeled secrets (`password is …`), Luhn-valid card numbers, confidentiality cues, spelled-out digit runs, spaced/obfuscated digit runs (with Unicode-digit folding), leetspeak-obfuscated ID-like tokens, and obfuscated emails (`x [at] y [dot] com`). De-dupes exact `(start,end)` duplicates only; overlapping-but-differently-bounded spans both survive.
- `impl Classifier for RulesClassifier` — `rules.rs:464-496`. Any span found → `Label::Private`, confidence `1.0`, spans populated. No spans, but `heuristic::detect_health_info` or `heuristic::detect_home_address` fires → `Label::Uncertain`, confidence `0.8`, spans empty. Otherwise `Label::Public`, confidence `1.0`.
- `impl Classifier for HeuristicClassifier` — `heuristic.rs:43-128`. Runs 8 detector fns, caps reasons at 5, hard detectors (SSN/card/API-key/financial-account/home-address) → `Private @ 1.0`; soft/conjunctive detectors (email+password, phone+context, health+context) → `Uncertain @ 0.8`; nothing → `Public @ 1.0`. `raw_output` is one `f32` per detector (1.0 if fired), 8 entries always.
- `pub(crate) fn detect_health_info` / `detect_home_address` — `heuristic.rs:235, 269`. Marked `pub(crate)` specifically so `rules.rs` can borrow them as the HEALTH/LOCATION stopgap — read the doc comments on both before touching either function's regex.
- `EnsembleClassifier::load(_model_dir: &Path) -> anyhow::Result<Self>` — `engine.rs:43-47`. Always `Err("trained classifier not available — using heuristic fallback")`. This exact string is documented as "the contract callers check for" but as of this read **no caller actually calls `load()` anywhere** — grep `EnsembleClassifier` outside `engine.rs`/`mod.rs`/doc comments turns up nothing in `lib.rs` or elsewhere. The fallback wiring described in the doc comment does not exist yet.

## Data flow / how it fits

```
lib.rs setup()
  └─ classifier: Arc<dyn Classifier> = Arc::new(RulesClassifier::new())   (lib.rs:73-74)
       └─ shared into PrivacyGate::new(classifier)                        (lib.rs:77, gate.rs:65-69)
            └─ PrivacyGate::check(binding, text, is_cloud_endpoint)       (gate.rs:77-119)
                 - Binding::Auto → classifier.classify(text), then:
                     Label::Public              → GateDecision::Allow
                     Label::Private|Uncertain   → RouteLocal if is_cloud_endpoint else Allow
                 - Binding::Public/Private bypass or hard-block without calling the classifier
       └─ same Arc<dyn Classifier> also feeds the tool-dispatch gating chain (lib.rs comment: "Shared between the message-level §7 gate and the tool gating chain so both classify identically")
```

`PrivacyGate::check` only reads `classification.label`; it never reads `confidence` or `spans`. `spans` currently has **no consumer anywhere in the codebase** (checked: no `.spans` access, no `rules::Span`/`classifier::Span` reference outside `classifier/`) — it exists to feed the PLAN §11 "annotated review view" redaction UI, which is not built yet. `confidence` is likewise not consumed downstream beyond debug/logging use.

Audit logging: `agent::loop_mod::AgentLoop` calls `PrivacyGate::check`, then writes a row to the `trm_logs` SQLite table (`storage/schema.rs:218`, `storage/profile.rs:769` `insert_trm_log`) — hash of the text only, never the text itself, per spec §3. That table name and the surrounding function/struct names (`TrmLog`, `log_trm_decision`, `insert_trm_log`) are a deliberate naming holdover from before the `trm/` → `classifier/` rename (see Gotchas).

## Invariants (do NOT break)

- **`Uncertain` must never be treated as `Public`.** Enforced today in exactly one place, `gate.rs:109` (`Label::Private | Label::Uncertain => …RouteLocal`). If you add a new call site that pattern-matches on `Label`, mirror this — do not add a bare `Label::Public => Allow` default that silently lets `Uncertain` fall through.
- **`RulesClassifier::classify` never returns `Label::Uncertain` from `detect()` hits** — any span found is unconditionally `Private @ 1.0` (rules.rs doc comment, lines 5-9: "this layer never returns `Label::Uncertain`; either it finds a span (Private) or it doesn't"). Only the HEALTH/LOCATION stopgap path returns `Uncertain`.
- **Layer 0 (`rules.rs`) is tuned for recall, not precision** — explicitly the opposite bias from `heuristic.rs`'s original design goal (module doc comment, rules.rs:6-12). A false positive just routes a message local (safe); a false negative is a leak. Do not "fix" a rules.rs false-positive by loosening a pattern without re-reading that tradeoff.
- **The regex crate (`regex`, RE2-derived) has no backtracking/lookaround**, which is also why these patterns can't ReDoS — a real property future edits should preserve. Don't introduce `fancy-regex` or similar to "port a lookaround more faithfully" without weighing that away.
- **Byte offsets vs char offsets**: `Span` carries both because Rust string-slicing needs byte offsets but the original Python (`rules.py`) used codepoint offsets. Neither matches JS/TS `String.slice()` (UTF-16 code units) — a future redaction UI consuming `Span` over IPC needs its own UTF-16 conversion; don't assume `start_char`/`end_char` are safe to feed straight into a frontend string slice.
- **`trm_logs` logs a hash of the text, never the text itself** (spec §3) — this lives in `agent/loop_mod.rs`/`storage/profile.rs`, not in `classifier/`, but any change that threads raw text further downstream from `Classification` should preserve this.

## Gotchas / watch-items

- **Doc-comment staleness in `mod.rs`**: the module doc (`mod.rs:4-10`) says "`HeuristicClassifier` is the conservative regex/keyword fallback that ships today" — this is now stale. As of `lib.rs:73-74`, **`RulesClassifier` is what ships**; `HeuristicClassifier` only appears in test code (`tools/dispatch.rs:347/397`, `agent/gate_tests.rs`, `agent/loop_tests.rs`, `hooks/privacy_filter.rs`, `hooks/tests.rs`, `ipc/contract_tests.rs`). If you change production wiring, update `mod.rs`'s doc comment too — it's actively misleading right now.
- **`EnsembleClassifier` fallback contract is aspirational, not implemented.** The doc comment on `EnsembleClassifier::load` describes callers checking the error string and falling back to `HeuristicClassifier`, but no such call site exists. When wiring the real ONNX model, you'll be writing that fallback logic from scratch in `lib.rs`, not just filling in `load()`'s body — and per the current PLAN, it should fall back to `RulesClassifier`-composed-with-the-ensemble, not the bare `HeuristicClassifier` the comment describes (the comment predates the rules.rs port).
- **No `ort` (ONNX Runtime) dependency in `src-tauri/Cargo.toml` yet.** The classifier bundle at `~/Desktop/Classifier Model + Install Guide for Claude/` ships PyTorch weights + an `export_onnx.py`, not `.onnx` files — per HANDOFF.md, ensemble integration is blocked on running that export step, separately from any Rust wiring work.
- **`trm` → `classifier` naming split.** The module was renamed 2026-07-09 (git-less repo, so no commit hash — see HANDOFF.md). The module itself, its files, and the `Classifier`/`Classification` types are all renamed. But: the `trm_logs` SQLite table (`storage/schema.rs`), `TrmLog` struct, `insert_trm_log`/`list_trm_logs`/`purge_trm_logs_older_than` (`storage/profile.rs`), `log_trm_decision`/`log_trm` in `agent/loop_mod.rs` and `agent/loop_tests.rs`, and scattered `trm` mentions in `hooks/mod.rs` and `models/client.rs` doc comments were **deliberately left as "trm"** (renaming a persisted table needs a migration, per HANDOFF.md line 115). If you're grepping for "everything related to the classifier," you must grep both `classifier` and `trm` — they're the same subsystem under two names in different layers.
- **`§7`/`PrivacyGate` naming is also a known-pending rename**, adjacent to but not part of this subsystem: HANDOFF.md notes the docs now say "privacy filter" while the code still says `§7`/`PrivacyGate`/`GateDecision`, and that rename is explicitly deferred to "the classifier-integration round" that wires the real ONNX model — i.e., whoever wires `EnsembleClassifier` for real will likely also be touching `gate.rs` naming.
- **`heuristic.rs`'s two `pub(crate)` functions are a load-bearing dependency, not dead code.** `detect_health_info` and `detect_home_address` look orphaned (nothing in `heuristic.rs` itself needs them to be `pub(crate)`) until you see `rules.rs:478-486` calling them directly as the HEALTH/LOCATION stopgap. Don't delete or privatize them, and don't change their regexes without checking `rules.rs`'s doc comment (lines 14-19) for the categories they're standing in for.
- **`RulesClassifier` is a strict superset of `HeuristicClassifier`'s hard detectors** (per `rules.rs:450-454` doc comment) except HEALTH/LOCATION, which route through the borrowed heuristic functions above. If a message is flagged `Private` by `HeuristicClassifier` in a test but you're validating against `RulesClassifier`, expect the label to still be `Private` (same or more spans) — but `raw_output` shape differs completely (`HeuristicClassifier` always emits 8 floats; `RulesClassifier` emits `vec![spans.len() as f32]` or an empty vec — don't write code that assumes a fixed-length `raw_output`).
- **Unicode digit folding covers ~18 of ~66 Unicode `Nd` blocks** (`rules.rs:147-170`, `DIGIT_BLOCKS`) — a deliberate scope cut for "realistic obfuscation surface for a personal single-user tool," not exhaustive. If a script needed for a real user is missing (e.g. some digit-run in an underrepresented script slips through as `Public`), extend `DIGIT_BLOCKS`, not `unicode_digit_value`'s logic.
- **`is_isolated_run`'s digit check is ASCII-only** even though Python's `\d` lookbehind is Unicode-aware (rules.rs:317-333) — a narrow, documented fidelity gap versus the ported Python original.
- **No `entropy`-based secret detector exists**, despite the module doc explicitly calling this out (rules.rs:54-59) — don't assume high-entropy strings alone (e.g. a bare 32-char random token with no "password="/"token="-style label) get caught; only `_LABELED_SECRET`-style (explicitly labeled) and character-class-shaped (`idish`) detectors exist.

## How to extend

- **New deterministic detector (structured PII / secrets)**: add a pattern to `patterns()` in `rules.rs` (or extend `CONFIDENTIALITY_CUES` for a new confidentiality phrase), wire it into `detect()`, choose/extend `RuleCategory`, and add both a `rules::tests` unit test and — if it changes classification outcomes — a `RulesClassifier` trait-level test near the bottom of `rules.rs`. Keep to the "deterministic, zero-lookaround, RE2-compatible" constraints described in the module doc comment.
- **New semantic category (needs judgment, not regex)** — e.g. improving HEALTH/LOCATION coverage, or adding PII_NAME/PII_ORG/PERSONAL_CONTEXT: this is explicitly out of scope for `rules.rs` (see its doc comment, lines 14-19) and is meant to land in the ONNX ensemble (`engine.rs`) once wired. Don't grow `rules.rs` regexes to chase these — that's the documented anti-pattern this codebase is trying to avoid.
- **Wiring the real ONNX ensemble**: implement `EnsembleClassifier::load` to load the two `ort::Session`s + tokenizers (fields are stubbed as comments at `engine.rs:29-32`), and per `engine.rs:50-60`'s doc comment, `classify()` should run `rules::detect(text)` FIRST as an unconditional pre-filter (short-circuit to `Private @ 1.0` with spans on any hit) before paying for transformer inference; only run the two encoders when layer 0 finds nothing, covering PII_NAME/HEALTH/LOCATION/PII_ORG/PERSONAL_CONTEXT via sliding 128-token windows + max private-probability fusion. Then flip `lib.rs:73-74` to construct `EnsembleClassifier` (with a fallback to `RulesClassifier` on load failure — that fallback logic doesn't exist yet, you're writing it). Requires adding an `ort` dependency to `Cargo.toml` and running `export_onnx.py` from the delivered bundle first.
- **Changing gate behavior around `Uncertain` or `spans`**: that logic lives in `agent/gate.rs`, not this module — `Classification` already carries what's needed (`confidence`, `spans`); the gate simply doesn't consume them yet. Building the PLAN §11 "annotated review view" / redaction means adding a consumer for `Classification::spans`, likely threaded through `agent/loop_mod.rs` → IPC → a new Svelte sidebar component — none of that plumbing exists today.
