## 1. The headline test assertion was INERT — rewritten so it books real money

**The refutation was correct.** The old test drove `StallStreamer`, whose `stream()`
returns `std::future::pending()`, so no round ever completed, `record_usage` never fired,
and `summary.known_cost_usd` stayed at the seeded $0.50 no matter what the fix did.
`assert!(known_cost_usd <= 2.0)` could not fail.

Replaced with a `BillingStreamer` (`work_runner.rs`, test module) that returns a
**complete** canned SSE stream — a content delta, a `usage` chunk
(`completion_tokens: 60_000`), and `[DONE]`. Against `gpt-4o` ($10.00/Mtok out in
`models::pricing`) that is **exactly $0.60 of real, booked, KNOWN cost per round**. The
model id in the test payload had to change from `gpt-x` to `gpt-4o` — `gpt-x` is unpriced,
so it books `cost_usd = NULL` and the governor's fail-closed "unknown" branch (not the
reservation) would have been what halted the losers. The test now asserts
`unknown_cost_calls == 0` to keep that honest.

The test is also made **deterministic**, which the old one was not: `BillingStreamer` is
gated on a `tokio::sync::Semaphore(0)`. Every helper parks inside `stream()` until the
test opens the gate, so all four are guaranteed to have completed their budget check while
$0 of their spend is on disk. Without that, the scheduler could run helper A to completion
(including `budget_reconcile`) before helper B even checks — which would "pass" while
testing nothing about concurrency.

### Language: what this is, stated accurately

The doc comment on `budget_check_and_reserve` no longer says "hard financial control". It
now says what is true: an **atomic pre-dispatch reservation** (bounds how many helpers
START) plus a **per-round unattended re-check** (bounds what one running helper SPENDS).
Together the residual overrun is **one round's cost**, not a `HELPER_DEADLINE` window.
Because the reservation serializes capped profiles to one helper at a time, only one
helper can be mid-flight, so the overrun is one round total — **not** one round per
helper. It is still not zero, and one round's cost is itself unbounded in size (a huge
context on an expensive model is one round). Calling it a "hard cap to the dollar" would
be false; calling it a bounded ceiling is accurate.

## 4. The `profile` shadow (permanent reservation leak on panic) — fixed

`run_one_item` used to rebind `profile` from the payload at line 345, so
`budget_check_and_reserve` / `budget_reconcile` keyed off the PAYLOAD profile while
`supervise_one_item`'s panic-path reconcile keyed off the QUEUE profile. A payload naming a
different profile therefore leaked a permanent reservation on a panic and would wedge that
profile forever.

The payload value is now `payload_profile` and does not shadow. Both reservation calls,
the `db` handle they read the ledger from, and the panic-path reconcile are all keyed off
the **queue** `profile` — one string, three call sites. A mismatch is logged
(`tracing::warn!`) rather than silently reinterpreted.

`run_subagent` still receives `payload_profile`, so the run's behavior is unchanged.
Production can't diverge: `delegate` stamps `ctx.profile` into the payload AND inserts the
row into that same profile's DB. See residual #4 below.

## NEEDS-LUKAS (residuals — none of these are closed)

**1. (KEPT FROM LAST ROUND — still true, still your call.) The reservation is the WHOLE
remaining budget, so background work is serialized for any capped profile.**
`work_runner.rs:91-94`: the first helper to take the lock reserves all remaining headroom,
not an estimate of what it will spend. Consequences, precisely:
- A profile with ANY cap set runs exactly **one** background helper at a time.
  `MAX_CONCURRENT_HELPERS` is effectively 1 for that profile. Uncapped profiles are
  unaffected (no reservation is recorded).
- Losers are not deferred or re-queued — they are terminally **Failed** with a `budget:`
  error, which reads to the user as "over budget" rather than "busy, try later". A burst of
  4 `delegate` calls on a capped profile yields 1 run and 3 budget failures. The new test
  asserts exactly this (`halted == 3`), so it is now pinned behavior, not an accident.
- `budget_reconcile` does `reservations.remove(profile)` — it clears the profile's whole
  entry rather than subtracting this task's share. Correct today (only one reservation can
  be outstanding per profile), wrong the moment the model changes to per-task estimates.
The alternatives (reserve a per-item estimate; make losers wait/re-queue instead of fail)
are product decisions, not bugs. I did not make them.

**2. The overrun is bounded, not zero.** One round can still complete after the cap is
crossed, and a single round's cost is unbounded in principle. A true to-the-dollar ceiling
needs pre-call cost estimation from the outgoing token count — a real feature, not a fix.

**3. ATTENDED turns are still only warned, never blocked.** That is C1's stated design
(`hooks/budget.rs` module docs: the human in front of the app is never hard-blocked
mid-thought). So a person sitting at the app can drive the profile past its cap. Making the
cap bind humans too is a deliberate product change and I did not make it.

**4. Payload profile vs. queue profile.** If they ever diverge, the pre-dispatch
reservation is keyed to the QUEUE profile while the run's spend books to the PAYLOAD
profile's ledger. Production cannot produce that divergence (`delegate` writes both from
`ctx.profile`), it is now logged if it happens, and the new mid-run re-check reads the
profile the spend actually lands in — so the cap is still enforced against the right
ledger. But the two halves would be watching different ledgers. The cleanest real fix is to
reject a mismatched payload outright; I did not, because failing work items on a new
condition is a behavior change beyond this packet.
