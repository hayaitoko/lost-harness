# P02 — Egress trust: remove suffix-based auto-trust (H-05)

**Status:** Done

**Branch:** `fix/p02-egress-trust`

**Findings:** H-05 (HIGH)

**Updated:** 2026-07-28T12:56:00Z

## Files changed

- `src-tauri/src/agent/egress.rs` — removed `.local`/`.lan`/`.internal`/`.ts.net` suffix auto-trust from `is_private_endpoint()`; updated doc comments; added five new regression tests

## Summary

The `is_private_endpoint()` function unconditionally treated any hostname ending in `.local`, `.lan`, `.internal`, or `.ts.net` as a private/local endpoint with zero DNS resolution or authentication. An attacker on the local network could poison mDNS/DNS to redirect those names to a remote machine, silently routing private prompts off-box.

**Fix:** `is_private_endpoint()` now treats only loopback literals (`localhost`, `[::1]`, `127.0.0.0/8`) and explicit private IP range literals (RFC 1918, Tailscale CGNAT) as private — these are address literals verifiable from URL parsing alone, with no resolution dependency.

The companion function `is_private_endpoint_trusted_by_name()` is unchanged: it identifies suffix-based names for UI enrollment flows, but these names no longer grant network access automatically.

## Follow-ups

1. **Caller-side integration:** `loop_mod.rs` and `fetch.rs` call `is_private_endpoint` to classify providers. After this fix, a `.ts.net` or `.local` provider URL will no longer be flagged private, so the routing/gate logic may now block or cloud-route these. The downstream fix packet should add an explicit trust-enrollment step that calls both `is_private_endpoint` (for IP/literal) AND optionally consults a trust table for named private services, using `is_private_endpoint_trusted_by_name` as the UI signal.
2. **`gate_tests.rs`** — lines 229–232 of that file assert that `.lan`/`.local`/`.internal`/`.ts.net` ARE private. These tests will fail on a full `cargo test --lib` until updated to match the new behavior. A follow-up packet should update those tests.
