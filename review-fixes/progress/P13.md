# P13 — Pack Import Validation & Atomicity

**Status:** Complete

**Branch:** `fix/p13-pack-limits`

**Finding:** M-13 (MEDIUM)

## Findings

`packs/mod.rs` (lines 105–125, 125–193) had the following issues:

1. **No byte cap** — `parse_pack` did not check the incoming JSON payload size against the pre-agreed `PACK_IMPORT_MAX_BYTES = 1_000_000` limit (enforced at IPC by P05, but not at the domain layer).
2. **Unbounded item counts** — No limit on the number of skills, agent types, or cron jobs a pack could carry.
3. **Unbounded string/list lengths** — No limits on field lengths (`name`, `description`, `content`, `system_prompt`, `schedule`, `seat`, `version`) or list sizes (`capabilities_required`, `tools_allowlist`, `trigger_examples`).
4. **No pre-mutation validation** — `install_pack` accepted whatever `parse_pack` returned and proceeded directly to SQL inserts.
5. **No transaction** — Skills and agent types were inserted via `insert_skill`/`insert_agent_type` sequentially with no SQLite transaction, so a mid-install failure left a partial commit.

## Changes Made

**File:** `src-tauri/src/packs/mod.rs`

### Added validation constants

| Constant | Value | Applies to |
|---|---|---|
| `PACK_IMPORT_MAX_BYTES` | 1,000,000 | Total JSON payload length |
| `PACK_MAX_SKILLS` | 50 | `pack.skills` count |
| `PACK_MAX_AGENT_TYPES` | 25 | `pack.agent_types` count |
| `PACK_MAX_CRON_JOBS` | 25 | `pack.cron_jobs` count |
| `PACK_MAX_NAME_LEN` | 128 | All `name` fields |
| `PACK_MAX_DESC_LEN` | 2,048 | `description` fields |
| `PACK_MAX_VERSION_LEN` | 32 | `version` field |
| `PACK_MAX_CONTENT_LEN` | 262,144 | Skill `content` / cron `prompt` |
| `PACK_MAX_SCHEDULE_LEN` | 256 | Cron `schedule` |
| `PACK_MAX_SYSTEM_PROMPT_LEN` | 262,144 | Agent-type `system_prompt` |
| `PACK_MAX_SEAT_LEN` | 64 | Agent-type `seat` |
| `PACK_MAX_LIST_ITEMS` | 100 | `capabilities_required`, `tools_allowlist`, `trigger_examples` |
| `PACK_MAX_LIST_ITEM_LEN` | 256 | Each individual string inside a list field |

### Added `validate_pack()` function

Validates all structural limits: item counts, per-field string lengths, list sizes, empty names, and empty schedules. Returns `Err(anyhow::Error)` with a descriptive message on the first violation.

### Updated `parse_pack()`

- Enforces `PACK_IMPORT_MAX_BYTES` byte cap on the raw JSON before parsing.
- Calls `validate_pack(&pack)` after format/name validation.
- All validation happens before any `Pack` is returned to the caller.

### Updated `install_pack()`

- **Defense-in-depth:** calls `validate_pack(pack)` at the start.
- **Early profile DB open:** opens the profile DB (for cron jobs) *before* the global transaction, so a missing/invalid profile is caught before any mutation.
- **Atomic global transaction:** skills and agent types are inserted via a single SQLite `BEGIN`/`COMMIT` transaction on `global.raw()` (using `rusqlite::Transaction`). A mid-insert failure causes a full rollback.
- **Best-effort cron jobs:** cron jobs are inserted after the global transaction commits, matching the existing design doc (two-DB architecture prevents cross-DB transactions).

### Updated imports

Removed unused `Skill` and `AgentType` struct imports (no longer constructed directly; raw SQL uses the `SkillApproval::Pending`/`AgentTypeApproval::Pending` enum variants).

## Deferred / known limits

- **Cron jobs are still not transactional with the global segment.** This is
  inherent: skills + agent types live in `global.db`, cron jobs in the profile
  DB, and SQLite cannot span the two in one transaction. The mitigation landed
  here is (a) open the profile DB *before* the global transaction so a
  missing/invalid profile aborts before any mutation, and (b) document the
  window in the module header and on `install_pack`. A failure that happens
  *after* the global commit but *during* cron insertion still leaves the
  (inert, Pending) skills/agent types in place. Everything a pack installs is
  inert by design, so the residue is reviewable, not armed.
- The limit values (50 skills / 25 agent types / 25 cron jobs / 256KB content)
  are chosen, not derived from a measured workload.
