## Codex's rejection, and what was actually true

Codex REJECTed the first pass: "Frontend calls a nonexistent IPC, swallows the
error, and falsely reports the key as stored." Re-checked each clause against
the branch as it stood at fc826d9:

- "nonexistent IPC" — TRUE, and NOT fixable here. `set_provider_api_key` is
  implemented in Rust but was never registered in `generate_handler![]`.
  **P05 owns that registration.** Until P05 lands, every rotation/add in the
  installed app rejects at the IPC boundary. Post-fc826d9 that failure is at
  least honest (the provider is not reported as configured) instead of silent.
- "swallows the error" — already fixed by fc826d9, and I re-verified it by
  mutation, not by reading: re-wrapping the `invoke` in a swallowing
  try/catch makes 3 of the new tests fail.
- "falsely reports the key as stored" — fixed for the IPC-failure path by
  fc826d9, but **still true on a second path**, which this packet fixes (below).

`apiKey` is genuinely gone from the `Provider` interface (8002e72); no
frontend file outside the store references it. `Settings.svelte` keeps the
plaintext only in its own form state and nulls the form on success.

## What changed in this packet

### 1. Remaining false-report path (a0beb5a)

`setProviderApiKey` returned `void`, and both callers set `hasApiKey = true`
on any resolve. In browser fallback (`!api.isTauriRuntime()`) it returns
early **without storing anything** — there is no keychain in a plain Vite dev
session, and `browserAddProvider` explicitly ignores its `_apiKey` argument.
So a dev-mode add or rotate still reported the key as stored, and persisted
`hasApiKey: true` to `lh.providers.v1`. Same lie as the swallowed-IPC bug,
different branch.

It now returns `boolean` — `true` only after the `set_provider_api_key`
invoke resolves — and both the new-provider and rotate paths derive
`hasApiKey` from that value rather than from a literal `true`.

### 2. Tests (6106f44)

12 new tests, 36 total in the file.

- **Legacy-localStorage scrub** — `vi.resetModules()` + re-import so the
  module's load-time migration runs against seeded storage. A pre-fix payload
  containing a plaintext `apiKey` is rewritten with the secret and the field
  both gone (asserted on the raw string and across *all* localStorage keys),
  `hasApiKey` preserved per entry, and no `apiKey` property on the in-memory
  model. An unparseable legacy blob is cleared to `"[]"` (fail closed).
- **Tauri-runtime block** — stubs `window.__TAURI_INTERNALS__` and mocks
  `invoke` from `@tauri-apps/api/core` (the single module both `tauri.ts` and
  the store import), so the fake backend can resolve or reject
  `set_provider_api_key` per test. Covers add success, add failure with
  rollback, add with no key, creation-IPC failure, rotate success, rotate
  failure on a keyless provider, rotate failure on a keyed provider, and
  blank-key edit. Asserts on all of: the IPC command + args, `hasApiKey`,
  what was persisted, and the absence of the plaintext anywhere in
  localStorage.
- **Rollback** — the add-failure test asserts the rejection propagates,
  `remove_provider` is called with the new id, and store + localStorage are
  left empty so nothing can look configured.

## Known-not-closed / follow-ups

1. **Blocked on P05.** In the installed app `set_provider_api_key` is still
   unregistered, so provider keys remain non-functional until P05 lands.
   P04's tests mock the IPC and therefore pass regardless — they prove the
   store's contract, **not** that the feature works end to end. An
   integration check after both merge is still required.
2. **No UI surface for `hasApiKey`.** `Settings.svelte` has the key input but
   never renders key state, so today the store's honesty is invisible to the
   user. Worth a small "Key stored / No key" indicator; deliberately not done
   here (out of declared scope, and Settings.svelte is a hot file).
3. **`hydrateProviders` still catches and logs.** Left as-is: it is a read
   path, a failed hydrate leaves the last-known-good cache untouched, and it
   never fabricates `hasApiKey: true`. Not part of H-01.
4. **Stale-flag edge case.** In the Tauri runtime the hydrate merge preserves
   the local `hasApiKey` because the backend's `ProviderInfo` carries no
   `has_api_key`. If a keychain entry is deleted out of band, the flag goes
   stale. The real fix is for the backend to report `has_api_key`; the store
   already reads `(p as any).has_api_key ?? false` so it will pick that up
   with no frontend change.
