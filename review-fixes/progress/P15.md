# P15 — M-09: background budget hard caps

Branch: `fix/p15-budget-caps`
Scope: `src-tauri/src/agent/work_runner.rs`, `review-fixes/progress/P15.md`

## Finding

M-09: the background work runner checked the budget non-atomically. Several helpers
could each read the same on-disk ledger, each conclude they were under the cap, and
then all spend — collectively blowing past the configured cap. The check was advisory,
not a hard ceiling.

## What changed

The work was already implemented (uncommitted in the worktree). I reviewed it, formatted
it, tested it, and landed it as-is. No redesign.

- New `BudgetLock = Arc<tokio::sync::Mutex<HashMap<String, f64>>>` — per-profile USD
  *reserved but not yet booked*. Created once in `spawn_work_runner` and cloned into every
  spawned helper task, so it is shared process-wide.
- New `budget_check_and_reserve(...) -> bool` (work_runner.rs:63): takes the lock, reads
  `budget_cap()` + `usage_summary_since(month_start)`, adds the outstanding reservation to
  the observed spend, and runs `budget::evaluate` against that *effective* summary. On
  `Halt` it finishes the item `Failed` with a `budget: …` error and returns `false`
  (caller must `return`). On pass it records a reservation and returns `true`.
  Check-and-reserve happens under one lock hold, so it is atomic.
- New `budget_reconcile(...)` (work_runner.rs:114): drops the profile's reservation after
  the run, so the next check sees real on-disk spend (per-round costs are already booked
  by `process_message → record_usage` during the run).
- Wired into both unattended paths:
  - `WorkKind::Cron` in `run_one_item` — checks/reserves before `run_cron_item`, records
    `record_cron_run(job_id, "failed")` on a budget halt, reconciles after.
    (The old inline budget check inside `run_cron_item` was removed; the caller now owns it.)
  - the AgentDispatch helper path in `run_one_item` — replaces the old advisory
    `budget_verdict_for(&db, false)` check; reconciles after the `timeout(...)` resolves.
- `supervise_one_item` also reconciles on the panic path, so a panicking helper cannot
  leak a reservation and permanently wedge the profile.
- The unavailable/error branch still fails closed (item `Failed`, "budget check
  unavailable — halting to fail closed").
- New test: `budget_lock_prevents_four_concurrent_helpers_from_exceeding_the_cap` —
  $2.00 cap, $0.50 already spent, 4 helpers claimed and spawned concurrently against the
  shared lock; asserts total known spend stays ≤ cap and that ≥2 of the 4 were
  budget-halted.

## Needs human decision (Lukas)

**The reservation is the entire remaining budget, so background work is serialized for any
budget-capped profile.**

At `src-tauri/src/agent/work_runner.rs:91–94`:

```rust
// Reserve the remaining budget so concurrent helpers see a reduced cap.
if let Some(cap_val) = cap {
    let remaining = (cap_val - effective.known_cost_usd).max(0.0);
    reservations.insert(profile.to_string(), reserved + remaining);
}
```

The first helper to acquire the lock reserves *all* remaining headroom, not an estimate of
what it will actually spend. Every other helper for that profile then computes
`effective.known_cost_usd == cap`, gets `BudgetVerdict::Halt`, and is finished `Failed`
with a `budget: …` error.

Consequences, precisely:

- A profile with **any** budget cap set can run exactly **one** background helper at a
  time. `MAX_CONCURRENT_HELPERS` is effectively 1 per capped profile — background work is
  serialized, not concurrent. (Profiles with `cap == None` are unaffected: no reservation
  is recorded, so they still run concurrently.)
- Losing helpers are not deferred or re-queued — they are terminally **failed** with a
  budget error, which surfaces to the user as "budget" rather than "busy". A burst of 4
  `delegate` calls on a capped profile yields 1 run and 3 budget failures.
- `budget_reconcile` does `reservations.remove(profile)` — it clears the whole profile
  entry rather than subtracting this task's share. That is consistent today (only one
  reservation can ever be outstanding per profile), but it is not correct if the
  reservation model is ever changed to per-task estimates.

This is a genuine hard financial ceiling and it does what M-09 asked for; the cost is
throughput and confusing failure text. The alternatives (reserve a per-item *estimate*
instead of the full remainder; or make losers wait/re-queue instead of fail) are design
choices, not bugs, so I left it alone. Your call.
