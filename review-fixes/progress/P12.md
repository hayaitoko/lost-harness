## What was implemented

`download_to_partial` gained an `expected_size: u64` parameter (the catalog's declared byte
count; `0` = unknown, ceilings inapplicable) and its two decision points were split into
unit-testable units: `classify_partial` / `plan_resume` (pure) and `stream_to_file`
(generic over the byte stream).

1. **Exact 206 validation — start, end AND total.** `parse_content_range` now returns
   `{start, end, total}` and `plan_resume` checks all three: `start` must equal the bytes
   already on disk, `end` must not reach past the declared size, and a stated `total` must
   equal `expected_size`. The total is no longer parsed-then-discarded. `Content-Length`, if
   present, is cross-checked against `end - start + 1`. Malformed ranges are hard errors, not
   "close enough". `total: *` is tolerated (HF always states it, and `end` plus the final
   exact-length check still pin the size) — documented in the fn doc.
2. **200 → truncate and restart.** `plan_resume` maps `200` to `ResumeAction::Restart` and
   `open_partial(path, 0)` opens with `.truncate(true)`. `open_partial` also asserts the file
   is exactly the length the plan assumed before writing.
3. **Over-declared sizes refused before any bytes.** Both the 206 `end >= expected_size` check
   and the 200 `Content-Length > expected_size` check run in `plan_resume`, which is called
   **before** `open_partial`, so nothing is opened or written on a bad response.
4. **EOF is proved.** The read loop no longer breaks at `expected_size`; it keeps polling and
   errors on any further non-empty chunk (refusing it **before** the write, so the excess never
   reaches the file). Bounded by a short `eof_grace` — see the caveat below.
5. **Total-download budget** (`DownloadLimits::total`, default 12 h) alongside the existing
   30 s idle timeout. A slow-drip server that emits a byte just inside the idle window can no
   longer hold the transfer open forever.
6. **Oversized pre-existing partial — decided, implemented, documented.** `classify_partial`
   returns `Discard`: a partial longer than the declared total is not a truncated prefix of
   the wanted file, it is *different bytes*, so no resume can make it hash correctly.
   Truncating it back to `expected_size` would be worse (it hands a plausible-looking file to
   the hasher) and refusing outright would wedge the download permanently. So it is thrown
   away (`tracing::warn!`) and the download restarts. Rationale is in the `classify_partial`
   doc comment.
   Two neighbouring cases fell out of the same classifier: `on_disk == expected_size` →
   `Complete`, short-circuits with no request at all (previously that sent `bytes=N-` and ate a
   416); `expected_size == 0` → unchanged legacy behaviour.

## Behaviour changes beyond the six assigned items — disclosed

- **A short transfer now returns `Err`** ("incomplete download: N of M byte(s)") where it
  previously returned `Ok` and let `verify_and_install` hash-fail and **delete** the partial.
  Net effect is better (progress survives, the next attempt resumes), but the error string the
  `download_model` IPC command surfaces changes. Grepped `src/` — the frontend does not match
  on download error text, it only displays it.
- **A non-200/206 status** now errors with our own message instead of reqwest's
  `error_for_status`. Same fail-closed outcome, different text.
- **`already == expected_size` no longer makes a request.** Previously that case always failed
  (416); now it proceeds to hash verification.
- **A transfer running longer than 12 h now fails** (resumably). Chosen because a 40 GB file at
  1 MB/s is ~11 h; the partial is kept so a slower line just needs a second attempt.

## Not proven / caveats

- **`eof_grace` is a bounded EOF probe, not an unconditional one.** Once every declared byte
  has landed, we wait up to 5 s for the end-of-body marker; if it never comes we accept the
  transfer rather than failing a complete download. So a server that delivers *exactly* the
  declared size and then goes silent forever is accepted without a proven EOF. Over-sending is
  still caught, because the extra chunk arrives inside the grace window. This is a deliberate
  trade (failing there would turn complete downloads into errors); it is documented on the
  `DownloadLimits::eof_grace` field.
- **The real reqwest wire path is not exercised.** There is no HTTP mock crate in
  `[dev-dependencies]`, and `host_allowed` pins egress to `huggingface.co`/`hf.co`, so a
  localhost mock server is impossible without weakening the allowlist — which I would not do
  for a test. `plan_resume`, `open_partial` and `stream_to_file` are unit-tested directly; only
  their *wiring* inside `download_to_partial` is untested, apart from the allowlist-refusal and
  `Complete` short-circuit tests.
- **The live HF E2E test was NOT run.** `models::runner::tests::live_e2e_search_download_spawn_chat_teardown`
  self-skips unless `LHP_E2E_LIVE=1` (it downloads ~0.6 GB). It compiles with the new argument
  and is counted in the 749, but its download path was not executed on real bytes.
