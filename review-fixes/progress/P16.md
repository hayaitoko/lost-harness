# P16 — OAuth rotation & Gmail efficiency (M-06, M-07)

Branch: `fix/p16-oauth-gmail` (base `eb17b94`)

## What was already in the worktree (uncommitted, kept)

The packet arrived with partial work sitting uncommitted. All of it was kept:

- `KeychainTokenProvider` single-flight refresh — a `tokio::sync::Mutex` held
  across the network call + keychain write, with a parking_lot fast path
  before it and a double-check after it.
- The rotated-refresh-token write is now durable: `let _ = self.secrets.set(..)`
  became a real `?` with a `failed to persist rotated refresh token …` error.
- `email_search` metadata projection: new `GmailApi::get_message_metadata`
  hitting `format=metadata&metadataHeaders=From|Subject|Date` instead of
  `format=full`, so a search page no longer downloads every body.
- Bounded-concurrent preview fetches (`Semaphore(3)`) instead of a serial loop.
- `GmailClient` takes `Arc<dyn TokenProvider>`; `EmailToolDeps` caches one
  `KeychainTokenProvider` per profile so the access-token cache survives
  across tool dispatches.

## What I changed

### (a) Response bodies are no longer read unbounded — `email/gmail.rs`

`ReqwestGmailHttp::request` ended in `resp.text().await.unwrap_or_default()`,
which buffers whatever the server sends. Replaced with `read_body_capped`:

- refuses up front when the declared `Content-Length` exceeds the cap,
- refuses mid-stream on the running total while pulling `resp.chunk()`, which
  is the only gate that catches a chunked or mis-declared body,
- decodes lossily (untrusted bytes must not panic the fetch layer).

Cap is `MAX_RESPONSE_BYTES = 32 MiB`. Rationale in the code: Gmail's own
message-size limit is 25 MB and `messages.get?format=full` returns oversized
attachment parts as an `attachmentId` rather than inline data, so 32 MiB is
above anything legitimate. **This number is a judgement call — see "needs a
human decision" below.** The cap is a field on `ReqwestGmailHttp` (set by
`new()`, overridable via the private `with_response_cap`) so the test can
drive the refusal with a 4 KiB body instead of allocating tens of megabytes.

### (b) Failed search rows carry their real message id — `tools/email.rs`

The error row was hard-coded to `"id": "?"`. The fan-out is now a standalone
`fetch_previews(client, ids)` that returns `(id, Result<EmailMessage, String>)`
per input id, in input order, so the error row names the message that failed.
The join-error path (a panicked fetch task) also keeps its real id, and it no
longer `.expect()`s — a panicked preview task degrades to one bad row instead
of taking the whole search down.

### Two pre-existing compile errors in the handed-over work

The uncommitted state did **not** build as tests. Both were caused by the
`Box` → `Arc` token-provider change and both are fixed inside declared scope:

1. `EmailToolDeps::google_client` passed `Arc<KeychainTokenProvider>` to
   `GoogleClient::new(Box<dyn TokenProvider>)`. Rather than edit
   `email/google.rs` (out of scope), I added a small `SharedTokenProvider`
   newtype in `tools/email.rs` that boxes the shared `Arc`. Calendar/Tasks
   therefore reuse Gmail's token cache and single-flight refresh instead of
   minting a private cold-cache provider.
2. `lib.rs` built `EmailToolDeps` with a struct literal including the new
   private `token_providers` field (`E0451`). Added
   `EmailToolDeps::new(secrets, endpoint, needs_reconnect)` and switched
   `lib.rs` and the three test construction sites to it, keeping the cache
   field private.

## Deferred / not done

- **`email_read` still uses `format=full`.** Correct — that tool exists to
  return the body. Only the *search preview* path was projected down to
  metadata. Not a gap, recording it so nobody re-reports it.
- **No integration test through `EmailSearchTool::run` itself.** The tool
  builds a real `ReqwestGmailHttp` internally, so there is no seam to inject a
  fake mailbox at the `Tool` level without a wider refactor of `EmailToolDeps`.
  The fan-out is tested directly via `fetch_previews`, which is the code the
  tool calls; the JSON row assembly around it is not covered by a test.
- **The `Semaphore` is per-call, not per-process.** Ten concurrent
  `email_search` dispatches can still put 30 requests in flight at Gmail. A
  shared per-profile limiter would be the real rate-limit story; out of scope
  here.

## Needs a human decision

1. **Is 32 MiB the right response ceiling?** It is generous by design (above
   Gmail's own 25 MB message limit) so nothing legitimate breaks, but it is
   still 32 MiB of allocation an attacker can force per in-flight request.
   Given `email_read` truncates at 40 000 chars downstream anyway, something
   like 8 MiB would be defensible and much tighter. I picked the safe-for-
   correctness number rather than the safe-for-memory one; say the word and
   it is a one-constant change.
2. **`SharedTokenProvider` newtype vs. changing `GoogleClient::new`.** The
   clean fix is `GoogleClient::new(tokens: Arc<dyn TokenProvider>)`, matching
   what `GmailClient` now takes. That is a one-line change in
   `email/google.rs`, which is outside this packet's declared scope, so I used
   the newtype instead. Worth folding into whichever packet owns `google.rs`.

# P16 remediation round (2026-07-29)

The first commit (`eacfb18`) passed adversarial verification. Two loose ends
were called out; both are addressed here.

## (1) The self-referential concurrency assertion — `tools/email.rs`

`a_slow_preview_does_not_stall_the_others` ended with

```rust
assert_eq!(*mailbox.peak_in_flight.lock(), SEARCH_CONCURRENCY);
```

which compares the observed peak against the very constant that produced it.
Raising `SEARCH_CONCURRENCY` to 5 left the test green, so the bound of 3 was
not actually pinned by anything. Now:

```rust
assert_eq!(*mailbox.peak_in_flight.lock(), 3);
```

The anti-stall assertions (fast fetches complete before the slow one; wall
clock stays under 430 ms where serial would be ~460 ms) were genuine and are
unchanged.

**Mutation check, actually run:** set `SEARCH_CONCURRENCY = 5`, re-ran
`cargo test --lib email` → `a_slow_preview_does_not_stall_the_others` FAILED.
Constant restored to 3 afterwards and the suite is green again.

## (2) The same unbounded read in two sibling modules

`read_body_capped` fixed the Gmail fetch layer, but the identical
`resp.text().await.unwrap_or_default()` survived in two places:

- `email/google.rs` — `GoogleClient::request_once`, the Calendar/Tasks fetch layer.
- `email/oauth.rs` — `HttpTokenEndpoint::post_form`, the token endpoint. This
  one is reachable *before* any account is connected.

Both now go through the same helper.

### Mechanics

- `read_body_capped` and `MAX_RESPONSE_BYTES` in `email/gmail.rs` became
  `pub(super)` (visible to the sibling `email::*` modules, not to the wider
  crate). The helper gained a `what: &str` label so the error text names the
  right API ("Gmail API" / "Google API" / "OAuth token endpoint"). Behaviour
  is otherwise byte-identical, and gmail.rs's existing cap test still passes
  unchanged.
- `GoogleClient` gained a `max_response_bytes` field + a private
  `with_response_cap` constructor (same pattern `ReqwestGmailHttp` already
  uses), so the refusal path is testable without allocating 32 MiB. `new()`
  still uses the shared `MAX_RESPONSE_BYTES` (32 MiB).
- `HttpTokenEndpoint` gained the same field plus a private `build(url, cap)`
  constructor. Its cap is a **separate, much tighter** constant,
  `MAX_TOKEN_RESPONSE_BYTES = 1 MiB`: an OAuth token response is a few
  hundred bytes of JSON, so there is no reason to allow it 32 MiB. This is a
  deliberate choice, not an oversight — flag it if you'd rather have one
  shared number.
- Both call sites moved from `unwrap_or_default()` to `?`. That is a real
  behaviour change beyond the size cap: a body-read failure used to be
  silently converted to an empty string, which `GoogleClient::json` then read
  as a legitimate `null` on a 2xx, and which oauth's classifier read as a
  malformed-but-present response. It is now an error.

### Tests added (2 new, both against a real loopback HTTP server)

- `email::google::tests::oversized_google_api_bodies_are_refused_at_the_fetch_layer`
- `email::oauth::tests::oversized_token_endpoint_bodies_are_refused`

Each has three arms: a declared `Content-Length` over the cap (refused before
a body byte is read), a **chunked** response over the cap (no declared length,
so only the running-total gate can stop it), and a control body under the cap
that must still round-trip intact.

**Mutation check, actually run:** reverted both call sites to

All three mutations (this one, the oauth one, and `SEARCH_CONCURRENCY = 5`)
were applied in a single run and produced exactly 3 failures, no more.
