# Hooks — gating chain and approval spine

- **Purpose** — The single, ordered, in-process checkpoint every tool call must pass through before it executes: privacy egress rules, a non-overridable hardline sandbox denylist, a non-overridable always-`Ask` floor for a hardcoded set of protected workspace paths (`.git/`, `config/secrets`, `.env`, `.ssh/`), per-tool/pattern permission policy, and first-use confirmation — plus the async human-approval machinery (ledger + prompter) that lets an `Ask` turn into a `Continue` without ever skipping the earlier gates.

## Files

- `src-tauri/src/hooks/mod.rs` — `HookEvent`, `EventContext`, `HookResult`, `GatingHook`/`ObserverHook` traits, `HookChain` (runs the gating hooks in order), and the three `build_pretooluse_chain*` constructors that assemble the real chain. `RoutingRequirement` also lives here.
- `src-tauri/src/hooks/privacy_filter.rs` — `PrivacyFilterHook`, a thin adapter over `agent::gate::PrivacyGate::check()`. First hook in the chain.
- `src-tauri/src/hooks/sandbox.rs` — `SandboxHook`, the hardline denylist (unit struct, no config). Second hook in the chain, deliberately positioned before anything that can `Ask`.
- `src-tauri/src/hooks/protected_path.rs` — `ProtectedPathHook`, the always-`Ask` floor for a hardcoded list of workspace paths (`.git/`, `config/secrets`, `.env`, `.ssh/`). Non-configurable (no constructor args, no `PolicySource`/config wiring). Third hook in the chain, between `SandboxHook` and `PermissionHook`. The `Ask` is satisfiable only by a fresh `Once`+`Fingerprint` grant — it consults `ApprovalLedger::covers_once` (which only inspects `once_fps`), so a `Session`/`Tool` grant from a different ask is invisible to it and can never widen the floor to standing coverage.
- `src-tauri/src/hooks/permission.rs` — `PermissionHook`, `PermissionMode`, `ToolRule`, `PolicySource` trait, `InMemoryPolicySource`. Fourth hook.
- `src-tauri/src/hooks/first_use.rs` — `FirstUseConfirmHook`. Fifth/last hook.
- `src-tauri/src/hooks/approval.rs` — the approval spine primitives: `ActionFingerprint`, `GrantScope`, `GrantTarget`, `ApprovalLedger` (with both `covers` for the general hooks and `covers_once` for floor-style hooks), `ApprovalRequest`, `ApprovalDecision`, `ApprovalPrompter` trait. Consumed by `ProtectedPathHook`/`PermissionHook`/`FirstUseConfirmHook` (read) and `ToolDispatcher` (write).
- `src-tauri/src/hooks/routing.rs` — `enforce_local_routing`, `LocalRoutingViolation`. The only code allowed to turn a `RoutingRequirement::LocalRequired` annotation into an actual endpoint pick.
- `src-tauri/src/hooks/tests.rs` — chain-level integration tests (`#[cfg(test)] mod tests;` at the bottom of `mod.rs`). Per-hook unit tests live inline in each hook's own file instead.
- `src-tauri/src/tools/dispatch.rs` — **not in the files-to-review list but is the real caller and the other half of the approval spine.** `ToolDispatcher::dispatch` builds the `EventContext`, calls `chain.run_gating`, and on `Ask` drives the prompter/ledger/re-run loop described below. The `Approve` arm additionally pins a forced-`Once`+`Fingerprint` grant when a protected-path prompt is answered with anything broader than `Once`, so the re-run settles without upgrading the floor itself. Read this file to understand how the gating chain is actually wired to running tools.
- `src-tauri/src/ipc/approval.rs` — Tauri-side `ApprovalPrompter` impl (`TauriApprovalPrompter`) and the `ApprovalRegistry` that parks a `oneshot` channel per pending request, keyed by request id, resolved by the `resolve_tool_approval` IPC command.
- `src-tauri/src/lib.rs` (`build_tool_dispatcher`, ~line 198) — where the real chain is constructed for the app: policy is *derived* from each tool's `RiskClass` (Safe → whole-tool `Allow` + pre-trusted; Write/External/Dangerous → `Ask`).

## Key types / traits / functions

- `HookEvent` — `hooks/mod.rs:83`. Only `PreToolUse` is exercised today; `PostToolUse`/`CronFired`/`CronCompleted`/`AppLaunch` are reserved variants with no wiring yet.
- `RoutingRequirement` — `hooks/mod.rs:111`. `Unconstrained` | `LocalRequired { reason: String }`. Default is `Unconstrained`. `.is_local_required()` at `hooks/mod.rs:128`.
- `EventContext` — `hooks/mod.rs:142`. Fields: `event`, `tool_name`, `input: ToolInput`, `command_text` (pattern-matching string — defaults to a copy of `content` via `with_content`, override with `with_command_text`), `binding: Binding`, `content`, `is_cloud_endpoint`, `conversation_id`, `routing`. Builder methods `pre_tool_use`, `with_content`, `with_command_text`, `with_binding`, `with_cloud`, `with_conversation_id`, `with_input`.
- `HookResult` — `hooks/mod.rs:242`. `Continue | Allow | Deny(String) | Ask(String) | Modify(ToolInput)`. `Continue` and `Allow` are chain-equivalent (both proceed); kept distinct so a hook can be explicit about *actively* allowing vs not objecting.
- `trait GatingHook` — `hooks/mod.rs:254`. `fn name(&self) -> &str; fn on_event(&self, ctx: &mut EventContext) -> HookResult;`. Sync, blocking-lane.
- `trait ObserverHook` — `hooks/mod.rs:268`. Fire-and-forget, never blocks/denies; not consulted for the gating decision. Has an async escape hatch `on_event_async`. No concrete implementation exists yet in this subsystem.
- `HookChain` — `hooks/mod.rs:290`. `register_gating`, `register_observer`, `gating_names() -> Vec<&str>`, `run_gating(&self, ctx: &mut EventContext) -> (HookResult, Option<&str>)` — the `Option<&str>` names which hook produced a `Deny`/`Ask` (used for "denied by: X" UI and for `ToolOutcome::Denied.by` / `ToolOutcome::Ask.by`). `Modify` is consumed inside the loop — rewrites `ctx.input` and continues; it can never be the terminal `(HookResult, _)` returned from `run_gating`.
- `build_pretooluse_chain(gate, policy) -> HookChain` — `hooks/mod.rs:368`. Plain chain, nothing pre-confirmed.
- `build_pretooluse_chain_with_confirmed(gate, policy, confirmed: &[&str]) -> HookChain` — `hooks/mod.rs:385`. Same, but pre-marks `confirmed` tools in `FirstUseConfirmHook` (for safe-by-default tools shipped by the body).
- `build_pretooluse_chain_full(gate, policy, confirmed, ledger: Arc<ApprovalLedger>) -> HookChain` — `hooks/mod.rs:411`. Same as above but threads one shared `Arc<ApprovalLedger>` into both `PermissionHook` and `FirstUseConfirmHook` via `.with_ledger(...)`. **This is the constructor the real app uses** (`lib.rs:248`). The caller MUST pass the same `Arc` into `ToolDispatcher::with_approval` or grants won't be visible to the hooks.
- `PrivacyFilterHook::on_event` — `privacy_filter.rs:35`. Maps `GateDecision::Allow → Continue`, `Block(reason) → Deny(reason)`, `RouteLocal → Continue` **plus** sets `ctx.routing = LocalRequired{reason}`.
- `SandboxHook::on_event` — `sandbox.rs:118`. Iterates a fixed `DENYLIST: &[DenylistEntry]` (`sandbox.rs:32`) matching against `ctx.command_text`; `Deny` on any match, else `Continue`. No constructor arguments at all — `SandboxHook` is a bare unit struct, which is itself the enforced invariant (see Invariants below).
- `ProtectedPathHook::on_event` — `protected_path.rs:96`. Iterates a fixed `PROTECTED: &[ProtectedPathEntry]` (`protected_path.rs:46`) matching against `ctx.command_text`; on any match, checks `ApprovalLedger::covers_once(&fp)` and returns `Continue` if covered, else `Ask(reason)`. The Once-only check is the whole mechanism that makes the floor non-widening: a `Session`/`Tool` grant from a different ask is invisible to `covers_once`. No constructor arguments — `ProtectedPathHook::new()` and `ProtectedPathHook::with_ledger(...)` are the only builders, and the former is just a fallback that uses its own empty ledger (used by the two non-`_full` chain constructors; those chains can't satisfy the floor anyway because they have no shared ledger with the dispatcher).
- `PermissionHook::resolve(&self, ctx) -> Option<PermissionMode>` — `permission.rs:205`. Most-specific matching `ToolRule` wins (specificity = literal-char count; `PermissionMode::priority()` at `permission.rs:34` breaks ties Deny(2) > Ask(1) > Allow(0)); falls back to `PolicySource::mode_for(tool_name)`; falls back to `None`.
- `PermissionHook::on_event` — `permission.rs:224`. `Allow → Continue`; `Deny → Deny(reason)`; `Ask` → checks `ledger.covers(tool_name, fingerprint)` first, `Continue` if covered else `Ask(reason)`; `None → Continue` (explicitly falls through to `FirstUseConfirmHook`, NOT an implicit ask).
- `glob_match(pattern, text) -> bool` — `permission.rs:82`. Minimal `*`-only glob, no regex crate.
- `trait PolicySource` — `permission.rs:127`. `mode_for(tool_name) -> Option<PermissionMode>`, `rules_for(tool_name) -> Vec<ToolRule>`. `InMemoryPolicySource` (`permission.rs:136`) is the only impl; a future SQLite-backed `tool_rules`/`tool_profile_permissions` source (PLAN M4) is meant to drop in against the same trait.
- `FirstUseConfirmHook` — `first_use.rs:25`. Two independent "already OK" sources: `seen: Mutex<HashSet<String>>` (set only via `mark_confirmed`, at construction time — never written by `on_event`) and the shared `ledger`. `on_event` (`first_use.rs:78`) returns `Continue` if either covers the tool/fingerprint, else `Ask` — and critically does **not** mark the tool seen just because it asked.
- `ActionFingerprint::of(tool_name, args) -> String` (`approval.rs:43`) / `::from_ctx(ctx) -> String` (`approval.rs:57`) — SHA-256 over `tool_name + 0x00 + canonical(args)`. `canonical()` (`approval.rs:65`) sorts object keys recursively so fingerprints are stable regardless of JSON key order/`serde_json` feature flags.
- `GrantScope` — `approval.rs:100`. `Once` (consumed at execution), `Session` (until app restart), `Always` (**currently aliased to `Session` in-memory** — no persistent `PolicySource` yet, PLAN M4).
- `GrantTarget` — `approval.rs:112`. `Fingerprint(String)` (the pin — exact action) | `Tool(String)` (deliberate broadening — any call to that tool).
- `ApprovalLedger` — `approval.rs:125`. Three `Mutex<HashSet<String>>` sets: `once_fps`, `session_fps`, `session_tools`. `covers(tool_name, fingerprint) -> bool` (`approval.rs:140`) — OR across all three, used by `PermissionHook`/`FirstUseConfirmHook`. `covers_once(fingerprint) -> bool` (`approval.rs:147`) — `once_fps` ONLY, used by `ProtectedPathHook` so the floor can't be satisfied by a standing grant. `grant(target, scope)` (`approval.rs:164`) — note `(Once, Tool(_))` is explicitly a no-op (`approval.rs:175`): a one-time grant has no fingerprint to pin to, so it grants nothing rather than silently widening to session-length. `consume_once(fingerprint)` (`approval.rs:187`) removes a once-grant; must be called by the dispatcher right before/after a covered call succeeds.
- `trait ApprovalPrompter` — `approval.rs:210`. `fn request(&self, req: ApprovalRequest) -> Pin<Box<dyn Future<Output = ApprovalDecision> + Send>>`. Implemented by `TauriApprovalPrompter` (`ipc/approval.rs:117`); `ToolDispatcher` holds `Option<Arc<dyn ApprovalPrompter>>` — `None` means round-1/headless fallback (surface the `Ask` to the model, don't block).
- `enforce_local_routing(routing: &RoutingRequirement, candidates: &[Provider]) -> Result<&Provider, LocalRoutingViolation>` — `routing.rs:50`. `Unconstrained` → first candidate (or error if none). `LocalRequired` → first candidate where `p.is_local() && p.is_private()`, else `Err(LocalRoutingViolation)` — structurally cannot return a cloud provider on this branch. Uses the same `is_local()/is_private()` definition as `AgentLoop::find_local_provider` by design (comment at `routing.rs:17-19`), so it can't quietly diverge.

## Data flow / how it fits

1. `ToolDispatcher::dispatch` (`tools/dispatch.rs:114`) is the real entry point (not in this subsystem's file list, but load-bearing to understand it). Given a parsed `ToolCall`, `ExecCtx`, `Binding`, and `is_cloud`:
   - Resolves the tool in the registry; checks `tool.available(&env)` (capability gate, separate from the hook chain).
   - Computes `canonical = "{name} {args}"` (feeds `command_text`) and `fingerprint = ActionFingerprint::of(name, args)`.
   - Loop (bounded `MAX_APPROVAL_ROUNDS = 4`, `dispatch.rs:145`): builds a fresh `EventContext`, calls `self.chain.run_gating(&mut ev)`.
     - `Continue`/`Allow` → consumes any once-grant for this fingerprint (`ledger.consume_once`, `dispatch.rs:162`, done *before* checking routing so a once-grant can't stay armed if routing blocks it), then checks `ev.routing.is_local_required() && is_cloud` — if true, **denies** here (`by: "privacy-filter"`) rather than running the tool and leaking the result to a cloud model next turn. Otherwise runs `tool.run(...)`.
     - `Deny(reason)` → `ToolOutcome::Denied { by, reason }`, tool never runs.
     - `Ask(prompt)` → if no `approver` wired, surfaces `ToolOutcome::Ask` (model sees "not granted this round"). If an approver exists, builds an `ApprovalRequest`, awaits `approver.request(req)`. `Approve(scope, target)` → `ledger.grant(...)`, then if `by == "protected_path" && scope != Once` (i.e. the user answered a protected-path prompt with "Allow for this session" / "Allow always") the dispatcher ALSO pins a forced `Once`+`Fingerprint` grant for this exact call so the re-run settles without ever upgrading the floor to standing coverage (`dispatch.rs:296-308`). Then `continue`s the loop — **re-runs the whole chain from scratch**, including the sandbox floor, protected-path floor, and privacy filter. `Deny`/`Timeout` → `ToolOutcome::Denied`.
   - `run_turn` (`dispatch.rs:264`) parses tool calls out of the model's own current-turn output (never from tool-result text — that's the "parse only your own output" rule) and dispatches each via `dispatch`.
2. The Tauri side wires this via `build_tool_dispatcher` (`lib.rs:198`): registers workspace-confined fs tools, derives `PermissionMode` from each tool's `RiskClass` (`RiskClass::Safe` → `Allow` + pre-trusted; `Write`/`External`/`Dangerous` → `Ask`), builds the chain with `build_pretooluse_chain_full`, and calls `ToolDispatcher::with_approval(ledger, Some(prompter))`.
3. `TauriApprovalPrompter::request` (`ipc/approval.rs:133`) parks a `oneshot` channel in `ApprovalRegistry` keyed by a UUID, emits `tool:approval_request` to the frontend, and awaits with a 300s timeout (deny-by-default, `ipc/approval.rs:159-167`). The frontend answers via the `resolve_tool_approval` IPC command, which calls `ApprovalRegistry::answer` — this touches *only* the registry, never the agent loop's stream lock (documented deliberately to avoid deadlock, `ipc/approval.rs:11-13`).
4. Downstream, once a tool call is allowed and executed, if `ctx.routing` was `LocalRequired`, whatever *does* the actual model-endpoint pick for a subsequent call is expected to run it through `enforce_local_routing` (`routing.rs`) rather than picking a candidate directly — that's a caller obligation, not something the hook chain enforces on its own after `dispatch` returns.

## Invariants (do NOT break)

- **First "no" wins, in fixed order.** The chain is `[PrivacyFilterHook, SandboxHook, ProtectedPathHook, PermissionHook, FirstUseConfirmHook]`, asserted by `default_pretooluse_chain_is_in_spec_order` (`tests.rs:184`). `HookChain::run_gating` short-circuits on the first `Deny`/`Ask` (`mod.rs:326-339`); anything registered after that point never runs for that call.
- **The sandbox floor always runs and cannot be configured away.** `SandboxHook` is a bare unit struct — no constructor args, no `SandboxConfig` wiring today (`SandboxConfig`/`SandboxNetworkConfig` at `sandbox.rs:143` are a locked-in *shape* for future OS-level enforcement, not consulted by `SandboxHook::on_event` at all). It is positioned immediately after the Deny-only `PrivacyFilterHook` and *before* every hook capable of `Ask` (`ProtectedPathHook`, `PermissionHook`, `FirstUseConfirmHook`) specifically so a whole-tool `Allow` or `Ask` policy can never let a denylisted command reach human confirmation (and eventually `Tool::run`) without the floor being consulted. Enforced by `sandbox_denies_even_when_permission_would_allow` and `sandbox_runs_before_any_hook_that_can_ask` (`tests.rs:194`, `tests.rs:216`), plus `cannot_be_overridden_by_any_config` (`sandbox.rs:281`) which exists specifically to catch a future PR that adds a bypassable `SandboxHook::new(config)`.
- **The protected-paths floor is non-overridable and Once-only.** `ProtectedPathHook` is parameterized exactly like `SandboxHook` (no constructor args, no `PolicySource`/config wiring) — the protected-path list is hardcoded, period. It's positioned between `SandboxHook` and `PermissionHook` so the sandbox's hard-Deny floor still runs first. Crucially, its `Ask` is satisfiable only by a fresh `Once`+`Fingerprint` grant: it consults `ApprovalLedger::covers_once` (`approval.rs:147`), which only inspects `once_fps`. A `Session`/`Tool` or `Session`/`Fingerprint` grant from a different ask is invisible to `covers_once` and can never widen the floor to standing coverage — a user clicking "Allow for this session" on a protected-path prompt gets the grant applied to other call sites legitimately, but the next protected-path call (different fingerprint) still prompts. Enforced by `protected_path_runs_before_permission_even_under_an_allow_policy` (`tests.rs:241`) and the dispatcher-level `protected_path_floor_asks_even_under_an_allow_policy` + `session_grant_does_not_bypass_the_floor_on_a_different_protected_path` (`dispatch.rs:1596`, `dispatch.rs:1634`). The dispatcher's `Approve` arm also pins a forced-`Once`+`Fingerprint` grant when a protected-path prompt is answered with anything broader than `Once` (`dispatch.rs:296-308`), so the re-run settles without upgrading the floor itself.
- **`RouteLocal` never silently degrades to "allow on cloud."** `PrivacyFilterHook` maps `GateDecision::RouteLocal` to `HookResult::Continue` *plus* sets `ctx.routing = LocalRequired`; it is never itself a `Deny`. `enforce_local_routing` is the only code allowed to resolve that annotation into an endpoint choice, and it fails loudly (`LocalRoutingViolation`, a named type, not a stringly-typed error) rather than falling back to the first (possibly cloud) candidate — see `local_required_never_returns_a_cloud_provider` (`routing.rs:120`). `ToolDispatcher::dispatch` additionally hard-denies (doesn't just warn) if `ev.routing.is_local_required() && is_cloud` before ever calling `tool.run` (`dispatch.rs:169-182`), covered by `local_required_call_is_blocked_on_a_cloud_endpoint` (`dispatch.rs:503`).
- **Asked ≠ approved.** `FirstUseConfirmHook::on_event` never marks a tool `seen` merely for having returned `Ask` — only `mark_confirmed` (construction-time pre-trust) or an actual ledger grant (recorded by the dispatcher after a real user "yes") can flip a later call to `Continue`. Enforced by `asking_does_not_mark_the_tool_seen` (`first_use.rs:120`). This is what stops an unattended agent from self-granting a state-changing tool by attempting it once.
- **A `Once` grant is per-action, never per-tool.** `ApprovalLedger::grant((GrantScope::Once, GrantTarget::Tool(_)))` is explicitly a no-op (`approval.rs:160`); `resolve_tool_approval`/the dispatcher is expected to force `Once ⇒ Fingerprint` upstream. Test: `a_once_grant_for_a_whole_tool_grants_nothing` (`approval.rs:264`).
- **Deny wins ties in `PermissionHook`.** When multiple pattern rules match with equal specificity, `Deny` (priority 2) beats `Ask` (1) beats `Allow` (0) — `deny_wins_tiebreak_among_equally_specific_matches` (`permission.rs:348`).
- **An unconfigured tool falls through to `Continue`, not an implicit `Ask`.** `PermissionHook::resolve` returning `None` maps to `HookResult::Continue` so `FirstUseConfirmHook` gets the final say — `unconfigured_tool_falls_through_as_continue` (`permission.rs:293`).
- **The dispatcher and the chain must share one `Arc<ApprovalLedger>`.** `build_pretooluse_chain_full`'s docstring and `lib.rs:248-254` both call this out explicitly — passing two different ledger instances silently breaks grant visibility (no compiler error, just approvals that never take effect).
- **`resolve_tool_approval` never touches the agent loop's stream lock** (`ipc/approval.rs:11-13`, reiterated at `dispatch.rs:211-217`) — this is what keeps a pending approval from deadlocking a concurrent send. Preserve this if you touch either IPC command.

## Gotchas / watch-items

- **`Always` currently behaves like `Session`.** No persistent `PolicySource` exists yet (PLAN M4 / SQLite `tool_rules`); an "always allow" grant does NOT survive an app restart even though the UI/API vocabulary suggests it should. Documented at `approval.rs:20-24` and `approval.rs:146-148`. If you wire persistence, both `ApprovalLedger::grant` and whatever consumes `GrantScope::Always` need updating together.
- **`SandboxConfig`/`SandboxNetworkConfig` are dead config** — a locked-in schema shape for future OS-level sandboxing (Seatbelt/bubblewrap), not read by `SandboxHook` at all today. `network.allowed_domains` is called out as meant to be enforced at the `shell_exec` library level, separately — don't assume setting `SandboxConfig.network.allowed_domains` does anything yet.
- **`ObserverHook` has no concrete implementation** in this subsystem — the trait and `HookChain::notify_observers`/`register_observer` exist but nothing calls `register_observer` anywhere in the reviewed files. TRM logging/telemetry is future work.
- **Only `PreToolUse` is live.** Every hook's `on_event` starts with `if ctx.event != HookEvent::PreToolUse { return Continue; }` — the other four `HookEvent` variants are reserved enum members with zero wiring; adding real behavior for `CronFired`/`AppLaunch`/etc. means writing new dispatch call sites, not just new hook logic.
- **`command_text` vs `content` divergence is easy to get backwards.** `EventContext::with_content` sets both `content` and `command_text` to the same string by default; `with_command_text` overrides only the latter. `PrivacyFilterHook` reads `content`+`binding`; `SandboxHook`/`PermissionHook` read `command_text`. In `ToolDispatcher::dispatch`, both are set from the same `canonical = "{name} {args}"` string (`dispatch.rs:135,151`) — so in production these two fields are currently identical; tests exploit setting them differently (e.g. `sandbox_denies_even_when_permission_would_allow` sets `.with_content("cleanup").with_command_text("rm -rf /")` to bypass the privacy filter cleanly while still hitting the sandbox denylist). Don't assume `content == command_text` when reasoning about a hook in isolation.
- **`glob_match`'s specificity heuristic is naive.** It's literal-character count, not glob "narrowness" in any formal sense — e.g. `"a*a*a*a*a*a*a*a*a*a"` would out-specificity a much narrower-in-practice pattern with fewer stars but more literal text elsewhere. Fine for today's short profile-authored rules; would need a real ranking if rules get complex or attacker-authored (they aren't, currently — profile-authored only).
- **`MAX_APPROVAL_ROUNDS = 4` in `ToolDispatcher::dispatch`** (`dispatch.rs:145`) is a backstop, not a designed retry count — one grant is supposed to settle in 2 passes (ask → grant → re-run). If you add a hook that can `Ask` more than once per call in the normal path, this cap may start firing legitimately; it currently fails closed (`ToolOutcome::Denied { by: "approval", ... }`) if exhausted.
- **`FirstUseConfirmHook`/`PermissionHook`/`ProtectedPathHook` each default-construct their own empty `ApprovalLedger`** if `.with_ledger` isn't called (`first_use.rs:40`, `permission.rs:191`, `protected_path.rs`) — `build_pretooluse_chain`/`build_pretooluse_chain_with_confirmed` (the two non-`_full` constructors) do NOT wire a shared ledger, so any `Ask` from those chains can never be satisfied by a grant; they're effectively "ask every time, no interactive resume" chains. Only `build_pretooluse_chain_full` (used by the real app) wires ledger-aware hooks.
- **Sandbox denylist is substring/heuristic matching on lowercased text**, not a shell parser — e.g. `"/.ssh/"` matches inside any longer path, `"curl"`/`"wget"` matching is a plain substring check. It's deliberately recall-biased/simple (per the module doc), not a hardened sandbox; don't treat a `Continue` from `SandboxHook` as "this command is safe," only "this command didn't match the fixed floor list."
- **PLAN.md vs code**: skim `docs/PLAN.md` §8 and `docs/tooling-and-skills.md` §3.4/§3.1/§10/§11 if you want the spec framing — the code here matches the spec's shape closely (I did not find a divergence worth flagging), but PLAN.md's "M3 build order item N" numbering is a planning artifact, not something enforced by the code; don't rely on it as a map of current file contents.

## How to extend

- **Add a new gating rule that should be non-overridable** (like the sandbox floor): add an entry to `sandbox.rs`'s `DENYLIST` array (`label` + `matches: fn(&str) -> bool`), not a new hook — keeping everything hardline in one place preserves the "first Ask-capable hook can't skip it" ordering guarantee. If it truly needs new hook machinery, it must be registered in `build_pretooluse_chain*` *before* `PermissionHook`/`FirstUseConfirmHook`.
- **Add a new always-`Ask` floor for a hardcoded list** (like the protected-paths floor): mirror `protected_path.rs` — no constructor args, no `PolicySource`/config wiring, consult only `ApprovalLedger::covers_once` (not `covers`) so a standing grant from a different ask can never satisfy it. Register it in all three `build_pretooluse_chain*` constructors between `SandboxHook` and `PermissionHook`. Update `default_pretooluse_chain_is_in_spec_order` and add a "runs before permission even under an Allow policy" test mirroring the one in `tests.rs`.
- **Add a new configurable per-tool policy default:** wire it into whatever builds the `InMemoryPolicySource` for the body — for the real app that's `build_tool_dispatcher` in `lib.rs`, keyed off `Tool::risk() -> RiskClass` (`tools/mod.rs:172`). Don't hand-special-case tool names in `PermissionHook` itself; it's meant to stay policy-agnostic.
- **Add a new `GatingHook`:** implement the trait (`name`, `on_event`), decide where in the chain it belongs relative to the Deny-only privacy filter / hardline sandbox / protected-paths floor / Ask-capable permission+first-use hooks, and add it inside `build_pretooluse_chain*` in `mod.rs`. If it can `Ask`, decide whether it should also consult the shared `ApprovalLedger` (take `Arc<ApprovalLedger>` via a `.with_ledger` builder method like the existing three) so a single user approval can satisfy it too. If it must remain satisfiable only by a fresh `Once` grant (floor-style), use `covers_once` not `covers` — see `ProtectedPathHook`.
- **Persist `Always` grants across restarts (PLAN M4):** implement a persistent `PolicySource` (SQLite `tool_rules`/`tool_profile_permissions`), and change `ApprovalLedger::grant`'s `(Session | Always, ...)` arm (`approval.rs:161-166`) to route `Always` there instead of into the in-memory `session_*` sets. Also update the module doc comment at `approval.rs:20-24`, which explicitly says this is deferred.
