## Summary

Replaced the global `tokio::sync::Mutex<()>` (`stream_lock`) on `AgentLoop` with a per-conversation `HashMap<String, Arc<tokio::sync::Mutex<()>>>` (`stream_locks`). A stalled turn in one conversation no longer blocks other conversations from processing messages.

### What changed

1. **Struct field `stream_lock` → `stream_locks`**  
   - Old: `stream_lock: tokio::sync::Mutex<()>` — a single global lock.
   - New: `stream_locks: Arc<parking_lot::Mutex<HashMap<String, Arc<tokio::sync::Mutex<()>>>>>` — per-conversation locks.

2. **`process_message` (L399)**  
   - Old: `let _stream_guard = self.stream_lock.lock().await;` — held lock for entire turn, blocking all conversations.
   - New: Acquires a per-conversation `Arc<tokio::sync::Mutex<()>>` from the HashMap (creating on first use), then locks only that. Two calls for the same `conversation_id` serialize; different conversations proceed independently.

3. **Constructor** — initializes the new `stream_locks` field.

4. **Comments updated** — references from `stream_lock` → `stream_locks` throughout; the struct doc, `cancel_conversation`, `conversation_is_cloud_safe` cold-scan comment, and `on_pre_compaction` doc.

5. **New concurrent test** (`two_conversations_progress_independently`)  
   - A single `AgentLoop` with a `SelectorStreamer` that returns a **pending** (never-ending) stream for "slow-conversation" and a **fast** canned SSE response for any other conversation.
   - Conv A is spawned and hangs in the SSE drain loop.
   - Conv B completes within a 5-second timeout — proving the per-conversation lock doesn't block it.
   - With the old global lock, conv B could never enter `process_message` while conv A held the lock.

## Safety analysis

- **No new deadlock introduced**: The `parking_lot::Mutex` on the HashMap is held only for the `entry().or_insert_with().clone()` operation — microseconds, no `.await` inside. The `tokio::sync::Mutex` on the per-conversation lock is held exactly as the old global lock was, but scoped per conversation.
- **Ordering preserved**: Within a single conversation, messages process in FIFO order (same as before). Cross-conversation ordering was never guaranteed.
- **Cancel-safety**: `cancel_conversation` only touches `self.cancellations` (a separate `parking_lot::Mutex<HashMap>`), never `stream_locks`, so deadlock-free by construction.
- **No lock inversion**: All lock acquisitions are leaf-locks (no nested `.await` while holding a `parking_lot` lock).

## Follow-ups

1. **`tools/dispatch.rs` L175–178**: `run_state: Mutex<RunState>` has a comment stating it's safe because `stream_lock` serializes all `process_message` calls. With per-conversation locking, this invariant is weakened — two concurrent runs for different conversations could race on `run_state`'s budget/repeat-detection. The field is already `Mutex`-protected (no data race), but per-run semantic correctness across concurrent conversations is untested. **Suggested fix: key `run_state` by conversation_id**, matching the new per-conversation lock structure. This is a separate, bounded change in `dispatch.rs` only.
2. **`conversation_is_cloud_safe`** cold-scan limit: The per-conversation lock means a single long cold scan only blocks its own conversation, not all conversations. The existing `COLD_SCAN_CAP` of 200 messages is still a sensible bound per-conversation.
3. **HashMap cleanup**: The `stream_locks` HashMap accumulates entries per conversation but never removes them. This is acceptable (bounded by active conversations, each entry is ~64 bytes). A bounded LRU or explicit cleanup on conversation deletion could be added as future polish, but is not load-bearing.

## Needs human decision

None. The change is conservative, preserves existing ordering guarantees, and the per-conversation locking pattern is already used by `cancellations`, `summary_cache`, and `cloud_safe_cache`.
