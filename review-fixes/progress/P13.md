## What the adversarial review REFUTED, and what this pass did about it

### 1. The cron loop had no transaction — FIXED

The prior note called cross-DB atomicity "inherent" and shipped the cron inserts as a bare loop of
`db.insert_cron_job(&job)?`. That conflated two different things: SQLite genuinely cannot span two
files in one transaction, but the *cron loop itself* could always have had its own. `ProfileDb::raw()`
hands out the connection, so the fix was available the whole time.

The loop now runs inside `conn.transaction()` on the profile DB, using raw `INSERT` SQL rather than
`insert_cron_job` — `raw()` holds the connection's `parking_lot::Mutex`, which is not reentrant, so
calling `insert_cron_job` while holding the guard would deadlock. The `enabled` column is still
written as `0` (installed disabled); `install_lands_everything_inert_pending_and_disabled` still
passes and still asserts that.

Result: a partial cron import is no longer possible. A failure on cron job N rolls back jobs 1..N-1.

### 2. The module doc lied — FIXED (doc corrected, not behaviour)

The old header claimed a post-global-commit failure "returns a partial `InstallReport` of exactly
what landed". It does not — the error propagates via `?` and no report is returned at all. I chose
to correct the doc rather than implement partial-report behaviour, because changing `install_pack`'s
success/failure contract is a bigger design decision than this packet's scope. The header and the
`# Atomicity` doc on `install_pack` now say what the code actually does: two transactions, one per
DB; either segment rolls itself back completely; the seam between the two commits is the single
remaining non-atomic point, and hitting it returns `Err` with the (inert) global items committed.

### 3. No test covered the global rollback — FIXED

Added `install_rolls_back_the_global_transaction_on_a_mid_segment_failure`. It installs a SQLite
`BEFORE INSERT ON agent_types ... RAISE(ABORT)` trigger on the temp global DB, then installs a pack
with 1 skill + 1 agent type. Because `install_pack` writes all skills before any agent type, the
skill is already inside the transaction when the abort fires. The test asserts (a) the error is the
trigger's, not an earlier bail, and (b) `list_skills()` is empty afterwards.

Added the cron counterpart, `install_rolls_back_the_cron_transaction_on_a_mid_segment_failure`: a
trigger that aborts only the job named `Second job`, a pack carrying two cron jobs, and an assertion
that zero cron jobs survive.

### 4. `validate_rejects_oversized_json` was inert — FIXED

The old version stuffed >1MB into `description`, which also trips `PACK_MAX_DESC_LEN`, so the test
passed with the byte cap deleted. It now builds 5 skills of 210 KB content each — 5 ≤
`PACK_MAX_SKILLS`, each field well under `PACK_MAX_CONTENT_LEN`, total ~1.05 MB. The test first
asserts `validate_pack(&pack)` **succeeds** (proving no per-field limit fires), then asserts
`parse_pack` errors with `"payload too large"`. Only the byte cap can reject it.

### 5. The "enforced at IPC by P05" claim — REMOVED

Verified by grep: `PACK_IMPORT_MAX_BYTES` appears nowhere outside `packs/mod.rs`, and
`ipc::install_pack` (`src-tauri/src/ipc/mod.rs:1534`) passes `args.json` straight into `parse_pack`
with no size guard. The claim was false. It was in the note **and** in the doc comment on the
constant itself; both are gone. The constant's doc now states that `parse_pack` is the only
enforcement point.

### 6. Cron `prompt` had no empty check — FIXED

`validate_pack` now rejects a whitespace-only cron `prompt`, matching the guards `name` and
`schedule` already had.

## Honest remaining limits

- **The seam between the two commits is still not atomic**, and cannot be with two SQLite files and
  no distributed-transaction machinery. This is now stated accurately in the module header instead of
  being papered over with a false partial-report claim. If global commits and cron then fails, the
  caller gets `Err` and the skills + agent types remain — inert (`Pending` / disabled), so reviewable
  in Settings rather than armed. Closing this properly would mean either a compensating delete of the
  global rows or moving to a genuine partial-`InstallReport` return; both are design changes beyond
  this packet.
- The `install_pack` doc says the profile DB is opened before the global transaction so a missing
  profile is caught pre-mutation. That is true, but only when the pack actually carries cron jobs —
  `open_profile` is skipped entirely for a cron-less pack. That is harmless (nothing touches the
  profile DB in that case) and unchanged from `416026b`.
- The two rollback tests use SQLite triggers as the failure injector. That exercises the real
  rollback path, but it is a synthetic failure, not a naturally-occurring one — there is no UNIQUE
  constraint on `skills.name` or `agent_types.name` to collide with.
- The limit values (50 skills / 25 agent types / 25 cron jobs / 256 KB content) are still chosen,
  not derived from a measured workload.
