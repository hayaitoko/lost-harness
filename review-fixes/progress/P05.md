## 2. H-06 — the loopback check was a string test

`host.starts_with("127.")` accepted `http://127.evil.com`, a public DNS name, and would
have handed it the provider's bearer key over plaintext HTTP. Replaced with
`host_allows_cleartext(&url::Host)`, which decides on the parsed host:

- `Host::Domain` → accepted only when it IS `localhost`. So `127.evil.com`,
  `127.0.0.1.evil.com`, `localhost.evil.com`, `10.evil.com` are all rejected.
- `Host::Ipv4` → `is_loopback() || is_private() || is_link_local() || 100.64/10` (CGNAT).
- `Host::Ipv6` → `is_loopback() || fc00::/7 || fe80::/10` (both spelled out; the std
  predicates are still unstable).

The `Host` enum also fixes the IPv6 bracket special-casing the old code needed, and it
recognizes `http://2130706433` (decimal `127.0.0.1`) as loopback — no string test can.

### DEVIATION from the packet instruction — read this

The packet said "require `is_loopback()`". I allow loopback **and private/LAN literals**.
Reason, not preference: `is_loopback()` alone breaks the product. The repo's own
pre-existing contract test
`ipc::contract_tests::update_provider_correct_shape_dispatches_and_keeps_stored_key`
adds `http://10.0.0.100:8000/v1`, and that is the documented deployment (a llama.cpp /
vLLM box on the user's LAN). I verified this rather than assuming: with a loopback-only
mutation in place, `cargo test --lib` fails **two** tests — my LAN test and that contract
test (transcript below in Validation). Under the strict rule, no LAN provider could be
added at all, and the only in-scope way to keep the suite green would have been editing
`contract_tests.rs`, which is outside my declared scope.

Private *names* (`.local`, `.lan`, `.ts.net`) stay **rejected** for cleartext even though
`agent::egress::is_private_endpoint` counts them as private — a name is whatever DNS/mDNS
answers first, so it cannot be trusted to hold a cleartext bearer key. That matches the
old behavior (it rejected them too), so this is not a new restriction.

### Redirect test

`ModelClient::new` already disabled redirects (landed in `88cb052`); it had no test. Added
`the_model_client_does_not_follow_redirects`: two one-shot loopback `TcpListener`s, the
first answering `302 Location: <second>`, the second answering a valid model list. With
redirects off the 302 surfaces as the error; re-enabling `Policy::limited(10)` makes
`list_models` return `["redirected"]` and the test fail (verified — see Validation).

Test lives in `ipc/mod.rs`'s test module rather than next to `client.rs` because
`client.rs` is out of scope for this packet. Slightly odd placement, disclosed here.

## 3. M-05 — `add_provider` now compensates

The keychain write preceded the fallible `insert_endpoint`, so a failed insert stranded a
live API key under a fresh uuid that no endpoint row — and therefore no UI — would ever
name again: unreachable and undeletable. `add_provider` now deletes the keychain entry on
insert failure (only if it wrote one), mirroring `update_provider`'s existing rollback.

## 4. Rotation takes effect without a restart

`set_provider_api_key` wrote the keychain and stopped. The keychain is only read at boot
(`hydrate_providers_from_storage`), so the live `Provider` — and the `ModelClient` cached
against it, which copies the key into its bearer header — kept signing requests with the
**rotated-out** key for the rest of the session. Now the command rebuilds the record with
the new key and calls `model_manager.add_provider`, which replaces it by id *and* drops
the cached client, so the next `get_client` rebuilds with the new key. The existence check
still runs before the write, so an unknown id writes nothing.

## 5. M-22 — no more fabricated routing in a success payload

`send_message` substituted `("", "unknown")` when the post-turn read-back came up empty:
a message id addressing nothing, and a routing decision nobody made, inside an `Ok(..)`.
The routing badge is how the user learns whether their text left the machine, so this is a
privacy-UI lie, not a cosmetic one.

`SendMessageResponse` now carries:

```rust
message_id: Option<String>,          // null when there is no row to point at
routing_decision: Option<String>,    // null — never a stand-in
#[serde(skip_serializing_if = "Option::is_none")]
routing_unavailable: Option<RoutingUnavailable>,  // absent on the happy path
```

`RoutingUnavailable` names the reason: `profile_db_unavailable`, `message_query_failed`,
`no_assistant_row` (the last is the *normal* shape of a gate block, which persists no
assistant row — so this is a reached path, not a theoretical one). `send_message` and the
tests both build the payload through `RoutingLookup::into_parts`, so the serialization
tests pin the mapping the command actually uses.

## Structural changes a reviewer should know about

- `add_provider` and `set_provider_api_key` are now one-line forwarders to
  `add_provider_inner(&AppState, args)` / `set_provider_api_key_inner(&AppState, args)`.
  A `State<'_, AppState>` can only be minted by a live Tauri app, and `send_message`-style
  commands can't even register under `MockRuntime`; the `&AppState` seam is what makes the
  compensation and rotation tests possible without a Tauri harness.
- The test module gained `test_state()` (real temp-dir `Storage`, empty `ModelManager`) and
  a local `RecordingSecretStore` that logs deletes. `secrets::MemoryProviderSecretStore`
  only exposes surviving values, and adding a `deleted` accessor to it would have meant
  editing `secrets.rs` — out of scope.

## Honest coverage gaps

- The two lines **inside** `send_message` that build the `Result<_, RoutingUnavailable>`
  from `open_profile` / `list_messages_by_conversation` are not executed by any test.

  and `into_parts` (everything downstream of those two lines) are covered, and both the

- `update_provider`'s pre-existing rollback still has no test. Out of this packet's stated

1. **The TS mirror of `SendMessageResponse` is now stale.**
   `src/lib/api/tauri.ts` (~line 49) still declares `message_id: string` and
   `routing_decision: string`; both can now be `null`, and `routing_unavailable` is
   undeclared. TypeScript can't see the Rust struct, so nothing errors — it's a silent
   drift that needs a one-line-per-field fix.
   I traced the runtime impact before changing the shape, and it is **not** a regression:
   - `chat.ts` reads `response.message_id` only in the `if (!resolvedMessageId)` success
     branch; it used to receive `""` there, which is equally falsy and equally matches no
     message row.
   - `finalizeMessage(..., response.routing_decision)` does `routingDecision ?? m.routing_decision`,
     so `null` keeps whatever the stream set. The old `"unknown"` was *worse*: it made
     `MainScreen`'s `m.routing_decision != null` badge condition true and rendered a badge
     for a decision that matched no branch.
   A follow-up could render the degraded state explicitly from `routing_unavailable`
   (e.g. "routing unknown" instead of no badge at all).
2. **Cleartext policy decision.** I allow http to RFC1918/CGNAT/link-local **literals**
   and reject it for private *names* (`.local`, `.lan`, `.ts.net`). If Lukas wants
   `http://tadashi.local:8000` addable, that's a deliberate widening and should be its own
   change with its own reasoning about DNS spoofing — not something I'd slip in here.

   calls it yet.
