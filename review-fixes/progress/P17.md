## H-09 — CI matrix was advertising support that does not exist

**The bug.** The matrix was `[macos-latest, ubuntu-latest, windows-latest]`, but
every Rust step was pinned to `--target aarch64-apple-darwin` with **no `if:`
guard**. On the ubuntu and windows legs those steps could only fail: the target
is not installed there and could not link even if it were. Two of the three legs
were guaranteed-red decoration.

**Shape chosen: single macOS/arm64 job. `ubuntu-latest` and `windows-latest`
are removed from the workflow entirely.**

> ⚠ **P21 — read this.** P21 also edits `.github/workflows/build.yml` and merges
> after me. The `strategy:`/`matrix:` block no longer exists, `runs-on` is a
> literal `macos-latest`, `${{ matrix.os }}` and `${{ runner.os }}` no longer
> appear anywhere in the file, and the "Install Linux system dependencies" step
> is deleted. Any P21 change written against the old matrix will conflict.

Why macOS-only rather than guarded multi-OS:

- The vendored llama.cpp runtime ships as arm64 Mach-O only
  (`src-tauri/vendor/llama-cpp/macos-arm64/`) — verified below.
- `computer-use` is built on macOS Accessibility + CoreGraphics
  (`core-graphics` is a `cfg(target_os = "macos")` dependency).
- `bundle.targets` is `["dmg"]`.

A green ubuntu/windows leg would have to be a `cargo check` of a subset the
product never ships. That is a maintenance cost with no signal, so the honest
answer for a macOS-only desktop app is: no non-mac leg at all. The finding's
requirement — *a plain `cargo check` on a non-mac host must not explode* — is
met by construction: CI no longer runs anything on a non-mac host, and (see
below) nothing in the source aborts a build by architecture any more.

Also added, both fail-fast before the long cargo steps:

- **`Assert macOS arm64 runner`** — `uname -s`/`uname -m` must be `Darwin`/`arm64`.
  `macos-latest` is Apple Silicon today; if GitHub ever repoints that label at an
  Intel image, this fails loudly instead of quietly producing an x86_64 build.
- Cache keys de-matrixed (`macos-arm64-cargo-*`, `macos-arm64-sccache`) and the
  bogus Windows sccache path (`"%LOCALAPPDATA%\sccache"`, which was a literal
  string, never expanded) replaced with the macOS cache dir.

### Scope expansion: `src-tauri/src/lib.rs` reverted to base

An earlier commit on this branch (`03dd8c9`) added:

```rust
#[cfg(feature = "local-runner")]
#[cfg(not(target_arch = "aarch64"))]
compile_error!("feature 'local-runner' is arm64-only: ...");
```

I removed it. Reasons, all checked rather than assumed:

1. **It makes the branch unbuildable on this project's own machine.** The Rust
   toolchain here is Homebrew's, host `x86_64-apple-darwin` (`rustc -vV`), with
   no rustup and no aarch64 `std` installed. So on this box:
   - `cargo check --lib` → the `compile_error!` fires (`local-runner` is a
     *default* feature).
   - `cargo check --lib --target aarch64-apple-darwin` → `E0463`, can't find
     crate `core`.

   i.e. with the guard in place, neither native nor cross build works locally.
   After the revert, `cargo check --lib` and `cargo test --lib` both pass (real
   output below). Merging the guard would have broken local `cargo test` for
   every other packet in the campaign.
2. **It duplicates a gate that now exists in the right place.** CI asserts an
   arm64 runner, builds `--target aarch64-apple-darwin`, and verifies every
   vendored binary is arm64-only. Those run on every push/PR.
3. It directly contradicts the finding's own requirement that a plain
   `cargo check` must not explode.

**Correction to an earlier claim of mine in this session:** I first thought the
two stacked `#[cfg]` attributes were the bug (that rustc applies only the first
one on a macro invocation). That is **wrong**. I tested it with the local
compiler — `#[cfg(unix)] #[cfg(target_arch = "aarch64")] compile_error!(...)`
compiles clean on this x86_64 host, so both attributes are applied and ANDed.
The guard was written correctly; it was simply firing because the host toolchain
really is x86_64.

`tauri.conf.json`'s `"targets": "all"` → `["dmg"]` from `03dd8c9` is left in
place. It is consistent with a macOS-only app. **I did not run
`npm run tauri build`, so the DMG bundle is unverified.**

## H-10 — the README's minimum macOS was wrong. It is now correct, and gated.

**This finding is NOT fully resolved and I am not claiming it is.** The binaries
still declare macOS 26. What changed is that the README no longer lies about it,
and CI will now catch the two drifting apart.

### (0) Verification — measured, not assumed

```
$ cd src-tauri/vendor/llama-cpp/macos-arm64
$ for f in llama-server *.dylib; do printf '%s: ' "$f"; \
    otool -l "$f" | grep -A4 LC_BUILD_VERSION | grep -E 'minos|sdk|platform' | tr '\n' ' '; echo; done
llama-server:              platform 1  minos 26.0  sdk 26.5
libggml-base.0.dylib:      platform 1  minos 26.0  sdk 26.5
libggml-blas.0.dylib:      platform 1  minos 26.0  sdk 26.5
libggml-cpu.0.dylib:       platform 1  minos 26.0  sdk 26.5
libggml-metal.0.dylib:     platform 1  minos 26.0  sdk 26.5
libggml-rpc.0.dylib:       platform 1  minos 26.0  sdk 26.5
libggml.0.dylib:           platform 1  minos 26.0  sdk 26.5
libllama-common.0.dylib:   platform 1  minos 26.0  sdk 26.5
libllama-server-impl.dylib:platform 1  minos 26.0  sdk 26.5
libllama.0.dylib:          platform 1  minos 26.0  sdk 26.5
libmtmd.0.dylib:           platform 1  minos 26.0  sdk 26.5
```

All 11 files: `platform 1` (macOS), `minos 26.0`, `sdk 26.5`, and
`lipo -archs` returns `arm64` for each. Vendored llama.cpp build is `b10088`.
`minos 26.0` means **macOS 26**, not macOS 15 — the previous README (and the
previous version of this note) mis-stated it as "macOS 15 (Sequoia)".

### (a) README fixed

The support matrix now says **macOS 26 (Tahoe) or later** and carries a
machine-readable marker `<!-- MIN_MACOS=26.0 -->`. A new "Why the minimum is
macOS 26" section shows the `otool` output, states that the floor comes from the
vendored runtime alone, and says plainly that lowering it requires a rebuild
rather than a doc edit. The old dead anchor link (`#needs-human-decision`,
which pointed at nothing in the README) is gone.

### (b) CI gate added

New step **"Vendored runtime matches documented minimum macOS"**, placed before
the toolchain install so it fails fast. It:

1. reads `MIN_MACOS=<x.y>` out of `README.md` (hard-fails if the marker is missing);
2. for each `*.dylib` and `llama-server` under
   `src-tauri/vendor/llama-cpp/macos-arm64/`, extracts the `LC_BUILD_VERSION`
   `minos` via `otool -l` and compares it to the README value;
3. asserts `lipo -archs` is exactly `arm64`;
4. hard-fails if the directory contains no Mach-O files at all (so deleting the
   vendor tree cannot silently pass the gate).

So re-vendoring llama.cpp at a different deployment target forces a matching
README edit, in the same PR, or CI goes red.

### 1. Rebuild the vendored llama.cpp against an older deployment target — the real H-10 fix

Right now the shipped app cannot claim to run on anything below macOS 26,
because the vendored runtime says so. Everything I did is documentation + a
drift alarm; the binaries are untouched (deliberately — the packet said not to
edit them). To actually lower the floor, rebuild llama.cpp `b10088` (match the
version in `src-tauri/vendor/llama-cpp/VERSION`) on an arm64 Mac with an SDK
that supports the desired target:

```sh
# pick the floor you actually want to support, e.g. 15.0
export MIN=15.0

git clone https://github.com/ggml-org/llama.cpp
cd llama.cpp
git checkout b10088                       # must match src-tauri/vendor/llama-cpp/VERSION

cmake -B build -DCMAKE_BUILD_TYPE=Release \
      -DCMAKE_OSX_DEPLOYMENT_TARGET="$MIN" \
      -DCMAKE_OSX_ARCHITECTURES=arm64 \
      -DGGML_METAL=ON -DLLAMA_BUILD_SERVER=ON -DBUILD_SHARED_LIBS=ON
cmake --build build --config Release -j

# confirm the new floor before copying anything in
otool -l build/bin/llama-server | grep -A3 LC_BUILD_VERSION   # expect: minos 15.0

# re-vendor
V="$REPO/src-tauri/vendor/llama-cpp/macos-arm64"
cp build/bin/llama-server "$V"/
cp build/bin/*.dylib      "$V"/

# regenerate the manifest the runner verifies at boot
cd "$V" && shasum -a 256 LICENSE *.dylib llama-server > ../MANIFEST.sha256

# update the README marker to match, or CI will fail (that is the point)
#   <!-- MIN_MACOS=15.0 -->  and the "macOS 26 (Tahoe)" wording
```

Then re-run `cargo test --lib runner` — `vendored_sidecar_matches_its_manifest`
checks the manifest — and smoke-test the built `.app` on the oldest macOS you
intend to support. `MANIFEST.sha256` currently hashes 12 entries (LICENSE + 10
dylibs + `llama-server`); keep that shape.

**Open question for you:** what floor do you actually want — macOS 15 (Sequoia),
or 14? That decision drives the SDK/Xcode version needed for the rebuild, and I
should not pick it.
