## 1. The regression: empty profile (M-03)

`ensure_valid_profile` rejected `""` and `profile_workspace_path` handed back
`base/__invalid_profile__` — 19 of 32 fs tests broken, and a validation failure
turned into a real directory on disk.

Replaced both with **one** normalizer, `profile_scope() -> Result<ProfileScope>`:

- `""` → `SharedBase` (the documented default/scratch contract; `open_profile`
  also rejects `""`, so it can never alias a real profile)
- a valid name → `Subdir(lowercased)`, mirroring `validate_profile_name` +
  `open_profile`'s ASCII allowlist **and** its `to_ascii_lowercase` fold
  byte-for-byte (the fold is load-bearing: on APFS `Work` and `work` are one
  inode, so one profile must be one DB and one tree)
- anything else → `Err`. **No sentinel directory, no silent fall back.**

Two thin views over it: `profile_workspace_root()` (fail-closed `Result`, used by
all six tools) and `profile_workspace_path()` (infallible peek, signature
unchanged, for the `ProtectedPathHook` resolve / legacy migration / read-only Files
IPC — each documented at the fn as safe with a base fallback).

`profile_workspace_path`'s public signature is unchanged, so the external callers
(`tools/exec.rs`, `hooks/protected_path.rs`, `ipc/mod.rs`, and the
dispatch/contract tests) needed no edit.

Also replaced the stale `profile_workspace_path_is_traversal_safe` test: it
asserted `"my work"`/`"café"`/`" work"` each get a verbatim subdir, a contract that
died when `validate_profile_name` was tightened to a strict allowlist.

## 2. Descriptor-relative traversal (M-04)

Check-then-use on a pathname is two independent resolutions of one string. The new
`confined` module opens the workspace root once and walks `rel` one component at a
time with `openat(2) | O_NOFOLLOW | O_CLOEXEC`; the final operation is
`openat`/`renameat`/`unlinkat`/`fstatat` **relative to the pinned parent
descriptor**. All six tools go through `Target`/`DirTarget`, which are backed by
the walk on unix and fall back to the previous canonical-pathname resolution on
platforms without `openat`.

- `read_file` → `openat` off the pinned parent
- `list_dir` → `fdopendir` on the pinned directory
- `search_files` → the recursive walk carries a pinned `DirTarget` per level
- `write_file` → one `fstatat(AT_SYMLINK_NOFOLLOW)` answers is-a-dir /
  is-a-symlink / did-it-exist, then temp-create + `renameat` **within the same
  pinned parent**
- `edit_file` → read-modify-write on ONE `Target` inside one `spawn_blocking`, so
  the content matched against is by construction the content replaced
- `delete_file` → `unlinkat`

`O_CLOEXEC` is on every descriptor deliberately: a `shell_exec` subprocess
inheriting a live handle to a workspace directory would itself be an escape hatch.

The workspace **root** is still opened by pathname and *does* follow symlinks, on
purpose: on macOS `env::temp_dir()` is under `/var` → `/private/var`, and a user's
storage root may legitimately sit behind a link. Nothing below the root is ever
followed.

Canonical pathnames survive in exactly one role — the opaque read-before-write set
key, which must carry the on-disk casing or a genuine read→write of one file is
falsely refused on a case-insensitive filesystem. That is why
`resolve_within{,_new}` are still called in read/write/edit: they supply the
lexical `..`/absolute rejection, the parent-containment check, and that key. They
no longer decide where a byte lands.

### Two real bugs found while doing it

1. **`openat` is variadic and the `O_CREAT` temp-file open passed no mode.** The
   kernel read a garbage variadic slot, so every written file got arbitrary
   permissions — locally unreadable, which surfaced as 8 tests failing with EACCES
   the moment `write_file` started using the new path. `openat` now takes
   `Option<mode>` with a `debug_assert` tying it to `O_CREAT`.
2. **`delete_file` deleted the wrong file.** It canonicalized first, so deleting a
   symlink followed it and removed the link's *target*, leaving the link dangling.
   `unlinkat` removes exactly the named entry. Test 3 below covers it.

Plus one latent trap closed in step 5b: `read_dir` hands `fdopendir` a `dup`, and a
`dup` shares the file offset, so a second listing off the same `DirTarget` would
silently return an EMPTY directory. `rewinddir` makes it idempotent.

## 4. `block_in_place` → `spawn_blocking` (M-21)

> **DEVIATION FROM THE PACKET, READ THIS.** The packet said "in
> `platform/macos/mod.rs`, swap `block_in_place` → `spawn_blocking`". That swap was
> **not carried out literally**, because it is not compilable in that file:
> `spawn_blocking` returns a `JoinHandle` that must be `.await`ed, and `osascript`
> is called only from synchronous trait methods (`ComputerBackend::ui_tree` /
> `resolve` / `synthesize`, `computer_backend.rs:75-89`) — one of which is reached
> from `GatingHook::on_event`, also synchronous (`hooks/mod.rs:386`). `osascript`
> therefore still calls `block_in_place`, now **flavour-gated**, and the actual
> off-load onto the blocking pool was placed at the nearest async seam,
> `computer_tools::act`. A reviewer who greps for `block_in_place` in
> `macos/mod.rs` will find it and should read this section before calling it unfixed.
> Net effect still satisfies M-21 (the `ui_*` tool path no longer blocks a runtime
> worker) and additionally removes a panic the literal reading would have kept.

The previous cut's `block_in_place` around `osascript` had a real defect worth
recording: on a current-thread runtime or in a `LocalSet`, tokio makes
`block_in_place` **panic** ("can call blocking only when running on the
multi-threaded runtime"), so a UI action there crashed the thread instead of
clicking a button. (Verified against the tokio 1.52.3 source: `worker.rs`'s
`block_in_place` returns that error for
`EnterRuntime::Entered { allow_block_in_place: false }`.)

Since the swap cannot happen inside `osascript` (see the scope note), the
`spawn_blocking` went to `computer_tools::act` and now covers the **whole**
blocking sequence rather than just the subprocess: `resolve` + `synthesize`, i.e.
the osascript calls, the Quartz event posts, and the three 20 ms `thread::sleep`s
in `drag`. Keeping it as one task also keeps the fresh re-resolve and the actuation
on the same thread and adjacent in time, which is the point of re-resolving
immediately before acting.

`osascript` itself is now flavour-gated: `block_in_place` only on a multi-thread
runtime (where it correctly hands this worker's core to a sibling before blocking),
a plain call otherwise. That keeps the synchronous hook path from stalling a worker
without the panic.

Also moved to `tokio::fs` + `spawn_blocking` in `fs.rs`: `read_file`, `list_dir`,
and the entire `search_files` tree walk.

Detail on the two that matter most:

**The symlink swap** is staged *deterministically* rather than raced: pin the
target (the "check"), replace the parent with a symlink to a directory outside the
workspace, then use the pinned descriptor. Critically the test **first proves the
window is real** by writing a decoy through the same pathname and asserting it
lands outside — without that the assertion could not fail and would prove nothing.

I wrote the threaded version first (a swapper loop racing `write_file.run`) and
measured it: it does catch a pathname-write regression, but **only
probabilistically** — 400 iterations missed it entirely, and ~20 000 iterations /
2–4 s were needed to catch it 3 out of 3 runs. I dropped it rather than ship a slow
partial detector, since the staged version tests the same property instantly and
always.

**Invalid-profile handling** is covered by
`an_invalid_profile_is_refused_by_every_tool_and_never_becomes_a_path` (step 1):
for each of five rejected names, all six tools must error with "invalid profile
name", nothing may be written at the shared base, no `__invalid_profile__` sentinel
may appear, `hello.txt` must be neither edited nor deleted, and no stray top-level
entry may exist afterwards. Mutations M2 and M6 above are its proof of teeth.

The three `osascript` tests run an inert `return "ok"` script — no
`tell application`, so no Accessibility or Automation grant and no consent dialog.

## Deliberate behaviour changes (reviewer: these are intentional)

1. **New files are created `0o600`** (umask applies) instead of
   `std::fs::write`'s `0o666`&umask = `0o644`. A rewrite via `renameat` replaces
   permissions, so an `edit_file` of a `0o644` file now yields `0o600`. Same user,
   so nothing in-process is affected; agent workspace files simply stop being
   world-readable. Flag it if you want `0o666` for exact parity.
2. **`edit_file` now caps its read at `MAX_READ_BYTES` (1 MiB)**, where it was
   previously unbounded. Rationale: a file the model cannot `read_file` in full is
   one it cannot edit safely, and the read-before-write guard already made >1 MiB
   files non-editable whenever a read-set is wired. Only reachable difference: an
   `edit_file` on a >1 MiB file with `reads: None` used to work and now errors.
3. **An intermediate symlink is refused even when it points inside the
   workspace.** This is the price of the pinned walk — "it resolved inside a moment
   ago" is not a fact that survives to the `open()`. `write_file` already refused a
   symlink *leaf*; this extends the same rule to every component.
4. **`delete_file` unlinks the named symlink** instead of following it to its
   target (bug fix, see §2).
5. **Module doc corrected (L-06)**: the old "TOCTOU mitigations" section described
   `fcntl(F_GETPATH)` verification and admitted an unclosed intermediate-symlink
   window; it now describes the walk that actually exists. Also corrected the claim
   that all three write tools enforce read-before-write — `delete_file` does not
   (it is gated by approval like the others).
