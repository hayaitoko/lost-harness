## Refutation 1 — a configured proxy totally bypassed the pin

**Confirmed, and it was the important one.** `build_pinned_client` never called
`.no_proxy()`. reqwest reads `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY` at
`Client::build()` time; with any of them set the socket goes to the **proxy**,
which resolves the target hostname *itself* at connect time. The vetted address
then receives nothing and the DNS-rebind TOCTOU the packet exists to close is wide
open — `.resolve_to_addrs()` becomes decorative.

`build_pinned_client` now ends in `.no_proxy()`. Order matters: reqwest's
`no_proxy()` **clears** the proxy list, so it must come after any `.proxy(..)`.

### Disclosed trade: MCP HTTP traffic no longer honours a configured proxy

This is deliberate, not incidental. A guard whose entire purpose is *choosing the
destination address* cannot permit an intermediary that re-resolves the name. If
Lukas is behind a corporate egress proxy, remote MCP servers will stop being
reachable, and the only correct fix is to pin at the proxy layer (a `CONNECT`
target the proxy is told not to re-resolve), not to re-enable proxying here.
Surveyed with grep: **nothing else in the crate configures a proxy**, so this
introduces no inconsistency with an existing app-level proxy feature — there is
none. `fetch.rs` (P07) carries its own fix on `review-fixes/integration`.

### The test seam, disclosed

`build_pinned_client` gained a third parameter, `proxy: Option<reqwest::Proxy>`,
which is `None` at its **single production call site** (`pinned_client_for`). It
exists so the regression test can hand a proxy to the *real* builder. Without
that seam the test would have to construct its own client, and the mutation that
deletes `.no_proxy()` from production would **survive** — which is exactly the
failure mode that got this packet refuted. Per the reviewer's instruction the test
uses an explicit `.proxy(..)` rather than mutating `HTTP_PROXY`, because env is
process-global and these tests run in parallel.

## Refutation 2 — the undisclosed redirect-query regression

**Confirmed.** `check_hop_transition` ran the full `validate_endpoint`, which
rejects any URL with a query. At base `eb17b94` there was no
`.redirect(Policy::none())`, so reqwest followed such redirects automatically and
this worked. A real MCP server that 307s onto a session-bearing URL therefore
began failing **every** RPC with no recovery route.

**Decision: allow a query string on a server-issued redirect target; keep refusing
it on a user-configured endpoint.** The rules are now split:

- `validate_url_shape` — the rules that hold for *every* destination: no
  credentials, no fragment, HTTPS unless the host is loopback.
- `validate_endpoint` (user-CONFIGURED) — adds the no-query rule. Rationale
  retained and narrowed: a query on a hand-entered endpoint is far more likely a
  pasted secret that would be **persisted** in the registration store and echoed
  into logs.
- `validate_redirect_target` (server-ISSUED) — shape only. A redirect target is a
  transient local variable; it is never persisted, so that rationale does not apply.

Nothing else is relaxed: the scheme rule (no HTTPS→plain-HTTP hop), the
credential/fragment rule, per-hop address vetting, the hop limit and the
never-forward-the-session-header rule all still apply to redirect targets.

Considered and rejected as a new hole: a malicious server could already redirect
to any URL it liked before this change, so permitting a query adds no exfiltration
channel it did not already have.

## Refutation 3 — the hop gate's call site was unprotected

**Confirmed.** The pre-existing downgrade test (`mcp_http.rs:776`) only exercises
the `check_hop_transition` helper, never its wiring into `post()`. Added
`the_production_redirect_path_enforces_the_hop_gate`, which drives the real
`post()` redirect loop: server A 307s to a **credentialed** URL on server B. That
target is otherwise perfectly reachable — loopback, plain HTTP, permitted address —
and B answers a well-formed JSON-RPC result for that exact request id, so if the
gate's `Result` is ignored the RPC **succeeds**. The test asserts the refusal *and*
that B received zero connections.

## Dead code — deleted, not annotated

`is_private_destination` was `pub` + `#[allow(dead_code)]` with no in-crate caller.
**Deleted.** Its two assertions were retargeted at `vet_hop`, the predicate the
live path actually uses (both inputs are IP literals, so `resolve_addrs`
short-circuits DNS and the assertions touch no network). Confirmed by grep that no
reference to the symbol remains anywhere in `src-tauri/src` or `src`.

## Behaviour changes — all disclosed

Carried over from the earlier commits (unchanged, still true):

1. **The block-list widened** from `{v4 private, loopback, unspecified}` ∪ `{v6
   loopback, unspecified, ULA}` to `fetch_url`'s full non-public set, so link-local
   (**including the `169.254.169.254` cloud-metadata endpoint**), CGNAT `100.64/10`,
   broadcast, documentation, multicast/reserved and IPv6 link-local are refused too.
2. **A private-but-non-loopback endpoint no longer connects** — `https://10.0.0.5/mcp`,
   `https://nas.local/mcp` fail at hop 0. → see "Needs a human decision".
3. **A DNS lookup now happens on every POST**, not only on redirects, because the pin
   must come from a fresh resolution. Mitigated by the pinned-client cache; not benchmarked.

New in this commit:

4. **MCP HTTP traffic ignores `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY`.** Deliberate;
   see Refutation 1 for the full trade.
5. **A redirect target may now carry a query string** — this is a *widening* that
   restores base-commit behaviour and fixes the regression in Refutation 2. A
   user-configured endpoint is unaffected and still refuses a query.
6. **`build_pinned_client` gained a `proxy` parameter**, `None` in production. A
   test seam, disclosed above. `validate_endpoint` (the `pub` API) is unchanged;
   `validate_url_shape` and `validate_redirect_target` are private.

### Not tested / limits of what I verified

- **No TLS anywhere in these tests.** The test servers are plain HTTP on loopback.
  The HTTPS→HTTP downgrade rule is proven at the helper level and its *call site*
  is now proven via the credentialed-target test, but not over a live TLS hop.
- **The proxy test uses an explicit `.proxy(..)`, not the env vars.** It exercises
  the same reqwest code path the env vars feed into, but I did **not** verify with
  `HTTP_PROXY` actually set, deliberately — env is process-global and would race
  the other tests. So "reqwest reads the env at `build()` time" remains the
  reviewer's finding plus reqwest's documented behaviour, not something I
  re-observed here.
- **The proxy sink is never actually exercised as a proxy.** It only counts
  connections; it does not speak the HTTP proxy protocol. That is sufficient for
  "zero connections" but means the test would not catch a *partially* working proxy.
- **The rebind test cannot use a real rebinding resolver.** It proves the pin
  determines the destination and that DNS is never consulted; it does not simulate
  an authority flipping its answer mid-flight.
- **The pinned-client cache is not directly unit-tested** — reqwest exposes no
  client identity to assert on and the test server closes each connection, so pool
  reuse is unobservable.
- **`connect()` against a real remote MCP server was not exercised** — none available.
- The extra per-POST DNS lookup was **not** benchmarked.
