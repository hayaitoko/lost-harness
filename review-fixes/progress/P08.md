## Finding

**H-07 — MCP stdio sandbox & consent.** `StdioMcpTransport::spawn` runs a
registered MCP server command as a child of the app. Two problems:

1. **No re-attestation of the binary.** Registration was the only moment a human
   looked at the command. After that the server auto-starts silently on every
   app boot (`lib.rs`'s background bring-up loop). Anything that could rewrite
   the file at `~/.local/bin/whatever` — a compromised npm postinstall, another
   app's updater, the agent itself via a write tool — inherited that consent
   permanently and got arbitrary code execution at next launch.
2. **Consent lived entirely in the renderer.** The install gate was a two-click
   confirm in `Settings.svelte`. A renderer-side compromise (XSS in rendered
   content, a malicious skill that can reach `invoke`) could call
   `invoke("register_mcp_server", …)` directly and install a server with no
   human in the loop at all.

## What the review caught, and what changed because of it

The first commit (`7b11447`) hashed only `args.command` and stored `args.args`
unverified. **That was the wrong unit of consent.** The dominant real-world MCP
registration shape is `npx -y @scope/server`, `node /path/server.js`, `uvx …`,
`python -m foo` — in every one of those the executable is a generic
**interpreter**, so pinning it pinned nothing that mattered and the actual
server code stayed freely swappable through argv. The headline
compromised-postinstall scenario the original commit message led with was
therefore still open. Fixed in `0b475d1`.

### 1. Invocation pinning (gap (a))

`src-tauri/src/tools/mcp_stdio.rs`

- `resolve_executable(command)` — resolves a bare command name by walking
  `PATH` (`std::env::split_paths` + an exec-bit check on unix), or treats a
  command containing a separator as a path, then `canonicalize`s it. This walks
  the *same* `PATH` the child inherits (`spawn`'s env allowlist), so resolution
  and execution agree. Deliberately not `which(1)`: no subprocess in a
  security-critical path.
- `sha256_of_file(path)` — chunked (64 KiB) SHA-256, so a large server binary
  is never slurped into memory.
- **`invocation_pin_digest(executable, args)` (new in `0b475d1`) — the pin is a
  digest over the WHOLE invocation:**
  - domain tag `lhp-mcp-invocation-pin-v1`;
  - the executable's canonical path **and its file contents**;
  - `argc`, then every arg **verbatim**;
  - for each arg that is an **absolute** path to an existing regular file
    (`node /opt/srv/server.js`), that file's canonical path **and contents**.

  Every field is length-prefixed (`label:len:value`), so argv cannot be
  re-split (`["ab","c"]` ⇄ `["a","bc"]`, `--flag=x` ⇄ `--flag` `=x`) without
  changing the digest.
- `resolve_arg_file(arg)` — the conservative arg→file resolver: skips flags
  (`-y`), package specs (`@scope/pkg`), module names, and **relative** paths.
  Relative paths are excluded on purpose: canonicalizing them depends on the
  app's cwd, which would make the digest unstable. Those args are still covered
  verbatim as argv; only their *content* is unmeasured.
- `resolve_and_hash_executable(command, args)` — the registration-time pin.
- `verify_pinned_executable(command, args, pinned_path, pinned_hash)` — the
  bring-up-time check. Fails **closed** on: path moved, invocation digest
  changed (binary contents, argv, or a script file argv names), or **no pin at
  all**.
- `bring_up_server` calls it with **`&row.args`** — literally the argv handed to
  `StdioMcpTransport::spawn` two lines below — in the stdio branch only (HTTP
  endpoints have no local binary). Because that function is exactly what
  `lib.rs`'s boot loop calls, the unattended auto-start path is covered.

`src-tauri/src/ipc/mod.rs` — registration pins `(command.trim(), &args.args)`.

Storage (`storage/global.rs`, `migrations.rs`, `schema.rs`):

- `McpServerRow` gains `executable_path: Option<String>` and
  `executable_hash: Option<String>`; insert/list/get SQL updated.
- Migration **v9** `mcp_servers_executable_pinning` adds the two columns;
  `GLOBAL_SCHEMA_VERSION` 8 → 9.
- **Naming caveat, disclosed:** the column is still called `executable_hash`
  but now holds the *invocation* pin, not a bare file hash. Renaming it would
  have meant touching the same hot storage files a dozen more times for zero
  behavioural gain, so instead the field doc on `McpServerRow`, the v9 migration
  comment and the registration comment all state explicitly what the value is
  and point at `invocation_pin_digest`.

**Bug caught and fixed while re-deriving the original change.** The uncommitted
working copy added these columns to *both* migration v9's `ALTER TABLE` **and**
`GLOBAL_SCHEMA_SQL`'s `CREATE TABLE mcp_servers`. That would have broken every
**fresh install**: a new DB runs v1 (the `CREATE`) then v9 (the `ALTER`), and
`ALTER TABLE ADD COLUMN` has no `IF NOT EXISTS` → "duplicate column name" →
`Storage::open` fails at first launch. The columns now live only in the
migration, matching the convention v2 already documents for
`memory_facts.pinned`. `fresh_global_db_has_the_mcp_executable_pin_columns` is
the regression guard.

### 2. Install consent nonce (gap (b))

`src-tauri/src/ipc/mod.rs`, `lib.rs`

- `AppState.pending_mcp_nonces: Arc<Mutex<HashMap<String, Instant>>>`.
- New command `generate_mcp_install_nonce` → issues a UUID, TTL 5 min
  (`MCP_INSTALL_NONCE_TTL`), and opportunistically evicts expired entries so an
  abandoned install flow can't grow the map without bound.
- `RegisterMcpServerArgs.nonce: String` — **no `#[serde(default)]`**, so a
  payload that omits it fails to deserialize at the IPC boundary and never
  reaches the command body.
- `register_mcp_server` consumes the nonce **first**, before any validation,
  resolution, or spawn. Single-use (removed on consume, valid or not) and
  TTL-checked.

## NEEDS-LUKAS

### 1. Least-privilege sandboxing of the spawned MCP child — DEFERRED, NOT DONE

This is an **accepted, documented deferral**, stated plainly: **an MCP server
child process still runs with the full privileges of the Lost Harness app.**
Same user, same filesystem access, same network access. Nothing in this packet
confines it. The only thing that changed is *which* invocation is allowed to
reach that position — H-07's consent half is closed; the containment half is not.

What is actually in place today, for the record:
- environment allowlist (`PATH`/`HOME`/`TMPDIR`/`USER`/`LANG` only, `env_clear`
  otherwise) — the pre-existing mitigation, so provider keys don't leak into
  the child;
- the pinning added here;
- capability/tier gating on the *tools* the server exposes.

None of that is an OS jail. The integration point when this is picked up is
`tools/exec.rs`'s sandboxed-spawn path (Seatbelt on macOS); doing it properly
needs a decision about what a legitimate MCP server is allowed to touch, which
is a product question, not a mechanical one.

### 2. The nonce is a renderer-flow gate, not a hardware root of trust

Honest framing, because the finding title says "consent": a renderer that can
call `invoke` can also call `generate_mcp_install_nonce`. So the nonce **does**
stop the specific attack of a bare, replayed, or blind
`invoke("register_mcp_server", …)` — including anything that captured a valid
payload earlier — and it makes install a deliberate two-call backend
transaction. It does **not** stop a fully-scripted renderer compromise that
performs both calls in sequence.

Making that airtight requires the confirmation to be minted by something the
renderer cannot drive — a native OS dialog owned by the Rust side, with the
nonce issued only after the user clicks in *that* window. That is a real UX
decision (extra modal on every MCP install) and I did not make it unilaterally.

### 3. Existing MCP servers stop working after this upgrade

Rows registered before v9 have NULL pins, and `verify_pinned_executable` fails
closed on them. On first launch after this change, any already-registered MCP
server will refuse to start with:

> MCP server `x` has no pinned executable hash — it was registered before
> executable pinning existed. Remove and re-register it to approve its binary.

This is the deliberate fail-closed choice (we never measured those binaries, so
we cannot attest to them), and with a single user the blast radius is one
re-registration. Flagging it because it is a visible behaviour change, and
because the alternative — silently pinning whatever is on disk at first boot —
would launder an unverified binary into an "approved" state, which defeats the
finding.

### 4. Pinning an interpreter WILL produce operational false positives

This is the cost of the design and you should expect to hit it:

- **A toolchain upgrade breaks every stdio MCP server.** An nvm/volta/asdf
  version switch, a `brew upgrade node`, a `uv`/`python` bump — any of these
  changes either the resolved path (`.../versions/node/v22.4.0/bin/node` →
  `v22.5.0`) or the binary's hash. Either way the pin mismatches and the server
  **hard-fails at the next boot** with "its executable moved" / "changed since
  it was approved". Recovery is manual: remove and re-register.
- **A server package update does the same.** `node /opt/srv/server.js` pins
  `server.js` by content, so `npm update` inside that server invalidates it.
- **The failure is silent-ish.** It surfaces as an error on the server's
  bring-up at boot, not as a prompt. There is no "re-approve this" affordance in
  the UI today — only remove + re-register.
- **Not everything is actually pinned.** `npx -y @scope/server` and
  `python -m foo` fetch/resolve their code at run time; that code is not a local
  file we can measure at pin time, so for those the pin covers the interpreter
  and the argv **but not the server code itself**. Argv pinning still stops the
  registration from being mutated to point somewhere else, and stops interpreter
  swaps — but a malicious *registry* update to an `npx`-launched server is NOT
  caught by this packet. Only a locally-resolvable script/binary is
  content-attested.

If the false-positive rate is unacceptable, the product-level answer is a
re-approval prompt ("`node` changed — approve the new binary?") rather than
weakening the pin. That is a UX decision, not a mechanical one.

### 5. TOCTOU between hashing and `execvp`

`verify_pinned_executable` hashes the file, then `StdioMcpTransport::spawn`
hands the path to the OS. Anything with write access to that file in the window
between the two can substitute content that never gets measured. Closing it
properly means holding an fd across the check and exec (`fexecve`-style), which
`tokio::process::Command` does not expose. Unpatched, and cheap to exploit only
by an attacker who already has write access to the pinned file at the exact
moment of boot — but it is a real gap and should not be described as "the binary
is verified before execution" without this footnote.

## Not done / out of scope

- No change to `Settings.svelte`; the UI's existing two-click confirm is
  unchanged and still the only user-visible gate.
- Frontend typecheck (`npm run check`) could **not** be run — `node_modules` is
  not installed in this worktree (`svelte-check: command not found`). The
  TypeScript edit is 3 lines and mechanical, but it is **unverified**.
- HTTP (Streamable) MCP endpoints are unpinned by design — there is no local
  binary to hash. Endpoint-identity pinning (cert/host) is a separate question.
- The `executable_hash` **column name** was not renamed to match its new
  invocation-pin semantics (see the naming caveat above); only its
  documentation was corrected.
