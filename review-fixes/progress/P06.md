## What commit 2 actually changed

### 1. DNS-rebind TOCTOU (the REVISE item)

`vet_hop()` now **returns the `SocketAddr`s it vetted**, and the request goes out
through a client built with `.resolve_to_addrs(host, &vetted)` — the address that
passed the check is the address the socket connects to. This mirrors P07's verified
`fetch.rs` approach (already merged into `review-fixes/integration`), read directly
from that branch rather than reinvented.

Before: the hostname was classified, then the request went out on a client with
reqwest's own resolver, which performed a *second, independent* lookup at connect
time. A rebinding authority answers public on the first query and private on the
second, and the second answer never faced the gate.

The redirect branch no longer performs its own resolve either. It does only the
URL-level checks (`check_hop_transition`) and lets the next loop iteration's
`vet_hop` do the single resolve-classify-pin. **Exactly one resolution per hop, and
its result is what the connection uses.**

The pinned client is cached under its exact `(host_key, sorted addrs)` pin
(`pinned_client_for`), so ordinary RPC traffic still reuses a connection pool
instead of re-handshaking TLS per `tools/call`. A vet that yields different
addresses rebuilds the client, so a pooled connection never outlives the address it
was vetted against.

### 2. Hop 0 is vetted

Previously only redirect targets were address-checked, so a registered HTTPS
endpoint went out unchecked — `https://10.0.0.1/mcp`, `https://169.254.169.254/mcp`,
or any domain whose A record points inward, all passed. The vet now runs at the top
of every loop iteration, hop 0 included.

### 3. IPv4-mapped IPv6 unwrapped in both gates

- `is_loopback_host()` (the single definition of "local-dev endpoint", used by
  `validate_endpoint`) unwraps the IPv4-mapped `::ffff:a.b.c.d` and IPv4-compatible
  `::a.b.c.d` forms, so `::ffff:127.0.0.1` is recognised as loopback.
- The address gate `addr_permitted()` delegates to `fetch.rs`'s existing
  `pub(crate) is_blocked_ip`, which already decodes mapped, compatible, NAT64
  (`64:ff9b::/96`) and 6to4 (`2002::/16`) embeddings. `::ffff:10.0.0.1` no longer
  slips through as "not private".

I **delegated rather than duplicated** the block-list. Being explicit about that
because it is the honest description: the mapped-form decoding for the *private*
question lives in `fetch.rs` (unmodified), not in a second copy here. The only
local unwrapper, `mapped_ipv4()`, exists solely for the *loopback* question and
handles just the two low-32-bit forms.

M-01 (streaming body cap) and the session-header isolation from commit 1 are
unchanged in mechanism; they now have tests (they had none).

## Behaviour changes beyond the assigned findings — deliberate, disclosed

1. **The block-list widened.** It was `{v4 private, loopback, unspecified}` ∪
   `{v6 loopback, unspecified, ULA}`. It is now `fetch_url`'s full non-public set,
   so link-local (**including the `169.254.169.254` cloud-metadata endpoint**),
   CGNAT `100.64/10`, broadcast, documentation, multicast/reserved and IPv6
   link-local are refused too. The old list let the metadata endpoint through,
   which is the canonical SSRF target.

2. **A private-but-non-loopback endpoint no longer connects.**
   `https://10.0.0.5/mcp`, `https://nas.local/mcp`, `https://192.168.1.50/mcp` now
   fail at hop 0. That is the direct consequence of vetting hop 0, and it is a real
   functional narrowing for anyone running an MCP server on their LAN over HTTPS.
   Loopback endpoints still work — that is the local-dev case `validate_endpoint`
   already blesses, and it is carved out via the `allow_loopback` flag derived once
   from the *registered* endpoint. Even under that flag only **loopback** is
   permitted; RFC-1918, ULA, CGNAT and metadata stay blocked on every hop.
   → See "Needs a human decision".

3. **A DNS lookup now happens on every POST**, not only on redirects, because the
   pin has to come from a fresh resolution. Mitigated by the pinned-client cache
   (connection reuse survives), but it is one extra `lookup_host` per RPC — normally
   an OS-cache hit. I did not measure it.

4. `is_private_destination` is now `pub` + `#[allow(dead_code)]` and has **no
   in-crate caller**. Kept deliberately (the finding names it; it is the
   request-free form of the predicate and is test-covered) but the live path calls
   `vet_hop` instead — asking twice is precisely the TOCTOU this packet closed. The
   `allow` keeps the crate's warning count at its baseline 88.

## Tests — 7 new, all six required categories

A minimal HTTP/1.1 test server on `127.0.0.1` (`spawn_server`) lets five of these
drive the **real `post()` loop end to end** — a loopback endpoint is a valid MCP
endpoint — rather than testing a re-implementation. `from_validated()` was factored
out of `connect()` so a transport can be built without a handshake; `connect()` now
calls it, so the tested construction path is the shipping one.

| Category | Test |
|---|---|
| header-strip | `session_header_is_sent_on_hop_0_and_stripped_after_a_redirect` — live 307 → 200; asserts hop 0's request head **contains** the token and hop 1's does **not**, and that the redirect is still followed |
| downgrade | `https_to_http_downgrade_is_refused_as_its_own_rule` — unit test on `check_hop_transition`; the target is `http://127.0.0.1:3000/mcp`, which *passes* `validate_endpoint` on its own (asserted), so only the downgrade rule can refuse it |
| hop limit | `redirect_hop_limit_is_enforced` — live server that redirects forever; asserts the error **and** `heads().len() == MAX_REDIRECT_HOPS + 1`, pinning the exact bound |
| IPv4-mapped IPv6 | `ipv4_mapped_ipv6_is_unwrapped_in_both_gates` — `validate_endpoint` (mapped loopback OK over HTTP, mapped RFC-1918 not), `addr_permitted` under both policies, `is_private_destination`, and the live path refusing `https://[::ffff:10.0.0.1]/mcp` |
| oversized body | `oversized_response_body_is_refused_while_streaming` — a **well-formed** JSON-RPC response of `MAX_RESPONSE_BYTES + 1024` (well-formedness asserted), so without the cap it would parse and succeed |
| rebind by construction | `pinned_client_cannot_be_moved_by_a_second_dns_answer` — two live servers; asserts an unpinned client cannot reach the `.invalid` host at all, that `vet_hop` hands back exactly the vetted addr, that the pinned client lands on it and the un-vetted server is contacted **zero** times, and that only re-pinning moves the destination |
| (extra) hop 0 | `hop_zero_is_vetted_not_only_redirects` — 4 private endpoints that all pass `validate_endpoint` (asserted) and must still be refused before a socket opens |

### Mutation-tested — every test verified falsifiable

Each mutation was applied, run, and reverted. Each killed the intended test and
only the intended test:

| Mutation | Result |
|---|---|
| `if hop == 0` → `if true` (session header on every hop) | header-strip test FAILED |
| downgrade condition short-circuited to `false` | downgrade test FAILED |
| `hop >= MAX_REDIRECT_HOPS` → `>= MAX_REDIRECT_HOPS + 1` | hop-limit test FAILED (7 requests, not 6) |
| hop 0 resolved but not classified (the pre-fix behaviour) | hop-0 **and** mapped-IPv6 tests FAILED |
| mapped-IPv4 unwrap removed from `ip_is_loopback` | mapped-IPv6 test FAILED |
| streaming cap condition → `false` | oversized-body test FAILED |
| `.resolve_to_addrs(host, addrs)` removed from `build_pinned_client` | rebind test FAILED |

One earlier mutation attempt (`allow_loopback \|\| hop == 0`) did **not** fail any
test — correctly, because it only widens hop 0 to *loopback*, which no test claims
is refused. I replaced it with the accurate "hop 0 unclassified" mutation above.

### Not tested / limits of what I verified

- **No TLS anywhere in these tests.** The test server is plain HTTP on loopback, so
  the HTTPS→HTTP downgrade rule is proven at the `check_hop_transition` unit level,
  not over a live TLS hop. `post()` calling that helper is structural (visible in
  the diff) and is exercised by the live redirect tests.
- **The rebind test cannot use a real rebinding resolver.** It proves the pin is
  what determines the destination and that DNS is never consulted (the `.invalid`
  host has no answer). It does not simulate an authority flipping its answer
  mid-flight; no such simulation is reachable without a custom resolver harness.
- **The pinned-client cache is not directly unit-tested** — reqwest exposes no
  client identity to assert on, and the test server closes each connection, so pool
  reuse is unobservable there. Its correctness rests on a byte-equality comparison
  of `(host_key, sorted addrs)`; the live tests exercise the code path (cache miss
  then hit across hops) but do not assert on reuse.
- **The extra per-POST DNS lookup was not benchmarked.**
- `connect()`'s handshake against a real remote MCP server was not exercised — no
  remote server available in this worktree.
