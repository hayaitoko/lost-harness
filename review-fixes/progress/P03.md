## H-04 — port-race impersonation

`pick_free_port()` drops its probe listener before the spawn, and the health check accepted any HTTP
2xx on `/v1/models`, so a local process holding that port could be registered as the **private**
provider and receive private prompts.

Now every spawn mints a fresh 128-bit token (`new_spawn_token`, uuid v4 hex):

1. `build_args` passes it to llama-server as `--api-key` and also keeps it on
   `SidecarCommand.api_key`.
2. `HealthCheck::is_healthy` takes the token. `HttpHealthCheck` requires: an **anonymous** request to
   a protected endpoint is refused → the **same** endpoint accepts our token → `/v1/models` returns
   2xx with a `data` array (a generic 2xx is no longer enough).
3. **`ensure_running` attaches the same token to the registered `Provider`.** `ModelClient` already
   sends `bearer_auth` when `api_key` is `Some`, so every later request is authenticated. This is the
   defect that sank the first attempt and it has its own test
   (`the_registered_provider_carries_the_same_token_the_sidecar_was_started_with`), verified by
   mutation (register with `None` → that test fails).

`SidecarCommand` has a hand-written `Debug` that redacts the token (field and the argv value after
`--api-key`), because argv can reach log lines.

### The correction that mattered (commit `1da9aa2`)

The first version of this rebuild probed `/v1/models` unauthenticated and required a refusal. I ran
the **real vendored binary** (`b10088`, router mode with an empty `--models-dir`, which needs no GGUF)
and measured:

```
/health, /v1/health, /models, /v1/models      → 200 UNAUTHENTICATED (exempt from --api-key)
/props, /tokenize, /detokenize, /slots,
/apply-template, /v1/embeddings,
/v1/chat/completions                          → 401 anonymous, 401 wrong key, 200 with our key
```

`/v1/models` is a **public** endpoint. Requiring it to refuse anonymous callers would have refused
**every legitimate sidecar** — local models would never have started. The identity probe is therefore
`GET {root}/props` (root = `base_url` minus the `/v1` suffix). `the_vendored_sidecar_enforces_the_api
_key_on_props_but_not_on_models` pins both halves against the real binary in the normal (non-gated)
test run, so a re-vendor that changes the auth surface fails a test instead of silently breaking
startup.

### Residual, not closed

- **Adaptive attacker.** Someone holding the port can refuse the anonymous probe, read the token out
  of the authenticated probe, and then answer the readiness check. Closing this needs a
  challenge-response llama-server does not offer. What *is* closed is the realistic case: a process
  already serving an OpenAI-compatible endpoint on the port we were handed. Documented in the
  `is_healthy` doc comment.
- **Token in argv.** `--api-key <token>` is visible to same-uid processes via `ps`. On macOS other
  users cannot read another user's argv, and a same-uid attacker can read our environment too, so
  the env form is not strictly better — but the binary does accept `LLAMA_API_KEY` (confirmed in
  `--help`), so switching is available as future hardening. I followed the packet's literal
  `--api-key` instruction.
- A tokenless start (tests only; `ensure_running` always issues one) degrades to readiness-only.
  Asserted explicitly rather than left to be discovered.

## L-02 — stderr went to /dev/null

`TokioSpawner` now pipes stderr into `StderrTail`: a ring bounded on both axes (40 lines, 400 chars
per line, 2000-char snapshot), drained by a background reader task — mandatory once stderr is piped,
since an unread pipe fills and then blocks the child. `redact_stderr_line` scrubs absolute paths and
≥32-char hex runs **on the way in**, so the buffer never holds the sensitive form. Both startup
failure paths (early exit, health timeout) append the tail, with a bounded (~100 ms, virtual under a
paused clock) wait so lines written just before the exit are not lost to the race.

Verified end-to-end with the REAL spawner: a `/bin/sh` "sidecar" that writes to stderr and exits 3
produces an error containing the message, containing `exited (code 3)`, and containing no absolute
path.

## M-11 — reaper identity

Identity was a suffix match on a 16-char-truncated `ps -o comm=`, and the recorded epoch was parsed
into `let _epoch` and discarded. Now the kernel answers both questions:

- `process_exe_path` → `libc::proc_pidpath`; the file name must be exactly `llama-server`.
- `process_start_epoch` → `libc::proc_pidinfo(PROC_PIDTBSDINFO).pbi_start_tvsec`; it must be within
  300 s of the epoch in the pidfile (`process_start_epoch_matches`).

Indeterminate ⇒ never kill. A legacy pidfile with no epoch field still falls back to the exe-path
check alone, so an upgrade does not leak the previous run's sidecar forever. The existing boot-id
guard is unchanged.

## M-10 — boot integrity was size-only

Boot stays cheap on purpose (hashing multi-GB models every launch is not acceptable), so the gap is
closed in the two places that matter:

- **First use, before launch.** `ensure_running` sha256-verifies the file before any spawn, once per
  app run (cached in `LocalRunnerSupervisor.hash_verified`, hashed on `spawn_blocking` so the UI's
  runtime keeps moving). A mismatch quarantines and refuses — a tampered GGUF is never executed and
  never becomes a provider.
- **On demand.** `verify_local_models_now(storage, only_id)` does the full re-hash for one model or
  all; the `verify_local_models` IPC command exposes it and clears the cached verification for
  anything it quarantines.

PID-reuse coverage is deliberately harsh: one test points a pidfile at a live PID whose executable is
not `llama-server` — **the test binary itself**, with a matching epoch and boot id — so a weakened
identity check would SIGKILL the test run. The other spawns a real binary actually named
`llama-server` (a copy of `/bin/sleep`): with a mismatched epoch it survives the reap, with the
recorded epoch it is reaped (exit status asserted non-success).

## How the two rejection causes were avoided

1. **No whole-tree reformat.** `rustfmt` was never run. `runner.rs` is not rustfmt-clean at base
   (`rustfmt --check` on the `eb17b94` copy reports 33 hunks), so running it would have produced
   exactly the churn that sank the first attempt; new code matches the surrounding style by hand.
   The diff is 2 files.
2. **The token is attached to the provider client**, not just to startup, with a dedicated
   mutation-verified test.

## Behaviour changes beyond the four findings (disclosed)

- **First local use of a model now hashes it.** On a multi-GB GGUF this adds real latency (seconds)
  to the first `ensure_running` of each app run — once per run per model, on a blocking thread. This
  is the intended cost of M-10's fail-closed check, but it is a user-visible change.
- **`Provider.api_key` is now `Some(..)` for bundled-runner providers.** Checked for fallout:
  `ModelManager::add_provider` is in-memory only (and drops the cached client, so the token takes
  effect), local-runner providers are never persisted to `endpoints`, `ProviderInfo` omits `api_key`
  (existing test `provider_info_omits_api_key`), and nothing outside `ipc`/`models::client` reads
  `.api_key`. Routing/privacy decisions use `base_url`, not credentials.
- **Public API signature changes** (all callers are in-file): `build_args` takes `api_key`,
  `HealthCheck::is_healthy` takes `api_key`, `SidecarCommand` gains a field and a manual `Debug`,
  `SpawnedProcess` gains a defaulted `stderr_tail`.
- **Test fixture**: `seeded_storage` used to record a placeholder sha256, which the new first-use
  check correctly rejects; it now records the real digest, with `seeded_storage_with_sha` for tamper
  fixtures.
- One new IPC command name (`verify_local_models`) enters the app's command surface.
