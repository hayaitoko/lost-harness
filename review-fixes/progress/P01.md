## Design decisions

### 1. Why `ConfirmRequired` instead of `Block`
The codebase already had this exact pattern at the audio boundary
(`AudioEgressDecision::ConfirmRequired` + `ApprovalLedger::take_once`). Adding a
third policy would have been a fork. The gate now speaks the same language, and
`PublicSendConfirmations` mirrors `take_once`'s atomic check-and-consume.

The grant is fingerprinted over the **exact text**
(`sha256("privacy_gate.public_send" ⊕ canonical {text})`), domain-separated from
tool-action fingerprints, so a tool approval can never be replayed as a
message-send confirmation and vice versa.

### 2. Expiry: single-use AND time-limited
`take()` removes the entry under the same lock that checks it (so two concurrent
identical sends cannot both consume one confirmation) and refuses an entry older
than the TTL (default 120 s; `grant()` also sweeps stale entries). A poisoned
mutex returns `false` — fail closed.

### 3. Item 6, the `HeuristicClassifier` empty-spans hole — **decision + why**
The first attempt gated on `classification.spans.iter().any(...)`. Per
`Classification::spans`' own doc, that vec is **empty by contract** for
`HeuristicClassifier` and the `EnsembleClassifier` stub — so the H-12 block was
vacuously false in exactly the fresh-install / no-models configuration the
finding is about.

**Decision: the floor is the RULES LAYER, not the active classifier.** `floor_hit`
calls `crate::classifier::rules::detect(text)` directly, which is a free function
independent of whichever `Classifier` is installed. It therefore fires identically
under the ensemble, the rules classifier, and the heuristic. This is also what
`AudioEgressGate::tts_egress` already does, so the two boundaries now agree.

Two deliberate consequences:
- `RuleCategory::Proprietary` (the "confidential" / "do not share" keyword cues)
  is **excluded** at the text boundary. Under an explicit `Public` binding,
  prompting on the mere word "confidential" would train the user to click through
  confirmations, which destroys the prompt's value. The stricter audio boundary
  keeps the cues. Tested: a classifier that screams `Private` about benign text
  does **not** manufacture a confirmation.
- The floor no longer depends on the classifier's label/confidence at all, so a
  classifier that is wrong in either direction cannot suppress it.

### 4. Degraded affects `Auto` only; `Public`/`Private` unchanged
`Private` already refuses cloud unconditionally. `Public` is an explicit user
opt-in and still gets the un-tunable floor. Degraded escalation is limited to
`Auto` + cloud (→ `RouteLocal`), where the gate would otherwise be trusting a
rules-only miss as evidence of cloud-safety. Degraded + **local** endpoint is
still `Allow` — fail-closed that bricks on-device use would just get switched off.

### 5. Tool path: `ConfirmRequired` → `Deny`, not `Ask` — **[SUPERSEDED by F2]**
This reasoning was wrong on its central claim. It said an `Ask` "would loop
forever because the grant lands on the tool's fingerprint, not the gate's text
fingerprint" — but the fix is simply to *look up the tool's fingerprint*, which
is what every other ask-capable hook already does. See "Remediation round 2 → F2".

# Remediation round 2 (commit 9d9df85)

The round-1 review confirmed all six REVISE items clean and all six new tests
provably live, then refuted the packet for introducing four reachable behavioural
regressions of its own. This is what I changed for each.

## F1 — the `Public` arm ignored `is_cloud_endpoint`

**Was:** `check_detailed`'s `Binding::Public` arm ran `floor_hit(text)` and asked
for a confirmation regardless of the endpoint, while `Auto` and `Private` both
consult `is_cloud_endpoint`. So
`check(&Public, "my SSN is 123-45-6789", is_cloud_endpoint=false, default cfg)`
returned `ConfirmRequired` for a send that never left the device — and on the tool
path (F2) that became a hard `Deny`.

**Intended behaviour, decided:** the gate governs EGRESS, so all three arms
consult the endpoint. `Public` + non-cloud is `Allow`, exactly as `Private` +
non-cloud is `Allow`. The classification is still computed and returned so the
redaction UI keeps working, and — deliberately — the cloud check runs BEFORE
`confirms.take()`, so a local send does not spend the confirmation the user
granted for the cloud send.

Tests: `public_binding_asks_for_a_confirm_only_when_something_actually_egresses`
(with a cloud control arm), `a_local_public_send_does_not_spend_an_outstanding_cloud_confirmation`,
and `a_public_bound_tool_call_to_a_local_endpoint_is_not_confirmed_at_all` on the
hook.

## F2 — the tool path hard-denied with no recovery route

**Was:** `GateDecision::ConfirmRequired` → `HookResult::Deny`. Round 1's
justification (see the superseded decision 5) was wrong.

How reachable this is, concretely: the hook's content is `dispatch_inner`'s
`format!("{} {}", call.name, call.args)`, and `rules::detect` flags **any** IPv4
literal (`RuleCategory::PiiContact`, unconditional), any e-mail address, and any
run of ≥9 digits. So `fetch_url {"url":"http://10.0.0.26:8000/status"}` under a
`Public` binding was an unrunnable call with nothing the user could do. The new
tests use exactly that fixture and assert the precondition (`rules::detect` is
non-empty) so they cannot pass vacuously.

**Fix:** `ConfirmRequired` → `HookResult::Ask(reason)`, satisfied from the
dispatcher's shared `ApprovalLedger` via
`covers_for(&ctx.tool_name, &ActionFingerprint::from_ctx(ctx), ctx.risk, ctx.attended)`.
That is the recovery route `ProtectedPathHook` / `PermissionHook` /
`FirstUseConfirmHook` already use: dispatcher prompts → records the answer →
re-runs the FULL chain → this hook sees the grant and continues.
`build_pretooluse_chain_full` threads the ledger into the hook (previously it went
only to the other three).

**Why `covers_for` and not `covers_once` — the honest tradeoff.** `covers_once`
would be the stricter floor (matching `ProtectedPathHook`), but it is not usable
here without a `dispatch.rs` change I am not in scope to make: the dispatcher
force-pins an extra `(Once, fingerprint)` grant only when `by == "protected_path"`,
so a user answering "allow for this session" to a privacy prompt would fail
`covers_once` on every re-run, burn all four `MAX_APPROVAL_ROUNDS`, and get
`Denied("too many confirmation rounds")` — a worse outcome than the bug. So:

- **Consequence, disclosed:** a standing grant the user deliberately recorded for
  this tool (e.g. "always allow `write_file`") now also satisfies the privacy
  confirm. Weaker than the message path's strictly-one-send store. Still strictly
  stronger than pre-H-12, which allowed every `Public`-bound tool call silently.
- `covers_for` (not `covers`) keeps B5: a `Session` grant for an `External` tool
  does **not** satisfy an unattended cron/delegate/headless replay. Tested, and
  mutation-killed.
- **Follow-up for Lukas / a later packet:** add `"privacy_filter"` to the forced-
  `Once` piggyback in `dispatch.rs`'s `Approve` arm (currently
  `if by == "protected_path" && scope != GrantScope::Once`), then tighten this
  hook to `covers_once`. That is a 1-line dispatch.rs edit plus a 1-word hook
  edit, and it makes the privacy floor Once-only like the protected-path floor.

**Second consequence, disclosed:** `PrivacyFilterHook` is FIRST in the chain,
ahead of the non-overridable `SandboxHook` denylist, and it can now `Ask`. The
module docs asserted the ordering rationale on the premise that the privacy hook
was "Deny-only, never-Ask", so I corrected them. **Nothing is bypassed** — an
approval makes the dispatcher re-run the whole chain from the top, where
`SandboxHook` denies exactly as before, and `Tool::run()` is only reached from a
`Continue` through every gate; the existing `sandbox_runs_before_any_hook_that_can_ask`
and `default_pretooluse_chain_is_in_spec_order` still pass unchanged. The real
consequence is cosmetic: a privacy prompt can now be raised for a call the sandbox
floor is going to refuse anyway. I did NOT reorder the chain (that would need
`hooks/tests.rs` edits and is a bigger behavioural change than the finding asked
for).

## F3 — the tool-hook gate had its own, unreachable confirmation store

**Was:** `PrivacyGate.confirms`' doc claimed the store is shared with the
tool-hook gate. False: `lib.rs` built that gate with `PrivacyGate::with_health`,
which allocates a fresh `PublicSendConfirmations`. A grant from
`ipc::confirm_public_send` could never be consumed there.

**Fix — structural, not a doc patch.** `clone()` is the only construction that
shares BOTH `health` and `confirms`, so there is now exactly ONE gate:
`build_tool_dispatcher`'s `classifier_health: Arc<ClassifierHealth>` parameter is
replaced by `gate: PrivacyGate`, and `run()` passes `gate.clone()` (it already
passed `gate.clone()` to `AppState`). The `confirms` and `with_health` docs now
state plainly that `with_health` starts an EMPTY store and that a second gate must
come from `clone()`. Both stale claims are gone.

Test: `a_confirmation_granted_on_the_message_gate_is_consumable_on_the_tool_path`
drives the REAL dispatcher — grant on the message gate, observe the tool path go
`Ask` → `Ok` → `Ask` (consumed exactly once).

**Honest scope of this fix:** structurally it closes the hole and makes the doc
true. In practice a *user-visible* cross-surface confirmation is unlikely, because
the fingerprint is over the exact text and the tool path's text is
`"{name} {json args}"` — a chat message would have to match that byte for byte. The
value is that the two paths can no longer diverge, and the tool path's own
`take()` is now against a store something can actually grant into. The symmetric
risk is equally small and disclosed: one store now serves both surfaces, so a
byte-identical text could in principle have its message-send grant spent by a tool
call. The tool path's real recovery route is the ledger (F2), not this store.

## F4 — `AudioEgressGate` built a permanently non-degraded gate

**Fixed, not commented.** `AudioEgressGate::new` now REQUIRES the shared
`Arc<ClassifierHealth>` and builds `PrivacyGate::with_health`. Nothing constructs
this in production yet (the voice loop is unwired), so C-01 was not being
bypassed — but a defaulted constructor was a trap for whoever wires it. Making
`health` a required argument means the healthy choice has to be written out.

Test: `a_degraded_classifier_withholds_cloud_tts_that_the_fallback_would_clear`
— healthy control arm (Allow) + degraded (Withhold) + degraded-but-local (Allow,
so fail-closed does not brick the offline voice path).
